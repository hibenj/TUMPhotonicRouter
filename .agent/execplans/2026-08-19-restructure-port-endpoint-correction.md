# Restructure port endpoint correction into one readable, well-tested stage

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. This document must be maintained in accordance with `.agent/PLANS.md`, which is checked into this repository at that path and describes the required structure and editing discipline for ExecPlans in general.

## Purpose / Big Picture

This repository (`TUMPhotonicRouter`) routes optical waveguides on a discrete grid, then "corrects" the very start and end of each route so its centerline lands exactly on the real, physical port it connects to (a port's physical center is an arbitrary micrometer coordinate set by the chip layout, not something constrained to a router grid point, so a small correction at each end is normal, not a sign of a bug). Today, "correct this net's endpoints" is not one thing: it is three separate top-level passes over the routed nets (`_apply_checked_endpoint_corrections_for_net_ids`, `_apply_checked_fanout_stub_endpoint_corrections_for_net_ids`, `_apply_crossing_aware_endpoint_corrections_for_net_ids`, all in `translation/route_rust.py`), run one after another, each deciding independently which nets it is and is not responsible for, with duplicated logic between them and, in the crossing-aware path specifically, a silent fallback chain that can produce a wrong-but-plausible-looking answer instead of a clearly-flagged failure -- this is exactly what happened in a real bug fixed the day before this plan was written (`.agent/execplans/2026-08-18-crossing-aware-endpoint-correction-direction-sequence.md`), where a valid correction was silently discarded and the code fell back, twice, to a worse answer that missed the real port by `2.0014` micrometers before a downstream verification check finally caught it.

After this plan is complete, there will be exactly one place a reader goes to understand "how does this net's endpoints get corrected, and why": one entry point, called once per routing run, that reads top-to-bottom as a short, obvious sequence (classify each net's situation, then apply the one correction strategy that situation calls for), backed by focused unit tests for each distinct situation rather than relying only on full-benchmark verification to catch a regression. A person can see this working two ways: (1) reading the new orchestration code and being able to answer "which of the three (now unified) treatments does net X get, and why" without tracing through duplicated boilerplate in three different functions; (2) running the exact regression scenario from the `2026-08-18` bug fix as a new, fast, focused test (no full benchmark needed) and seeing it fail on the old code shape and pass on the new one.

## Surprises & Discoveries

- Observation: the actual scope here is bigger, and more architecturally justified, than "endpoint correction has 5 duplicate rules that should collapse into 1." Reading the real call sites (`translation/route_rust.py`, around line 6923-6947, where `_RouteNetsRustSession.run()` calls all three passes in sequence) shows the three passes exist because there are two genuinely independent, real constraints on a net's endpoints, not accidental duplication: (a) whether the net's route crosses another route (a net involved in a crossing cannot have its endpoint freely re-corrected by the "unrestricted" native corrector, because that corrector is free to move geometry anywhere along the route, including the region right around the crossing point that must stay fixed -- see the comment at `translation/route_rust.py` line 4707-4712 explaining exactly this for the fanout-stub case), and (b) whether the net's source or target is a "fanout stub" (a pre-corrected adapter used for dense multi-port fan-out, which must not be re-corrected on that side). These two axes combine into the three passes: plain nets get the unrestricted corrector directly (`_apply_checked_endpoint_corrections_for_net_ids`); fanout-stub nets get a partial version of the same unrestricted corrector, skipping the already-corrected side (`_apply_checked_fanout_stub_endpoint_corrections_for_net_ids`); and any net involved in a crossing, regardless of fanout-stub status, is excluded from both of those and handled entirely by the separate, restricted, splice-based mechanism (`_apply_crossing_aware_endpoint_corrections_for_net_ids`, backed by `translation/route_rust_endpoint_correction.py`). This does not mean the current code is fine as-is -- see the next two observations -- but it does mean the restructuring must preserve this real, two-axis classification, not naively merge everything into one code path that ignores it.
- Observation: the two passes that call the "unrestricted" native corrector (`_apply_checked_endpoint_corrections_for_net_ids` and `_apply_checked_fanout_stub_endpoint_corrections_for_net_ids`) each independently re-derive the same `crossing_net_ids` set from `self.router.crossing_events()`, with identical boilerplate, including an identical `except Exception: crossing_net_ids = set()` that silently swallows any error and proceeds as if no crossings existed at all (`translation/route_rust.py`, around lines 4512-4526 and 4680-4694). This is a second instance of exactly the class of problem the `2026-08-18` plan already found once in the crossing-aware path: a failure that should be visible (crossing detection genuinely failed) is instead silently treated as a normal, unremarkable case (no crossings). Confirm during this plan's Milestone 0 whether this has ever actually been observed to fire in practice (it may never have been hit, in which case removing the swallow entirely and letting a real error propagate is likely the right fix, not adding more defensive code around it).
- Observation: there is already substantial, real focused test coverage for pieces of this area -- `tests/test_port_alignment_diagnostics.py` has roughly 25 tests directly exercising `_absorbed_terminal_centerline`, the crossing-aware correction path, and the "checked" batch corrector (`apply_checked_endpoint_corrections`/`apply_checked_endpoint_corrections_and_commit`), including tests with names like `test_crossing_aware_endpoint_correction_rejects_inserted_mid_access_geometry` and `test_crossing_aware_endpoint_correction_absorbs_both_split_terminal_sides`. This plan's own "add focused tests" work is not starting from zero, and should extend and reuse this file's existing fixtures and patterns rather than inventing a new, parallel test style. What is genuinely missing, confirmed by reading the diff of the `2026-08-18` bug fix directly (`git show 20aab29 --stat`), is a dedicated regression test for the *specific* bug class just fixed: a candidate correction whose newly-inserted segment lands at the position `_compatible_terminal_direction_sequence` does not expect, for the specific reason that the baseline's own port-adjacent segment already matched the port's facing direction. That fix's only verification was a full `multiportmmi_8x8` benchmark run; nothing in `tests/test_port_alignment_diagnostics.py` or elsewhere pins this exact scenario down at the unit level, so a future change could silently reintroduce it without any test noticing until the next full-benchmark run.

## Context and Orientation

This section assumes no knowledge of any prior conversation or prior ExecPlan. Every fact needed to understand and execute this plan is repeated here.

### What "endpoint correction" means and why it exists

The router finds paths on a discrete grid (`grid_size_um` micrometers per cell). A port's real, physical connection point is an arbitrary `(x, y)` coordinate in micrometers, set by the chip's component layout -- it is essentially never exactly on a grid cell boundary. "Endpoint correction" is the step, run once per net after routing and before the final GDS chip layout is written, that adjusts the very start and end of that net's centerline (the sequence of `(x, y)` points describing its physical shape) so it lands exactly on the real port, not just close to it. This is normal, necessary, and already mostly correct; this plan is about *how the code is organized*, not about changing the correction math itself except where a bug is found.

### The three current passes, and the two real constraints behind them

All three passes are called from `_RouteNetsRustSession.run()` in `translation/route_rust.py`, in this exact order, around lines 6923-6947 (guarded by `if self.enable_checked_endpoint_correction:`):

1. `_apply_checked_endpoint_corrections_for_net_ids` (`translation/route_rust.py`, line 4485): the default pass. Builds a batch of `(net_id, route_obj, opened_candidate_cells, clearance_exempt_cells, source_port_um, target_port_um)` tuples for every net that is not a fanout-stub net and not involved in a crossing, then calls a single Rust batch method, `self.router.apply_checked_endpoint_corrections(...)` (line 4564), which does the actual geometric correction work in Rust.
2. `_apply_checked_fanout_stub_endpoint_corrections_for_net_ids` (`translation/route_rust.py`, line 4651): for nets where exactly one side (source or target, never both, per the `if source_has_fanout_stub and target_has_fanout_stub: continue` check at line 4705-4706) is a "fanout stub" -- a pre-corrected endpoint adapter used for dense multi-port fan-out patterns, which must not be touched again -- this pass calls the *same* Rust method, `apply_checked_endpoint_corrections`, but only requests correction for the non-stub side (`source_port = None if source_has_fanout_stub else ...`, line 4716-4720). It also excludes any net involved in a crossing, with an explicit comment (line 4707-4712) explaining why: the unrestricted corrector could move geometry on the crossing-protected side before the crossing-aware pass gets a chance to splice it correctly.
3. `_apply_crossing_aware_endpoint_corrections_for_net_ids` (`translation/route_rust.py`, line 5109): handles every net excluded from the first two passes -- anything involved in a crossing. This is the only pass that does *not* call the simple batch Rust method directly; instead it calls `_apply_crossing_aware_endpoint_correction_to_record` (`translation/route_rust_endpoint_correction.py`, line 1053), which is where the `2026-08-18` plan's bug lived. That function's job is to get the *same* rich, unrestricted correction the other two passes use (it does call `route_port_corrected_centerline`, the identical underlying Rust correction, via `_spliced_crossing_endpoint_centerline`, line 682) but then slice out only the portion of that correction from the route's start to the first crossing point (or the last crossing point to the route's end), so the crossing-protected middle region is never touched. If that sliced portion fails a compatibility check (`_compatible_terminal_direction_sequence`, line 621 -- the function fixed in the `2026-08-18` plan), it falls back to a second, weaker, Python-only solver (`_absorbed_terminal_centerline`, line 439) limited to a small "guard window" near the crossing point; if *that* also fails, it silently falls back a third time to the raw, uncorrected route for that region (`translation/route_rust_endpoint_correction.py`, lines 786-787 and 807-808).

Both of the first two passes independently re-derive the same `crossing_net_ids` set (which nets are involved in any crossing) from `self.router.crossing_events()`, with near-identical boilerplate including an identical `except Exception: crossing_net_ids = set()` (lines 4512-4526 and 4680-4694) -- see Surprises & Discoveries for why this specific duplication is itself worth fixing, separately from the deeper crossing-aware fallback bug already fixed.

### The `2026-08-18` bug, as a concrete example of the pattern to eliminate

`.agent/execplans/2026-08-18-crossing-aware-endpoint-correction-direction-sequence.md` (already complete, commit `20aab29`) fixed one specific instance of a broader pattern: a correction strategy inside the crossing-aware path silently failed and fell through to a worse fallback, without that failure ever being visible until a much later, separate verification stage caught the final, wrong result. The specific bug was in `_compatible_terminal_direction_sequence`: it assumed the one newly-inserted correction segment always sits at a fixed position in a list of directions, when in the common case (the baseline's own port-adjacent segment already matches the port's facing direction) the real, correct new segment lands at the *other* position instead -- rejecting an already-correct answer and triggering two further silent fallbacks, the last of which returned the raw, uncorrected route for that region, landing `2.0014` micrometers from the real port against a `2.0` micrometer tolerance. Read that plan's own Surprises & Discoveries section in full for the exact evidence trail; it is not repeated here, but the general shape -- "a correction strategy can fail, and when it does, the code keeps trying progressively worse fallbacks without ever surfacing that a fallback happened at all" -- is the central problem this restructuring plan exists to eliminate, not just patch one instance of.

### Relevant existing test coverage

`tests/test_port_alignment_diagnostics.py` (about 1050 lines) already has substantial, real, focused coverage of pieces of this area: tests calling `_absorbed_terminal_centerline` directly with hand-constructed centerlines (for example `test_crossing_aware_endpoint_correction_keeps_required_port_straight`, line 867, and `test_crossing_aware_endpoint_correction_does_not_modify_bend_samples`, line 882), tests of the crossing-aware path's rejection behavior (`test_crossing_aware_endpoint_correction_rejects_inserted_mid_access_geometry`, line 803; `test_crossing_aware_endpoint_correction_rejects_unanchored_source_prefix`, line 846), and tests of the "checked" batch corrector directly via the Rust binding (`test_batch_checked_endpoint_correction_returns_per_net_metadata`, line 544; several `test_checked_case4_bump_*` tests around lines 392-544). This plan's testing work should read this file first and extend it, not duplicate its patterns from scratch.

## Plan of Work

### Milestone 0: characterize current behavior before changing anything

Before any restructuring, write characterization tests (tests that record and pin down the *current*, real behavior of the system as it exists today, including any warts, so later milestones can be validated against "did this change on purpose" rather than discovering a difference only by re-running a full benchmark) for: (a) which of the three passes a net with a given combination of (has a crossing: yes/no, has a fanout stub on source: yes/no, has a fanout stub on target: yes/no) actually gets routed through today -- this is the classification logic this plan's later milestones will consolidate, and it needs to be pinned down precisely, including edge cases like a net with fanout stubs on *both* sides (currently skipped by the fanout-stub pass entirely per the `continue` at line 4705-4706 -- confirm what actually happens to such a net today, since it is excluded from pass 2 but may or may not also be excluded from pass 1 depending on its crossing status, and Milestone 0 should determine and record the real, current answer rather than assume one); and (b) a new, focused regression test for the exact `2026-08-18` bug scenario (a correction whose new segment lands at the position `_compatible_terminal_direction_sequence` does not expect for `allow_extra_at_start=True`), confirmed to fail if the fix from that commit were reverted and pass with it in place -- this closes the gap identified in Surprises & Discoveries. Also confirm, empirically, whether the `except Exception: crossing_net_ids = set()` swallow at lines 4512-4526/4680-4694 has ever actually been observed to catch anything (search git history and any logged/recorded evidence; if none is found, plan to remove the swallow in a later milestone rather than preserve it).

### Milestone 1: consolidate net classification into one place, additively

Add one new function (exact name and location to be decided during implementation, once the current code is read fresh -- a reasonable starting point is a method on `_RouteNetsRustSession` or a small dataclass/enum-returning helper in `translation/route_rust.py`, but do not lock this in before reading the code, per `.agent/PLANS.md`'s own guidance against over-specifying before source inspection) that computes, once, for every net, which of the (now-named, not just implicit) correction categories it belongs to: no correction needed, plain/unrestricted, fanout-stub-source-only, fanout-stub-target-only, or crossing-aware. This subsumes the currently-duplicated `crossing_net_ids` derivation (compute it once, pass it in) and makes the fanout-stub-both-sides case (whatever Milestone 0 found the current real answer to be) an explicit, named outcome instead of an implicit fallthrough. This milestone is purely additive: the three existing passes keep running exactly as they do today, just reading their net-id sets from this new, shared classification instead of each re-deriving their own. Validate with Milestone 0's characterization tests: the classification for every net in a real benchmark run should match what Milestone 0 recorded as current behavior, cell for cell.

### Milestone 2: make failure visible

Replace the crossing-aware path's silent fallback-to-uncorrected-baseline (`translation/route_rust_endpoint_correction.py`, lines 786-787 and 807-808 in the state as of commit `20aab29`) with something that records, at minimum in the diagnostics already written to `build/routes/*_diagnostics.txt`/`*_FAILED.txt` for other routing decisions in this repository, that a fallback occurred and which one -- so a future case like the `2026-08-18` bug would be visible immediately (in per-net diagnostics, the same place a routing failure is already visible) rather than only surfacing much later via a separate photonic-verification failure, or worse, silently landing just inside tolerance and never being caught by anything except a full geometric audit. Apply the same principle to the two `except Exception: crossing_net_ids = set()` sites from Milestone 0, per what that milestone found (remove the swallow if it has never legitimately fired, or make it visible if it can).

### Milestone 3: collapse the top-level entry point into one readable sequence

Once Milestones 1 and 2 exist, restructure `_RouteNetsRustSession.run()`'s three sequential calls (lines 6923-6947) into one call to a single, clearly-named orchestration function that, read top-to-bottom, tells the whole story: classify nets (Milestone 1's function), then for each category, apply the one correction strategy that applies, using the now-visible-on-failure mechanics from Milestone 2. This is the milestone that delivers the user's stated goal directly ("one file where you can really read the workflow from") -- the underlying Rust calls and correction algorithms should not need to change at all for this milestone; it is purely about how the dispatch is organized and named.

### Milestone 4: broaden test coverage

Extend `tests/test_port_alignment_diagnostics.py` with focused tests for the new classification function (Milestone 1) and the failure-visibility mechanism (Milestone 2), reusing that file's existing fixture patterns. Do not remove or weaken any existing test in that file without independently confirming, the same way this repository's other recent plans have, that the property it protects is preserved by the restructuring, not just that it happens to still pass.

### Milestone 5: broad validation

Run the full validation ladder: `PYTHONPATH=. .venv/bin/pytest -q` (expect no new failures beyond whatever this plan intentionally changes); `benes_4x4` and `multiportmmi_8x8` end to end, reading `build/verification/*.json` directly for both crossing and photonic verification (per `.agent/WORKFLOW.md`'s Routing Verification Gate -- a passing `pytest` run does not satisfy this on its own). Critically, given a discovery made the day this plan was written: `multiportmmi_8x8` and `multiportmmi_16x16` both have a documented "stable crossing-router baseline" configuration recorded as a comment in `benchmarks/multiportmmi_8x8.py` and `benchmarks/multiportmmi_16x16.py` (`STABLE_ROUTING_ENV`/`STABLE_ROUTING_FLAGS` -- two environment variables, `PHOTONIC_ROUTER_LONG_STRAIGHT_CONGESTION_WEIGHT=0.05` and `PHOTONIC_ROUTER_FANOUT_STUB_BEND_DEGREES=90`, plus `--crossings true --crossing-mode lidar-pure --fanout-access-mode static-stubs --routing-window-scale 0.35 --foreign-port-keepout-cells 0`), which differs substantially from the router's own bare CLI defaults on three of those four flags.
