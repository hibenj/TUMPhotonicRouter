## Purpose / Big Picture

The repository owner's prioritized finding (2026-09-01, with GDS screenshots): large parts of the multiportmmi layouts route as 90-degree Manhattan geometry where 45-degree diagonals are obviously better -- nested rectangular detours around the dense fan-in groups (32x32, and visibly also 16x16), and even the FIRST-layer fanout's upper routes, which commit early into empty space. "Die 90 grad routen verschlechtern die route qualitaet. das wuerde ich analysieren und reparieren." The reference router (LiDAR, ~/Documents/Repositories/working/LiDAR) routes the identical multiportmmi_32x32 input clean with wide diagonal fans (1257 s, DRV 0, 50 crossings) under the SAME perpendicular-crossing rule (verified in its `drc/drcmanager.py`: `(check_ori + nType) % 180 == 0`), so the degradation is our engine's behavior, not a law of the topology. LiDAR is the reference for detecting problems -- explicitly NOT a template to copy (owner direction).

After this plan, routes are diagonal wherever geometry allows, 90-degree only where genuinely necessary; measurably: the Manhattan-excess of multiportmmi_16x16 drops, the first-layer fanout in the owner's screenshot routes as symmetric diagonals, and `multiportmmi_32x32` progresses past its current `n_108` collapse (net 109/447) -- ideally to clean completion, closing the "32x32 under lidar-pure is a baseline must" goal.

## Surprises & Discoveries

- (2026-09-01, session 08c2c1e6) **Bare `routing_flow.py multiportmmi_32x32` is NOT the stable configuration**: `benchmarks/multiportmmi_32x32.py` has no `STABLE_ROUTING_FLAGS`/`STABLE_ROUTING_ENV`, so the flow's auto-stable-defaults feature applies nothing and a bare run uses script defaults -- it then fails EARLIER, at `n_110` (`not_perpendicular` repair cascade against n_111), not at net 156. mm32 runs must pass the mm16-inherited config explicitly: env `PHOTONIC_ROUTER_LONG_STRAIGHT_CONGESTION_WEIGHT=0.05 PHOTONIC_ROUTER_FANOUT_STUB_BEND_DEGREES=90`, flags `--crossings true --crossing-mode lidar-pure --fanout-access-mode static-stubs --foreign-port-keepout-cells 0`. (Same trap class as the `run_routing_flow` direct-call finding below.) Also confirmed en passant: rust `net_id` == the numeric part of the net name (n_156 <-> net_id 156), while the flow's `[i/N]` counter is the 1-based execution position, which differs.

- (2026-09-01) The long-documented "direct `run_routing_flow(...)` fails at a different net than the real CLI under nominally identical flags" mystery (2026-08-26 target-side-stubs plan, Decision Log) is explained: `main()` applies the benchmark's `STABLE_ROUTING_ENV` via `os.environ.setdefault` BEFORE routing; a direct `run_routing_flow` call skips that, so e.g. `PHOTONIC_ROUTER_LONG_STRAIGHT_CONGESTION_WEIGHT=0.05` and `FANOUT_STUB_BEND_DEGREES=90` are silently absent and multiportmmi_16x16 then fails at n_113 (observed in this plan's attribution harness; CONFIRMED: with the two env vars set, the direct call routes the benchmark cleanly and matches the CLI). Scripts that call `run_routing_flow` directly must set the benchmark's STABLE_ROUTING_ENV themselves.

- (Carried from 2026-08-31/09-01 analysis) The perpendicularity rule does NOT forbid diagonals per se (owner's correction: diagonal x diagonal crossings are legal and occur); it forbids mixed-angle pairs. Manhattan geometry emerges where the crossed material is axis-aligned -- and our own mechanisms (orthogonal fallback commits, port-adjacent axis segments, possibly simple routes) keep producing exactly that material.
- LiDAR comparison facts (reference only): same perpendicularity rule; its 32x32 GDS has only 3.27 um^2 total waveguide overlap (clean by our overlap standard) and no tight bundling (densest slice: 49.25 um edge gaps); it uses a per-node escalating crossing budget instead of our 200 um search loss, and 10 ripup rounds with history.

Analysis recorded with the decision: Option 2 would NOT fix H2 for us -- a count cap bounds none of the pending dimensions, and net 156 needs ~11 crossings anyway, so the escalated pass would explode identically (LiDAR survives budget 10 only because its node key carries no crossing dimensions at all). Code finding that sharpened the fix: in the exploding 155-partner searches `require_all_partners=false`, so `crossed_mask` is NOT tracked there -- the measured ~63 variants/cell come entirely from `pending_after_crossing_{cells,angle,partner_index}` (partner index alone up to 155 values) times `straight_run_cells`. Design (lead, approved by owner "ja"): **eager completion chain in the unified kernel's Tier-2 branch** -- when a hook-evaluated move returns an outcome with `pending_after_crossing_cells > 0`, the kernel immediately completes the debt with forced 1-cell straight steps (each re-validated through the SAME `hook.evaluate`, which already consumes pending in both the contact and no-contact paths and legalizes any NEW crossings the completion run hits -- the dense-bundle case), pushes the intermediate nodes only as un-keyed parent scaffolding in `extended_nodes`, and enqueues/keys ONLY the final debt-free state. Pending states never enter `extended_state`/the open heaps; per-cell key variants collapse to `straight_run_cells` (<=6). All existing pending machinery (consume/reject logic, margins, reservations) is reused as the chain-step validator, not rewritten; an illegal completion abandons the whole move (today's per-state rejections, just earlier). Catalog note: the longest straight primitive is 4 cells < margin 5, which is exactly why pending exists across primitive boundaries and why the chain (not "reject missing_after>0" or longer primitives) is the right grid-shaped form of the owner's proposal.
