# Future Architecture Initiative: path-length matching interface (stage 4 of 4)

## Purpose / Big Picture

This is the fourth and final stage of `.agent/PROJECT_GOAL.md`'s "Future Architecture Initiative": give path-length matching (PLM) -- delay-structure insertion so benchmarks like `heater_s_mod` end up with matched optical path lengths -- a real, explicit interface (`typing.Protocol`/`abc.ABC` in Python, `trait` in Rust), matching the repository owner's C++-background target shape (functionality behind a header-declared interface both the implementation and its tests answer to). The prior three stages (obstacle map building + grid snapping, A* single-net search, geometry realization) are done; see `.agent/REPOSITORY_STATE.md`'s Completed ExecPlans for each. This plan follows the same characterize-first-then-present-options discipline the geometry-realization plan established, since interface/boundary design is a real tradeoff, not a mechanical step.

Milestone 0 (below) is a full characterization of PLM's current shape. It found something the prior stage-characterization plan's shallower pass did not: PLM is not one entangled stage needing a boundary decision the way geometry-realization/PLM was -- it is **two halves in very different states**, and the harder half already has more interface infrastructure in place (two private `Protocol`s already doing real work) than the initial characterization gave it credit for. Milestone 1 presents concrete options for what "add a real interface" should mean given that finding, to the repository owner, before any design or implementation proceeds.

## Context and Orientation

**Path-length matching (PLM)** is the routing-pipeline stage that inserts extra waveguide length (via "meanders" -- serpentine detours) into shorter optical paths so that paths meant to arrive together (e.g. both inputs to a 2x2 MMI splitter) have matched physical length, which matters for interference-based photonic components. It runs after net routing and before final GDS realization.

The stage splits into two halves, each already characterized in Surprises & Discoveries above:

1. **Graph/requirement computation** ("how much extra length does each edge need, and where could it be inserted"): `python/photonic_router/path_length_graph.py`, `translation/path_length_requirements.py`, `translation/path_length_candidates.py`, `translation/path_length_diagnostics.py`, unified under `translation/route_rust_analysis.py`'s facade. Pure Python, pure data in/data out, already `Protocol`-typed (`SchematicLike`).
2. **Meander insertion / candidate planning** ("given a required extra length on an edge, find and commit a physical meander geometry that achieves it"): `translation/route_rust_meanders.py` (Python orchestration, calling into the Rust backend via PyO3) and `src/plm.rs` (the Rust planning functions themselves, sitting on top of `src/auto_meander.rs`'s search core). Already has two private `Protocol`s, a real session dataclass, and (as of this session) direct Rust-level test coverage.

Key files by full path:

- `python/photonic_router/path_length_graph.py` (324 lines) -- graph model, `SchematicLike` Protocol, timing analysis.
- `translation/path_length_requirements.py` (308 lines), `translation/path_length_candidates.py` (319 lines), `translation/path_length_diagnostics.py` (460 lines) -- the three split-by-responsibility modules.
- `translation/route_rust_analysis.py` (59 lines) -- the existing compatibility facade over the three files above.
- `translation/route_rust_meanders.py` (3,139 lines) -- meander-insertion orchestration; `_RustBackendProtocol`/`_MeanderRouterProtocol` at `:38`/`:50`; `_MeanderPlannerContext` at `:210-1237`; `analyze_meander_insertion_for_requirements` (the real production entry point) at `:2263-3057`; `insert_meanders_for_requirements` (legacy/test-only) at `:3058-3139`.
- `translation/route_rust.py:534` -- the one production call site, inside `route_match_and_realize`.
- `src/plm.rs` (1,054 lines pre-test-addition, now larger with this session's 42 tests) -- the 4 public Rust planning functions and `RegisteredPlmContext`.
- `tests/test_path_length_graph.py` (2,983 lines, 39 tests) -- the only test file covering either half; despite its name, it covers both.

### Milestone 2 design finding (2026-08-20): the Rust and Python halves of Option B are not symmetric

Started Milestone 2 (design) immediately after Milestone 1's decision landed. Reading `_MeanderPlannerContext`'s 4 registered-planning methods' actual signatures (`plan_requirement_candidates_registered` `:323`, `plan_request_sequence_registered` (via `plan_mixed_request_candidate_registered` `:419` calling it), `plan_split_request_registered` `:572`, `plan_final_requests_registered` `:759`) found they do **not** mirror `plm.rs`'s 4 functions' clean, already-public, plain-typed signatures the way Option B's description assumed.
