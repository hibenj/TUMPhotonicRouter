This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. ## Purpose / Big Picture

This is the third step of `.agent/PROJECT_GOAL.md`'s "Future Architecture Initiative," continuing the recommended order from `.agent/execplans/2026-08-19-future-architecture-initiative-stage-characterization.md` (obstacle map building + grid snapping, done; A* single-net search, done -- see `.agent/execplans/2026-08-19-extract-astar-single-net-search-interface.md`; now geometry realization and path-length matching).

Unlike the two prior extractions, this one starts with an open design question instead of a clean scope: the stage-characterization plan found `src/geometry_realization.rs` (8,273 lines, 70 `#[test]`s) and `src/plm.rs` (1,053 lines, **zero** `#[test]`s) coupled at the Rust type level -- `plm.rs` directly imports meander-geometry types (`AutoMeanderConfig`, `AutoMeanderPlanningProfile`, `AutoMeanderSidePolicy`, `AutoRouteAnalyticMeanderPlan`, `DenseOccupancyPrefix`, `GeometryGridSpec`, `SparseCellIndex`, plus the function `plan_auto_analytic_meander_for_centerline_depth_sweep_with_prefix` and `cell_count_in_grid_rect`) straight from `geometry_realization.rs`. **A preliminary check while scoping this plan (2026-08-20) found the picture is more tangled than a two-file coupling**: a third module, `src/meander.rs` (898 lines), defines its own parallel-looking meander types (`AnalyticMeanderConfig`, `AnalyticMeanderPlan`, `MeanderBox`, `MeanderPlanningMode`, `MeanderTurnModel`) with similar-but-differently-named counterparts to `geometry_realization.rs`'s `AutoMeanderConfig`/`AutoRouteAnalyticMeanderPlan` -- whether these are two genuinely separate systems (older/newer, or different purposes), or one wraps/supersedes the other, is not yet established. On the Python side, at least 5 files plausibly split across these same concerns without a confirmed mapping yet: `translation/route_rust_meanders.py` (3,139 lines, the largest single Python file in `translation/`), `translation/path_length_candidates.py`, `translation/path_length_diagnostics.py`, `translation/path_length_requirements.py`, and `python/photonic_router/path_length_graph.py` (already confirmed, by the characterization plan, to use `typing.Protocol` -- existing prior art for this exact pattern).

Given this, this plan does not commit to a boundary or an interface design up front. Milestone 0 is a thorough characterization of the real coupling (which types/functions genuinely belong to "realize this route's geometry" versus "plan delay-matching meanders" versus something in between, and how `meander.rs` relates to both). Milestone 1 is presenting concrete boundary options, with tradeoffs, to the repository owner -- **this milestone requires the repository owner's decision, not a solo Claude choice**, per the repository owner's own direction (2026-08-20): characterize first, then present options, matching how the dense-port lateral-width finding (a different, unrelated design question, `.agent/REPOSITORY_STATE.md` Current Findings item 2) was handled. Milestones after that (design the actual interface(s), implement, test, validate) are intentionally left unspecified until Milestone 1's decision lands, per `.agent/PLANS.md`'s guidance against over-specifying before the design is justified.

This plan follows the repository owner's standing direction to use the Claude+Codex flow (`.agent/CLAUDE_CODEX_FLOW.md`) for implementation slices once a change is bounded and well-specified, and the zero-behavior-change discipline established by the two prior extractions -- once a boundary is chosen and an interface designed, implementation should move/rename/formalize existing behavior, not change it.

## Surprises & Discoveries

- **Preliminary finding (2026-08-20, before Milestone 0 formally began)**: `src/meander.rs` (898 lines) exists as a third module with its own meander-planning types (`AnalyticMeanderConfig`, `AnalyticMeanderPlan`, `MeanderBox`, `MeanderPlanningMode`, `MeanderTurnModel`, `MeanderPlanningError`, `MeanderSide`, `PhysicalPoint`, `StraightSegment`, `AnalyticMeanderFootprint`), separate from `geometry_realization.rs`'s `AutoMeanderConfig`/`AutoMeanderPlanningProfile`/`AutoMeanderSidePolicy`/`AutoRouteAnalyticMeanderPlan`/`DenseOccupancyPrefix`/`SparseCellIndex`. `plm.rs` imports `MeanderPlanningMode` from `meander.rs` directly (`src/plm.rs:10`) in addition to its imports from `geometry_realization.rs` (`src/plm.rs:5-9`). `src/plm.rs` itself has zero `#[test]`s (confirmed via `grep -c '#\[test\]' src/plm.rs`), consistent with the stage-characterization plan's earlier finding.

- **Q1/Q2 answer -- this is a clean, one-directional 3-layer stack, not a symmetric two-file coupling, and `plm.rs` has no real dependency on realization-proper code at all.** Read `src/plm.rs` in full (1,053 lines) and traced every import to its definition and usage:
  - **`meander.rs` (lowest layer, self-contained)**: pure analytic meander math -- `plan_analytic_meander`, `plan_fill_box_multi_bump_footprint`, `AnalyticMeanderConfig`, `AnalyticMeanderPlan`, `MeanderBox`, `MeanderSide`, `MeanderPlanningMode`, `MeanderPlanningError`, plus geometric primitives (`PhysicalPoint`, `StraightSegment`, `MeanderTurnModel`, `AnalyticMeanderFootprint`). Confirmed zero references back to `geometry_realization.rs` or `plm.rs` (`grep -n "AutoMeander\|geometry_realization" src/meander.rs` returns nothing) -- this module is a genuine, independent leaf.
  - **`geometry_realization.rs` (middle layer) bundles two separable concerns that happen to share a file, not one coherent stage**: (a) route-to-polygon realization proper (endpoint correction, crossing insertion, `route_to_primitive_centerline`, per `.agent/PROJECT_GOAL.md`'s stage description) and (b) an obstacle-aware "Auto" meander-search layer (`AutoMeanderConfig`, `AutoMeanderPlanningProfile`, `AutoMeanderSidePolicy`, `AutoRouteAnalyticMeanderPlan`, `plan_auto_analytic_meander_for_centerline_depth_sweep_with_prefix` at `src/geometry_realization.rs:4641`, `cell_count_in_grid_rect` at `:3690`) that **imports from `meander.rs`** (`src/geometry_realization.rs:14-16`: `plan_analytic_meander`, `plan_fill_box_multi_bump_footprint`, `AnalyticMeanderConfig`, `AnalyticMeanderPlan`, `MeanderBox`, `MeanderPlanningError`, `MeanderPlanningMode`, `MeanderSide`) and wraps its output type (`AutoRouteAnalyticMeanderPlan.plan: AnalyticMeanderPlan`, `:3746`). This "Auto" layer sweeps `meander.rs`'s single-attempt analytic planner across multiple depths/positions with obstacle-occupancy awareness (`DenseOccupancyPrefix`, `SparseCellIndex`) to find a legal meander. `DenseOccupancyPrefix`/`SparseCellIndex` are used **only** within this Auto-meander-search family in `geometry_realization.rs` (confirmed by reading every non-definition usage site: `check_meander_box_free` at `:3673`, the route-based sweep wrapper at `:4348`, and the `mod tests` block -- all meander-search-related, none in the realization-proper endpoint-correction/crossing-insertion code). `GeometryGridSpec`, by contrast, **is** genuinely shared infrastructure -- 39 usages across the file, including realization-proper code, not just the Auto-meander family -- so it is not part of this misplacement.
  - **`plm.rs` (top layer) depends on exactly the "Auto" meander-search family above, and nothing from realization proper.** Every one of `plm.rs`'s 4 public planning functions (`plan_registered_geometry_requirement_candidates`, `_request_sequence`, `_split_request`, `_final_requests`, all confirmed present at `src/plm.rs:391,533,648,791`) bottoms out in one shared helper, `plan_registered_geometry_sequence_at_endpoint` (`src/plm.rs:253`), which calls `plan_auto_analytic_meander_for_centerline_depth_sweep_with_prefix` directly with an **already-extracted centerline** (`&geometry.centerline`, a plain `Vec<(f64, f64)>` field on `RegisteredMeanderGeometry`, `src/plm.rs:14-18`) -- `plm.rs` never touches `RouteResult`, `PrimitiveLibrary`, or `route_to_primitive_centerline` itself. The one place a `RouteResult`-consuming variant of the meander planner exists, `plan_auto_analytic_meander_for_route_depth_sweep_with_prefix` (`src/geometry_realization.rs:4613`, which calls `route_to_primitive_centerline` then delegates to the centerline-based planner), is called from exactly one place in the whole codebase -- `src/py_router.rs:12933` -- and `plm.rs` is not involved in that call path at all (confirmed via `grep -rn "plan_auto_analytic_meander_for_route_depth_sweep_with_prefix" src/*.rs`, only 3 hits: its own definition, an import alias, and that one call site). So the "coupling" `plm.rs` has with `geometry_realization.rs` is not a genuine cross-stage dependency on realization -- it is a dependency on meander-search code that is currently *stored inside* `geometry_realization.rs` but conceptually belongs with path-length matching, not with realizing a route's physical geometry.

- **Q3 answer -- the Python side already reflects roughly the same split, including existing `Protocol` prior art specifically for this surface.** `translation/route_rust_meanders.py`'s own module docstring reads "Meander planning helpers for **path-length matching**" (`translation/route_rust_meanders.py:1`) -- the file's own author already considered this PLM's territory, not realization's, despite the "meanders" name. It defines two `typing.Protocol`s (`translation/route_rust_meanders.py:38,50`): `_RustBackendProtocol` (a thin structural type for the PyO3 module) and, more relevantly, `_MeanderRouterProtocol` -- a full structural interface over `PyPhotonicRouter`'s PLM/meander-related PyO3-bound methods, including `plan_auto_analytic_meander_requirement_candidate_indices_registered_opened_auto_config` and 3 siblings that are the PyO3 bindings for exactly `plm.rs`'s 4 public functions read above, plus `register_meander_route_geometries`/`add_registered_meander_reserved_cells`/etc. (the Python-side counterpart of `RegisteredPlmContext`). This is a second piece of existing `Protocol` prior art in this codebase (the first being `python/photonic_router/path_length_graph.py`'s `SchematicLike`, found by the stage-characterization plan) -- and it already covers almost exactly the Rust-side PLM surface this plan is investigating, which meaningfully de-risks and shrinks whatever Python-side interface work a later milestone would need. `translation/path_length_candidates.py`/`translation/path_length_diagnostics.py`/`translation/path_length_requirements.py` were not read in full given time budget, but their names and `python/photonic_router/path_length_graph.py`'s already-confirmed scope (graph construction/annotation, not meander geometry) suggest they sit one layer up from `route_rust_meanders.py`, closer to "which edges need how much extra length" than to "how do I physically insert a meander" -- worth a closer read in Milestone 1's design, not yet confirmed to the same evidence standard as the rest of this entry. `translation/route_rust_realization.py`/`translation/route_rust_geometry.py` were not found to reference PLM/meander concerns in this pass (not exhaustively re-verified here, per prior sessions' own characterization of those files as endpoint-correction/geometry sub-pieces).

- **Q4 answer -- test coverage confirms the same split exists at the test level: of `src/geometry_realization.rs`'s 70 `#[test]`s, 28 (40%) specifically reference `AutoMeander`/`plan_auto_analytic_meander` (confirmed via `grep -c` scoped to the `mod tests` block), the rest presumably realization-proper (not individually categorized further, time-boxed).** This means the Auto-meander-search tests are already a distinguishable, non-trivial (28 tests) chunk that would move cleanly with the code if it moved, not a small afterthought. `plm.rs`'s zero tests are exercised only via `src/py_router.rs`'s 4 real call sites, confirmed at `src/py_router.rs:13236,13318,13402,13488` (closely matching, and refining, the prior characterization's approximate `13215-13467` range) -- each inside a `#[pymethods]` PyO3-bound method reading from `self.registered_plm` (a `RefCell<RegisteredPlmContext>`) and other `self.*` config fields, consistent with the earlier characterization's finding that `plm.rs`'s only exercise today is through this orchestration layer, not direct unit tests.

- **Q5 answer -- no further hidden duplication found beyond the layering itself; the "coupling" is real but is a misplacement (wrong file), not a symmetric shared-ownership problem.** No evidence of formula-level duplication between `meander.rs` and `geometry_realization.rs`'s Auto-meander layer (the latter wraps/sweeps the former, it does not reimplement it) or between `geometry_realization.rs` and `plm.rs`. The one genuine shared-infrastructure type crossing all three files is `GeometryGridSpec` (grid width/height/origin/size), which is correctly treated as common and is not part of the misplacement.

- **Boundary options for Milestone 1** (evidence-grounded, not ranked -- repository owner to choose):
  1. **Move the Auto-meander-search layer out of `geometry_realization.rs`.** Relocate `AutoMeanderConfig`/`AutoMeanderPlanningProfile`/`AutoMeanderSidePolicy`/`AutoRouteAnalyticMeanderPlan`/`DenseOccupancyPrefix`/`SparseCellIndex`/`cell_count_in_grid_rect`/`plan_auto_analytic_meander_for_centerline_depth_sweep_with_prefix` (and the 28 tests that exercise them) into a new module (e.g. sitting next to `meander.rs`, or merged into `plm.rs` itself) -- leaving `geometry_realization.rs` genuinely scoped to route-to-polygon realization only, and giving path-length matching a clean, self-contained 2-layer stack (`meander.rs` -> the relocated Auto-search layer -> `plm.rs`) that can then get its own trait/`Protocol` without touching realization at all. Directly fixes the root cause found (misplacement, not a real coupling). Tradeoff: the largest mechanical change of the three options -- real code motion across ~950 lines plus 28 tests, and `plan_auto_analytic_meander_for_route_depth_sweep_with_prefix`'s one call site (`src/py_router.rs:12933`) and its dependency on `route_to_primitive_centerline` need care so the one legitimate cross-layer bridge (route -> centerline -> meander search) still works cleanly after the move.
  2. **Leave the file layout as-is; add a purely-additive trait/`Protocol` at the `plm.rs`<->`geometry_realization.rs` boundary**, covering just the meander-planning surface `plm.rs` actually calls (mirroring the two closed sibling plans' low-risk posture: no code motion, format the existing contract, e.g. a `MeanderSearch` trait wrapping `plan_auto_analytic_meander_for_centerline_depth_sweep_with_prefix`). Lowest effort and risk of the three, matches the pattern that already worked twice. Tradeoff: does not fix the actual structural finding (the Auto-meander code still physically lives in the wrong file, mixed with unrelated realization-proper code in an 8,273-line file) -- formalizes a boundary around a misplacement rather than correcting it, which may read as papering over the real issue just found.
  3. **Hybrid: move only the data/config/plan types, leave the search algorithm in place.** Relocate the type definitions (`AutoMeanderConfig`, `AutoMeanderPlanningProfile`, `AutoMeanderSidePolicy`, `AutoRouteAnalyticMeanderPlan`) to sit with `plm.rs` or a shared module, since they are what `plm.rs` actually names in its own public signatures, but leave `plan_auto_analytic_meander_for_centerline_depth_sweep_with_prefix` itself (the search algorithm, which calls other `geometry_realization.rs`-local helpers like `check_meander_box_free`/`meander_box_to_grid_rect` not yet fully traced in this pass) in `geometry_realization.rs`, exposed through a trait. Smaller mechanical change than option 1 (types only, not the algorithm or its 28 tests), while still moving plm.rs's own vocabulary out of realization's file. Tradeoff: leaves a real function (the actual meander search) in a file that doesn't conceptually own it, and splits the Auto-meander family's types from its implementation across two files/modules, which could itself become the "next session's confusing finding" the same way this plan's own predecessor findings kept compounding.
