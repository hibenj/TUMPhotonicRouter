## Purpose / Big Picture

This repository's crossing-legality logic (`src/py_router.rs`) supports two conceptually different modes: `allow_only_expected_pairs` (crossings are pre-planned from the schematic's topology -- a net is only allowed to cross specific, named partners decided before routing starts) and `lidar-pure` (the mode this repository's active benchmarks actually use -- a net's crossings are discovered by colliding with whatever is physically nearby during the search, not pre-decided). The repository owner's own mental model of `lidar-pure` is simple: A* just routes, and when it collides with another net's cell, it asks "which net is this and is crossing it legal here." Reading the real code this session (while diagnosing and fixing `.agent/execplans/2026-08-19-fix-collision-crossing-zero-event-acceptance.md`'s bug) found that the actual implementation does not read that cleanly: there are at least seven distinctly-named "find the candidate partner nets" functions and at least three independent, hand-written, textually-divergent blocks of code (in three different top-level functions) that each separately decide "what partner set should I use for a collision-crossing attempt on this net" -- and two of those three disagree with each other about how `lidar-pure` mode should behave. The bug just fixed lived inside exactly this tangle, and its investigation is what surfaced the tangle in the first place, not a separate audit.

After this plan is complete, there will be one clear, well-tested answer to "how does this repository decide which other nets a route might legally cross, and where does that decision get made" -- matching the repository owner's own reactive, collision-driven mental model wherever `lidar-pure` mode is active, with whatever remains of the older `allow_only_expected_pairs`-specific plumbing clearly separated from it rather than sharing functions that silently branch between two different intents.

## Surprises & Discoveries

- Observation: there are at least seven distinctly-named "candidate partner set" functions in `src/py_router.rs`, found while tracing the collision-crossing zero-event-acceptance bug: `crossing_allowed_partner_set` (line ~3201 as of this writing -- line numbers will drift as this plan's own work proceeds, always re-grep rather than trust a cited number), `lidar_pure_owner_lookup_partner_set` (~3220), `lidar_route_window_partner_lookup_set` (~3234), `lidar_probe_partner_lookup_set` (~3264), `lidar_route_result_partner_lookup_set` (~3277), `crossing_partner_lookup_set_for_result` (~3334), `crossing_partner_lookup_set_for_route` (~3355). At least two of these are genuinely, defensibly different (`lidar_route_window_partner_lookup_set` computes a bounding box from a net's *source/target state* before a route exists, to scope a pre-search attempt; `lidar_route_result_partner_lookup_set` computes a bounding box from an *actual route's cells*, after a route exists, for post-search validation) -- but several others look like they could collapse into one parameterized helper (a single "partner set within a bounding box, computed from either two states or a route's cells" function) rather than five-plus near-copies. This has *not* been confirmed as safe to do yet -- it is a hypothesis from reading, not from a full call-graph trace.
- Observation: `crossing_allowed_partner_set` (~3201) itself internally branches on `allow_only_expected_pairs`: when true, it returns the topology-declared allowed-partner set (the real "expected pairs" mode); when false (i.e., in `lidar-pure` mode), it returns *every currently-committed net in the entire obstacle map*, unfiltered by any spatial window at all -- a single function serving two conceptually unrelated callers with two different meanings of "allowed partner," selected by a mode flag buried inside the function body rather than being two separate, clearly-named functions.
- Observation: `lidar_pure_owner_lookup_partner_set` (~3220) has a doc comment that states the repository owner's own mental model explicitly and is worth quoting in full, since it is the clearest evidence of what the *intended* design already is for at least this one function: "In LiDAR-pure this is not a whitelist of nets the route is allowed to cross. It is only the centerline lookup database for owners that A* discovers from actual dynamic obstacle cells while expanding moves." This confirms the reactive, collision-driven design is the documented intent, at least here -- the open question this plan exists to answer is whether every other partner-lookup function and call site is actually honest to that same intent, or whether some of them (particularly the *windowed*, pre-search ones like `lidar_route_window_partner_lookup_set`) are a different, more restrictive mechanism that predates or was bolted on alongside the reactive one, rather than being part of the same coherent design.
- Observation: at least three independent, hand-written blocks decide "what partner set should this net's collision-crossing attempt use" (all found via `grep -n "let collision_partner_ids"`), and they do not all agree:

- Observation (2026-08-19, Milestone 0, confirmed by reading all seven functions in full plus an exhaustive `grep` of every call site): the seven functions' real shape and call graph. **`crossing_allowed_partner_set(net_id)`** (line 3201) is the true base case: if crossing is disabled, empty set; if `allow_only_expected_pairs=true`, the topology-declared allowed partners (filtered to ones with committed cells); if `false` (i.e. lidar-pure, or collision-crossing-with-expected-pairs -- see the next observation), *every currently-committed net in the entire obstacle map*, completely unwindowed. **`lidar_pure_owner_lookup_partner_set(net_id)`** (3220) is a pure one-line passthrough to `crossing_allowed_partner_set` with an explanatory doc comment; it adds zero behavior of its own -- genuinely redundant as an *implementation*, but arguably not as a *name*, since it gives lidar-pure callers a semantically honest label ("owner lookup database", not "allowed partners") for what is, underneath, the same full-map call. **`lidar_route_window_partner_lookup_set`** (3234) and **`lidar_route_result_partner_lookup_set`** (3277) are a genuine, defensible pre-/post-search pair -- both compute a bounding box (with a caller-supplied margin) and filter `obstacle_map.net_route_entries()` to nets with any cell inside it, but one derives the box from a *source/target state pair* (before a route exists) and the other from an *actual route's cells or compressed waypoints* (after one exists); their bbox-and-filter bodies are near-identical, unshared code, a real, low-risk candidate for a shared "cells within bbox" helper. Both have exactly one call site each, both purely internal to their respective wrappers. **`crossing_partner_lookup_set_for_route`** (3355) and **`crossing_partner_lookup_set_for_result`** (3334) are the actual public-facing pair every real caller uses: each computes the same crossing-margin formula from `CrossingConfig`, then delegates to the matching windowed function above (in lidar-pure mode) or straight to `crossing_allowed_partner_set` (otherwise) -- itself a second, legitimate pre-/post-search pair mirroring the layer beneath it. **`lidar_probe_partner_lookup_set`** (3264) stands apart from all six others: it does not compute a bounding box against `net_route_entries()` at all, but instead queries the obstacle map's actual dynamic cell ownership near a *probe route* (`dynamic_owners_for_native_route`) and filters to owners already present in a caller-supplied `final_routes` map -- a fundamentally different mechanism (real cell-level ownership, not a coordinate-bbox test), and it has exactly one call site, inside `route_many_with_repair_and_commit`'s victim-selection logic (see below), where it is used to decide whether a collision found by a probe route is a legal crossing partner (not a rip-up victim) rather than to seed a search attempt. Conclusion for Milestone 1: the seven functions are not seven independent near-duplicates needing a single merge -- they are two real pre-/post-search pairs (states-vs-route-cells) sharing unshared bbox-filter code worth extracting, one pure-naming passthrough, one true base case, and one structurally distinct probe/ownership mechanism that should stay separate.

- Observation (2026-08-19, Milestone 0, divergence audit, `route_single_net_and_commit_native` read in full lines 5386-5650ish): the "two-stage vs. single-stage" divergence the plan's Surprises & Discoveries already flagged is real, and reading the full function body explains its *shape*, though not yet its full *rationale*. `route_single_net_and_commit_native`'s actual flow in lidar-pure mode is: (1) the first `collision_partner_ids` computation (line 5466) is *always empty* in lidar-pure mode (guarded by `!lidar_pure_crossing`), so the first `crossing_attempt` block never fires a collision-crossing search for lidar-pure nets at all; (2) it then unconditionally tries a *plain, non-crossing* A* search first (lines 5510-5616) and returns immediately if that commits successfully; (3) only if the plain search fails or fails to commit does it fall through to a *second*, separate collision-crossing attempt (line 5617-5634) using `lidar_pure_owner_lookup_partner_set` (the full, unwindowed set). ## Context and Orientation

This section assumes no knowledge of any prior conversation or prior ExecPlan. Every fact needed to understand and execute this plan is repeated here.

### The two crossing modes

This repository's router can require or discover "crossings" -- points where two nets' waveguides physically cross, which is legal only under specific geometric conditions (perpendicular enough, enough straight run on both sides, etc., configured via `CrossingConfig` in `src/py_router.rs`). Two modes exist, controlled by `crossing_context.config().allow_only_expected_pairs`:

- **`allow_only_expected_pairs = true`** ("expected pairs" mode): before routing, some upstream process (topology analysis) decides which specific pairs of nets are *allowed* to cross, and routing must either achieve exactly those crossings or fail. `crossing_allowed_partner_set` returns this pre-decided set in this mode, and `try_route_through_expected_crossing_partner` (`src/py_router.rs`, ~line 5211) is the search entry point built around it.
- **`allow_only_expected_pairs = false`**, combined with `use_collision_crossing_routing = true` ("lidar-pure" mode, gated by the helper `lidar_pure_crossing_enabled()` at ~line 3228): crossings are *discovered*, not pre-decided -- a net's route is allowed to cross whichever other already-committed nets it happens to run into, subject to the same legality checks. This is the mode this repository's actively-tracked benchmarks (`benes_4x4`, `multiportmmi_8x8`, `multiportmmi_16x16`) use via `--crossing-mode lidar-pure`. `try_route_with_collision_crossings` (and its wrappers, `..._with_loss` and `..._using_primitives`) is the search entry point for this mode -- see `.agent/execplans/2026-08-19-fix-collision-crossing-zero-event-acceptance.md` for the bug this session already fixed inside it.

### Why "partner set" functions exist at all

A* cannot discover "which other nets exist nearby" purely from a cell coordinate during search -- to validate whether a specific physical crossing is *legal*, the search needs the specific candidate partner net's own committed waypoints (to check angle and margin against). So before or during a search attempt, something has to answer "which other nets' waypoints should I even have on hand to check against." That answer-computing step is what all of the partner-lookup functions listed in Surprises & Discoveries are for. The repository owner's own simpler mental model -- "A* just routes, and when it collides it asks which net is it" -- is *architecturally close* to at least one of these functions' documented intent (`lidar_pure_owner_lookup_partner_set`'s own comment), but this plan's job is to confirm (or fix) whether the rest of the code actually behaves that simply, given the divergences already found.

### Relevant files

Everything in scope is in `src/py_router.rs` (a single, very large file -- 17,000+ lines as of this session). No Python-side files are expected to need changes for this plan's subject matter, though Milestone 0's call-graph trace should confirm nothing in `translation/route_rust*.py` depends on Rust-side function names or signatures this plan might change (the PyO3 boundary is the `#[pymethods]`-annotated public surface; purely-internal Rust helper functions like the ones this plan concerns are not part of that boundary and are safe to rename/consolidate without any Python-side change, but this should be confirmed, not assumed).
