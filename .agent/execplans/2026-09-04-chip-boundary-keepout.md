# Chip-boundary keepout: no routing outside the die

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. This document must be maintained in accordance with `.agent/PLANS.md`.

## Purpose / Big Picture

Owner (2026-09-04, with a screenshot of multiportmmi_32x32): a route runs east of the output grating couplers -- beyond the chip boundary -- and comes back. Routing east of the outputs (outside the chip at all) must not be allowed.

Cause: `make_grid_spec` (`python/photonic_router/static_obstacle_builder.py`) builds the grid from `expand_bbox(benchmark.bbox, security_margin_um)` (20 um default) plus `chip_add_x_um`/`chip_add_y_um` (flow defaults 0 / 40 um). The 20 um padding was pure free space: nothing marked it static, so the search used it whenever a detour around the GC array was cheaper than a crossing. Evidence in `build/routed_multiportmmi_32x32_braid_full.gds`: component bbox right edge x = 11424.164 um (GC bodies 11397..11424.164), a top-level waveguide polygon (layer 1/0) with a vertical run at x = 11425.25 um centerline (edge 11425.75) between y = 3201 and 3357 um -- i.e. in grid column 5722 (cell 11424.5..11426.5), the first column east of the chip.

Rule adopted: the routable die is the component bbox (polygons + ports) plus the EXPLICIT `chip_add_*` margins; the `security_margin_um` padding is grid slack for clearances/stubs and never routing space. An explicit `--die-bbox` stays routable as a whole. Every grid cell outside the routable bbox becomes a static obstacle (four disjoint bands). The bbox bounds snap to cells like port coordinates (`floor_snap_to_grid`), so a port lying exactly on the component bbox keeps its cell.

## Outcomes & Retrospective

**Outcome (2026-09-04 13:10):** routes can no longer leave the chip. The routable die is the component bbox plus the explicit `chip_add_*` margins; the `security_margin_um` grid padding is static (four bands, bounds floor-snapped like ports). The final photonic gate additionally rejects any centerline outside that bbox (`route_outside_chip`). All seven benchmarks route verification-clean with verdicts identical to the braid run, except multiportmmi_32x32 where the eastern detour became two legal crossings (119 -> 121). GDS: `build/routed_multiportmmi_32x32_chipboundary_full.gds`, `build/routed_benes_32x32_chipboundary_full.gds`.

**Retrospective:** the fix was a one-line cause (`make_grid_spec` expands the bbox, nobody marks the expansion static) found by reading the grid dimensions against the bbox (5732 cells = 11464 um vs 11424 um). Tests first paid off immediately: the "cell center outside" rule failed on a port lying exactly on the bbox, which is exactly the case that would have blocked a source port in a real benchmark. Two things worth keeping: every static rule now has a verifier twin (search-time keepout + final-gate check, the lesson of 2026-09-02/03 applied to geometry), and a klayout scan of the GDS against the component bbox is a 10-line oracle that does not depend on our own bookkeeping. Process slip: a `git stash` during a running guard ladder -- harness rule added.

**Open for the owner:** the flow default `chip_add_y_um = 40` keeps a 40 um routable margin above and below the chip (`routing_flow_config.py`); left/right is 0. If the chip is really only the component bbox in y too, that number becomes 0 -- not changed here.
