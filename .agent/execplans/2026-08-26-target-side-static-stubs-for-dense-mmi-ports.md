## Purpose / Big Picture

`multiportmmi_16x16` (`benchmarks/multiportmmi_16x16.py`) is one of this repository's fixed benchmark netlists used to exercise the photonic waveguide router end to end. Its documented "stable baseline" command currently fails partway through, at net `n_49` (`mmi0_ps_array_0_heater_2,o2 -> mmi0_multiport_0_0,o3`), with `RuntimeError: No route found for n_49 ... error=No repair route found`. This plan's job is to fix that failure -- not the separate, already-tracked, lower-priority "routing looks worse than it needs to" issue for other nets in this same benchmark (that work is parked in `.agent/execplans/2026-08-26-diagonal-crossing-conflict-adjacent-fanout-nets.md` and must not be conflated with this plan).

After this plan is implemented, someone will be able to run `multiportmmi_16x16`'s stable baseline (command in Concrete Steps) and see it complete successfully all the way through, including `n_49`, instead of crashing at net 50 of 223.

The repository owner's own diagnosis, confirmed by direct investigation this session, is that this benchmark used to have (or should have) a mechanism where the dense group of ports on `mmi0_multiport_0_0` (the large 16-input MMI combiner nets like `n_49` connect into) gets access reservations of *different* lengths per port -- middle ports reaching further out in the X direction than edge ports -- so that a "seamless connection" is possible into the dense port row without ports blocking each other. That staggering logic still exists in the code, and still computes different lengths per port exactly as expected, but a later step immediately flattens every port in the group back to the same, maximum length before the result is ever used -- silently erasing the intended effect. The fix direction agreed with the repository owner is not to restore the flattened staggering as-is, but to replace the whole reservation-based approach for these dense target ports with the same real, pre-committed stub-waveguide mechanism this router already uses for dense *source* ports (see Context and Orientation) -- because a real committed route does not have the self-blocking-gap problem that made the flattening necessary in the first place, so staggering can survive without reintroducing that bug.

## Surprises & Discoveries

- Observation: the staggering logic in `_dense_target_port_runway_lengths` is real, correct, and produces exactly the "middle ports reach further" property the repository owner remembered -- but it never survives to actually affect the router, because `_equalize_dense_runway_reach` unconditionally overwrites every port's length with the group maximum immediately afterward.
  Evidence (reproduction command in Concrete Steps, run with `PHOTONIC_ROUTER_TRACE_RUNWAY_INSTANCE=mmi0_multiport_0_0`):

      runway_trace target mmi0_multiport_0_0,o1  length=16
      runway_trace target mmi0_multiport_0_0,o2  length=16
      runway_trace target mmi0_multiport_0_0,o3  length=16   <- n_49's own target port
      ... (o4 through o10, all length=16) ...
      runway_trace source mmi0_multiport_0_0,o11 length=15
      ... (o12 through o20, all length=15) ...

  Every port in each group (10 target ports, 10 source ports on this same instance) ends up with one single, uniform length -- the group's own maximum -- rather than the staggered per-port lengths the earlier part of the same function computes.

- Observation: `_equalize_dense_runway_reach`'s own docstring (`translation/route_rust.py:2250`-`2268`) explains exactly why the flattening exists, and that reasoning is specific to the *abstract reservation* approach, not to staggering in general: a port's reservation is a wide box (`half_width_cells` cells on each side, not reduced by staggering -- only the forward length is staggered), and if neighboring ports in a dense group kept different lengths, the longer one's wide box can bleed sideways past where a shorter neighbor's own reservation stops, blocking that neighbor's lane in a gap where nothing physically exists. This is a real bug the equalization correctly prevents for the *reservation* mechanism -- but it does not apply to a real, physically-committed stub waveguide, which only occupies its own actual path (plus normal routing clearance), not an artificially wide box reserved the whole way regardless of what is really there. This is why "replace the reservation with real committed geometry" removes the need for equalization instead of requiring a smarter equalization.

- Observation: the dense-runway length, when present for a port, *overrides* that port's general footprint length (`translation/route_rust.py:6752`-`6759`, inside `route_nets_rust`'s setup): `custom_runway_length = dense_port_runway_length_by_spec.get(port_spec)`, and if it is not `None` and the port has no explicit custom access rule, `length_cells = max(1, int(custom_runway_length))` replaces whatever `_resolve_port_footprint_cells` returned. This matters for the planned follow-up step (zeroing the target-side runway knobs once target stubs exist): zeroing only the general per-port footprint length (the way source stubs were zeroed via `_is_dense_source_fanout_instance` scoping inside `_resolve_port_footprint_cells`, see `.agent/REPOSITORY_STATE.md` Resolved Findings entry 3) would NOT be enough for target ports, because `dense_port_runway_length_by_spec`'s override would still win. The dense-runway length itself (i.e. what `_dense_target_port_runway_lengths` returns for a now-stubbed port) must become 0, or that port must stop appearing in `dense_target_port_runway_length_by_spec` at all, for the general footprint zeroing to actually take effect.

- Observation (2026-08-26, implementation): the first stub-geometry design (reusing the source side's two-bend, laterally-offsetting `_two_bend_static_stub_centerline_um` for target ports) caused a REGRESSION on `multiportmmi_8x8` (`n_24` newly failed, only 31/111 routed): laterally offsetting adjacent target stubs onto different lanes produced near-duplicate diagonal candidate paths for adjacent nets, which then illegally collided (`realized_reasons=[(24, "not_perpendicular"), (24, "collinear_route_overlap"), ...]` in the `PHOTONIC_ROUTER_NATIVE_REPAIR_DIAG=1` trace) -- the exact same collision class documented in the diagonal-crossing plan. Target ports must NOT be laterally redistributed; they only need straight, length-staggered approaches.

- Observation (2026-08-26, implementation): a straight two-point stub whose far end is grid-snapped fails the router's strict terminal-tangent validation (`validate_target_tangent`, `src/geometry_realization.rs`; error "port endpoint correction would require an unsupported terminal stub") because a port's true physical position is generally NOT on a grid cell center -- the raw line has a sub-cell lateral kink. An intermediate fix (absorbing the kink with a small real-bend-radius curve via `_fanout_stub_centerline_um`) passed all verification but was REJECTED by the repository owner on visual GDS inspection: it renders as an ugly dogleg artifact in what should be a clean straight run ("this geometry is not correct... weird geometry which tried to make up for the y correction"). Passing verification is not the bar; the geometry must also look right.

- Observation (2026-08-26, implementation): the final design ("keep the port's exact Y along the whole stub; make the anchor's exact point the net's effective port; let ordinary endpoint correction close the grid-to-anchor gap") initially appeared not to work -- the corrected centerline's tail stayed at the raw grid endpoint -- and the cause was NOT in the correction machinery itself but in dispatch: `_apply_crossing_aware_endpoint_corrections_for_net_ids`'s outer loop skipped any net with zero realized crossing points (`if not crossing_points: continue`), and `n_23` (crossing-planned but zero realized crossings) fell through completely uncorrected -- a pre-existing latent gap, only exposed once target-anchored nets started depending on that pass. Two-line fix recorded in Progress. After the fix, `n_23`'s final segment is exactly straight into the true port: tail `(1249.5, 687.5) -> (1263.8, 687.5)` (constant Y).

- Observation (2026-08-26, n_123 investigation): direct trace of every target-stub build call confirms staggering is computed correctly and symmetrically for every group, e.g. `mmi0_multiport_2_0`'s 14 target ports get `forward_cells = 6,9,12,15,18,21,24 | 24,21,18,15,12,9,6`. The repository owner's observation that the failure-state GDS shows only the upper half staggered is therefore NOT a build-time bug; leading (unverified) explanation: stubs are only drawn as part of routed nets' centerlines, and the missing lower-half stubs belong to exactly the nets at/after the `n_123` failure that never routed.

## Context and Orientation

This repository implements a photonic waveguide router with a Python orchestration layer (`translation/route_rust.py` and sibling files) calling into a Rust routing core (`src/py_router.rs`, `src/astar.rs`) via PyO3 bindings.

`multiportmmi_16x16` is a fixed benchmark netlist (`benchmarks/multiportmmi_16x16.py`, placement data in `benchmarks/data/multiportmmi_16x16.yml`). Its documented "stable baseline" invocation is:

    PHOTONIC_ROUTER_LONG_STRAIGHT_CONGESTION_WEIGHT="0.05" PHOTONIC_ROUTER_FANOUT_STUB_BEND_DEGREES="90" PYTHONPATH=. .venv/bin/python routing_flow.py multiportmmi_16x16 --crossings true --crossing-mode lidar-pure --fanout-access-mode static-stubs --routing-window-scale 0.35 --foreign-port-keepout-cells 0

`--fanout-access-mode static-stubs` selects the router's "static stubs" behavior (`fanout_access_mode_normalized == "static-stubs"` throughout `translation/route_rust.py`): for certain dense groups of SOURCE ports on the same component instance, instead of just reserving empty grid cells as a keep-out zone in front of each port (an abstract "runway"), the router pre-plans and commits an actual, real, physical two-bend waveguide stub for each port before the main per-net routing begins, then routes each net from a "virtual anchor" at the far end of its own port's stub rather than from the port's own physical location. This is implemented in `_build_static_fanout_anchors` (`translation/route_rust.py:1964`), which builds one `_FanoutAnchor` per qualifying source port, and `_two_bend_static_stub_centerline_um` (nearby in the same file), which computes each stub's actual geometry. `_is_dense_source_fanout_instance`/`_is_dense_source_fanout_group` (elsewhere in the same file) decide which instances/port groups qualify.

Separately, and for BOTH source and target ports, `_dense_source_port_runway_lengths` (`translation/route_rust.py:2130`) and `_dense_target_port_runway_lengths` (`translation/route_rust.py:2278`) compute a per-port "runway length" -- how many grid cells forward from the port to reserve as a keep-out, abstractly, with no real geometry -- for ports that are part of a dense group (at least 3 source ports, or at least 4 target ports, sharing an instance and angle). Both functions intentionally stagger this length so that ports nearer the middle of the group get a longer reserved runway than ports at the edges (matching the repository owner's recollection: "the middle ones go out the furthest in x direction"). Immediately after computing the staggered lengths, both functions call `_equalize_dense_runway_reach` (`translation/route_rust.py:2245`), which overwrites every port in the group with the SAME length -- the group's own maximum -- to avoid a specific self-inflicted bug (a longer port's wide reservation box bleeding sideways into a shorter neighbor's lane; see that function's own docstring for the full explanation). The net effect, confirmed in this plan's Progress section, is that the staggering is computed but never actually takes effect: every port in a dense group ends up with the identical, maximum length.

For SOURCE ports on a `static-stubs`-eligible instance, this abstract runway-length mechanism still runs, but the final port footprint used by the router is overridden to be small/negligible once the port has a real committed stub anchor -- this was already found and fixed earlier this session (see `.agent/REPOSITORY_STATE.md` Resolved Findings entry 3): `_resolve_port_footprint_cells` (`translation/route_rust.py`, search for `stub_port_lane_length_cells`/`stub_port_lane_half_width_cells`) returns 0 for both length and half-width when `_is_dense_source_fanout_instance` is true for that port's instance, because the real committed stub waveguide already provides everything the abstract reservation used to provide, making the reservation redundant. Both knobs (`PHOTONIC_ROUTER_STUB_PORT_LANE_LENGTH_CELLS`, `PHOTONIC_ROUTER_STUB_PORT_LANE_HALF_WIDTH_CELLS`) remain present as real, overridable parameters defaulting to 0 -- they were not deleted, only re-defaulted. This plan's second not-yet-done Progress item is to do the equivalent thing for target ports, once target stubs exist.

For TARGET ports, no equivalent "real stub, therefore skip the abstract reservation" step exists at all yet, because no real target-side stub mechanism exists yet -- `_build_static_fanout_anchors` only ever considers `self.source_port_specs_by_instance`. This is the gap this plan closes.

`n_49` (`mmi0_ps_array_0_heater_2,o2 -> mmi0_multiport_0_0,o3`) targets `mmi0_multiport_0_0,o3`, one of 10 target ports on that instance sharing the same angle -- exactly the kind of dense target group `_dense_target_port_runway_lengths` was written for, and exactly the kind of port that would benefit from a real pre-committed stub instead of a flattened abstract reservation.

Key terms: "runway" (this codebase's name for a reserved-but-otherwise-empty grid-cell keep-out extending forward from a port, as opposed to a "stub," which is a real, physically-committed waveguide segment); "dense group" (a set of ports sharing a component instance and a compass angle, above a size threshold -- 3 for source runways, 4 for target runways, 3 for source static-stub eligibility per `_is_dense_source_fanout_group`); "anchor" (`_FanoutAnchor`, the record of where a real pre-committed stub ends and the main net search should actually begin/end); "equalize" (`_equalize_dense_runway_reach`, the function that currently flattens staggered lengths back to a single uniform value per group).
