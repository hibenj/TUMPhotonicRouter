## Purpose / Big Picture

This repository, TUMPhotonicRouter, is a mixed Python/Rust codebase (Python orchestration and benchmark/schematic handling in `translation/`, `routing_flow*.py`, `benchmarks/`; a compiled Rust extension in `src/`, built with `maturin` and called from Python via PyO3) with no automated code-quality tooling today: no linter, no formatter, no type checker, and no GitHub Actions CI at all (`.github/` does not exist in this repository as of this writing). Every check this repository currently relies on -- `cargo test --lib`, `pytest -q`, and the benchmark validation ladder -- is run manually, by a person or an agent, in a local terminal.

After this plan: running one command (`nox -s lint`, or the equivalent listed in Concrete Steps if `nox` is not adopted -- see Milestone 1's own decision) checks Python formatting (`ruff format --check`), Python lint rules (`ruff check`), Python static types (`mypy`), Rust formatting (`cargo fmt -- --check`), and Rust lint rules (`cargo clippy`), and reports a clear pass/fail for each. The same checks run automatically on every push and pull request via a GitHub Actions workflow, so a regression in code quality is visible without anyone remembering to run a linter locally. A short, project-specific coding-standards document (its exact location and name decided in Milestone 1, most likely `.agent/CODING_STANDARDS.md` to match this repository's existing `.agent/*.md` process-document convention) captures the small number of conventions a linter cannot check on its own -- primarily this repository's established comment philosophy ("a comment explains why, not what") and its preference for grouped configuration objects over long, flat keyword-argument lists -- rather than re-deriving all of PEP 8 or the Rust API Guidelines from scratch, since those are already well-written, freely available, and already what `ruff`/`clippy`/`rustfmt` enforce mechanically.

A person can see this working, once complete, by running the exact command from Concrete Steps in a clean checkout and observing a clean pass, and by pushing a branch with one deliberately introduced lint violation (for example, an unused import) and observing the GitHub Actions check fail on it.

  Evidence: `/home/benjamin/Documents/Repositories/working/fiction`. ## Context and Orientation

### Key terms, defined for a reader new to this repository or to Python/Rust tooling

"Linter": a tool that reads source code without running it and reports patterns that are likely bugs, likely to confuse a future reader, or simply inconsistent with the project's chosen style. "Formatter": a tool that rewrites source code's whitespace, line breaks, and similar cosmetic layout into one consistent style, without changing what the code does.

"`ruff`": the linter and formatter this plan uses for Python. It is a single, fast, Rust-implemented tool that replaces what used to require several separate Python tools (`flake8` for linting, `isort` for import ordering, `black` or similar for formatting, `pyupgrade` for modernizing old syntax) -- this repository does not have any of those older tools installed today, so `ruff` is being adopted as the first and only Python linter/formatter, not as a replacement for something already in use.

"`mypy`": a static type checker for Python -- it reads the type hints already present in this repository's function signatures (most functions already have them, per this session's own earlier reading of `routing_flow.py`) and reports where the code's actual behavior could violate them, without running the code.

"`cargo clippy`": the standard Rust linter, run via `cargo clippy` the same way `cargo test`/`cargo build` are already run in this repository. "`cargo fmt`": the standard Rust formatter, part of the same `cargo` toolchain already installed and used throughout this repository's existing validation ladder.

"`nox`" (a candidate, decided in Milestone 1, not assumed): a Python task runner that lets a single named command (for example `nox -s lint`) run a sequence of tool invocations in an isolated environment, so the exact same command works identically for a person running it locally and for CI running it in a GitHub Actions runner. `fiction` uses this; this repository could adopt it or use a plainer shell script -- Milestone 1 must decide and record which, since Concrete Steps in every later milestone depends on the answer.

"Auto-fixable": a lint finding the tool itself knows how to safely rewrite (for example, sorting imports alphabetically, or replacing `Optional[int]` with the newer `int | None` syntax this repository's own `requires-python = ">=3.10"` in `pyproject.toml` already permits). "Safe" auto-fixes are ones the tool's authors consider behavior-preserving by construction; "unsafe" auto-fixes (`ruff --unsafe-fixes`) are ones that usually preserve behavior but are not guaranteed to in every case, and this plan does not apply them without a human reviewing the diff first.
