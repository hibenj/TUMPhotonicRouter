## Purpose / Big Picture

This repository (`TUMPhotonicRouter`) routes optical waveguides between components on a photonic chip layout, converting a schematic (a description of which component ports must be connected) into physical waveguide geometry that avoids obstacles and, where two routed waveguides must cross, does so in a way that is physically and optically legal ("crossing verification"). The routing itself happens on a discretized grid: physical micrometer coordinates are rounded to integer grid cells, and a pathfinding search (A*, "A-star", a standard shortest-path search algorithm that explores promising directions first using a distance estimate) finds a sequence of grid cells connecting a source port to a target port while avoiding cells marked as blocked.

Earlier work on this branch (recorded in `.agent/execplans/2026-08-17-restructure-translation-route-rust.md` and `.agent/execplans/2026-08-18-restructure-route-nets-rust.md`) made the Python orchestration code that drives this search readable, without changing its behavior. A separate, ongoing effort (not itself an ExecPlan yet, tracked informally and summarized in `.agent/REPOSITORY_STATE.md` under "Current Snapshot") is now walking through that same pipeline stage by stage, comparing what each stage's code actually does against what it is supposed to do, and fixing real correctness bugs found along the way (not refactoring for its own sake). Two such bugs have already been found and fixed this way: a rotation/mirror ordering bug in `translation/layout_from_schematic.py` (commit `fae111d`) and a dropped obstacle-handle/cell-set bug in `python/photonic_router/static_obstacle_builder.py` (commit `75edf33`). That walkthrough covered, in order: benchmark loading, `layout_from_schematic`, static obstacle map building, and grid snapping / port-to-grid-state conversion (`port_to_grid_state`, `_snap_nearly_collinear_states`, `_snap_same_heading_minimum_bend_offset` in `translation/route_rust.py`), all with no further bugs found beyond one flagged-but-unconfirmed, currently-dormant oddity noted below in Surprises & Discoveries.

This ExecPlan is the next stage of that same walkthrough: the actual routing search (A*), and the "crossing verification" logic that decides whether one routed waveguide is allowed to physically cross another. This is the largest and most architecturally significant part of the codebase — it spans a Python orchestration layer (`translation/route_rust.py` and the `translation/route_rust_crossing_*.py` modules) and a Rust search-and-geometry engine (`src/py_router.rs`, `src/astar.rs`, `src/geometry_realization.rs`) called from Python through a compiled extension module, `photonic_router._rust` (built with `maturin`, a tool that compiles Rust code into a Python-importable native module; see `_load_rust_backend()` in `python/photonic_router/static_obstacle_builder.py` for how Python locates and loads it). Unlike the earlier stages, which were self-contained Python functions a reader could review start to finish in one sitting, this stage requires understanding a protocol that spans two languages, so this plan starts with an orientation milestone before any specific bug-hunting.

Someone picking this plan up after a break should be able to read this document alone (no other prior context) and know: what "crossing mode" means and why it matters, where in the code a routing attempt is rejected and why, how to reproduce a concrete known failure with full debug output, and what has already been ruled out versus what remains uncertain.

- Observation: `translation/route_rust.py`'s `_snap_same_heading_minimum_bend_offset` (around line 1081) special-cases ports that face the same cardinal direction and are exactly one grid cell short of the minimum perpendicular offset a pair of opposing 90-degree bends geometrically requires (`min_offset_cells = 2 * bend_radius_cells`, from its own docstring). ## Context and Orientation

Read this section fully before starting Milestone 0; it defines every term of art this plan uses and orients you to the relevant files.

The repository root is `/home/benjamin/Documents/Repositories/working/TUMPhotonicRouter` (referred to below by paths relative to that root). The active git branch is `crossings/verification-foundation`.

A "benchmark" in this repository is a small Python script under `benchmarks/` (for example `benchmarks/TOY.py`) that describes a toy or realistic photonic circuit: which components exist, where they are placed, and which of their ports must be connected by a routed waveguide (a "net"). `routing_flow.py` is the command-line entry point that loads a benchmark, converts it to a physical layout, and routes it; running `python routing_flow.py TOY` from the repository root (with the project's virtualenv active, i.e. using `.venv/bin/python`) routes the `TOY` benchmark, which is small (4 nets) and fast, making it a good default reproduction case.

The routing itself happens on a "grid": physical micrometer coordinates are divided into square cells of a fixed size (`grid_size_um`), and every position in the router's search is an integer `(x, y)` cell coordinate plus an "angle", one of 8 possible directions in 45-degree increments (0 = east, 2 = north, 4 = west, 6 = south, with 1/3/5/7 as the diagonals), matching the `_angle_to_step` function read during Stage 4 of the broader walkthrough (`translation/route_rust.py:913`). A "state" (the Rust type `PyState`, exposed to Python as `rust_backend.State(x, y, angle)`) is one such `(x, y, angle)` triple; A* searches over states, not just cells, because the router also needs to track which direction a route is currently heading (turns cost more than straight travel, and only certain turn shapes are physically realizable as waveguide bends).

"Obstacles" are cells the router must not route through: physical device geometry (walked and understood in the prior obstacle-map-building stage of this walkthrough, see `python/photonic_router/static_obstacle_builder.py`) plus, dynamically, cells already used by previously-routed nets in the same run (so two waveguides do not simply overlap on top of each other, except where a deliberate, legal "crossing" is allowed).

A "crossing" is the case where two different nets' routed waveguides physically cross paths at one point on the grid. This is sometimes allowed (two waveguides can cross at a shallow or perpendicular angle without significantly leaking optical signal into each other, which is why the code frequently refers to a physical realization of a crossing as a "crossing component" or "component" placed in the layout at that grid location) and sometimes not (a shallow, near-parallel crossing, or one that runs for too many consecutive cells, is not physically realizable or leaks too much signal). "Crossing verification" is the set of checks that decide whether a specific candidate crossing is legal.

The router has three crossing modes, controlled by the `crossing_mode` parameter (see `translation/route_rust.py:769` for where it is normalized and validated) and by the `--crossing-mode` command-line flag (defined in `routing_flow.py` around line 239, one of `window`, `collision`, or `lidar-pure`; passing `pure` or `lidar` as shorthand is also accepted and normalized to `lidar-pure`, per `translation/route_rust.py:770`). All three modes share one underlying Rust-side boolean, `use_collision_crossing_routing` (a field on the Rust router struct, declared at `src/py_router.rs:726`), which Python sets via `self.router.set_collision_crossing_routing(True)` for `crossing_mode in {"collision", "lidar-pure"}`, or `set_collision_crossing_routing(False)` for `"window"` (this call site is at `translation/route_rust.py:6292`-`6303`). So `"window"` mode never engages the collision/crossing-aware search machinery in Rust at all — it must have some separate, simpler crossing check (not yet read; out of scope for Milestone 1 below since the concrete failure being investigated uses `lidar-pure`, but worth reading before any future window-mode work). `"collision"` and `"lidar-pure"` both set that flag `True`; what actually distinguishes them is a second, independent setting, `allow_only_expected_pairs` (a field on the Rust `PyCrossingConfig` struct, `src/py_router.rs:303`, set from Python via `router.set_crossing_config(rust_backend.CrossingConfig(..., allow_only_expected_pairs=...))` in `translation/route_rust_crossing_plan.py:192`-`200`). The value passed is `self.effective_allow_only_expected_crossings`, computed at `translation/route_rust.py:776`-`778`: it equals the caller-supplied `allow_only_expected_crossings` argument (which defaults to restricting crossings) for `"collision"` mode, but is unconditionally forced to `False` for `"lidar-pure"` mode regardless of what the caller asked for. In other words: `"collision"` mode only permits a route to cross nets that were pre-computed as "expected" to cross based on the schematic's topology (a whitelist of crossing pairs, computed before any routing happens, by `_build_crossing_plan_info` in `translation/route_rust_crossing_plan.py:139`); `"lidar-pure"` mode has no such whitelist and instead evaluates the legality of any crossing it physically discovers while searching, purely from geometry (angle, straight-run length) rather than from an expected-topology list — this is almost certainly what "LiDAR" is standing in for in this project's naming (a sensor that reacts to whatever it physically detects, rather than consulting a predetermined map), though the exact etymology was not confirmed from any comment or documentation and should not be treated as more than an informed guess. The Rust function `lidar_pure_crossing_enabled(&self) -> bool` (`src/py_router.rs:3333`) makes this concrete: it returns `self.crossing_context.is_enabled() && self.use_collision_crossing_routing && !self.crossing_context.config().allow_only_expected_pairs` — true whenever crossings are enabled at all and `"lidar-pure"` mode's characteristic "no whitelist" setting is in effect.

The Python orchestration for a single net's routing attempt lives in `translation/route_rust.py`, inside the `_RouteNetsRustSession` class (the result of the Phase 2 restructuring recorded in `.agent/execplans/2026-08-18-restructure-route-nets-rust.md`; every routing concern that used to be a nested closure inside one giant function is now a named method on this class, with shared state as `self.attr`). The method `_dispatch_native_routing` (`translation/route_rust.py:3863`) is where a batch of nets' source and target states, plus the current set of "opened" cells (temporarily unblocked cells near a port, so the route can leave the port's own component without being blocked by its own clearance margin) and dynamic obstacles, get packed into one Python list and handed to the compiled Rust extension in a single call — either `self.router.route_many_with_repair_and_commit(...)` if rip-up-and-reroute repair is enabled (`self.repair_config.enabled`, controlled by the `--ripup-reroute` CLI flag), or `self.router.route_many_normal_and_commit(...)` otherwise. Both are PyO3-bound Rust methods (`route_many_normal_and_commit` at `src/py_router.rs:8572`, `route_many_with_repair_and_commit` at `src/py_router.rs:8692`); reading `route_many_normal_and_commit`'s body confirms it loops over the batch and, for each net, calls `self.route_single_net_and_commit_native(...)` (the call is at `src/py_router.rs:8626`), which is exactly the function already identified as the source of the `"No legal LiDAR crossing route found"` error. So the full call chain for a single net, in the non-repair case actually exercised by the TOY reproduction below, is: `translation/route_rust.py:3863` `_dispatch_native_routing` (Python) -> `src/py_router.rs:8572` `route_many_normal_and_commit` (Rust, PyO3-exposed) -> `src/py_router.rs:5476` `route_single_net_and_commit_native` (Rust, called once per net in a loop). The repair-enabled case (`route_many_with_repair_and_commit`) was not read in as much detail, but its signature and surrounding code make clear it wraps the same kind of per-net routing with additional rip-up/retry logic on top; confirming whether it also calls `route_single_net_and_commit_native` directly, or some other per-net entry point, is a remaining item for whoever next needs the repair-path call chain specifically (not needed for Milestone 1's TOY case study, which does not trigger repair for this particular net on the first attempt).

The Rust engine lives in `src/`. `src/astar.rs` (roughly 10,000 lines) implements the core pathfinding search; it has not yet been read in any detail as part of this walkthrough. `src/py_router.rs` (roughly 17,000 lines) implements the PyO3 bindings (PyO3 is the library used to expose Rust functions and types to Python) plus the higher-level per-net routing orchestration that decides when to retry, when a crossing is legal, and when to give up — this is where `route_single_net_and_commit_native` (starting at `src/py_router.rs:5476`, its full body spans to roughly line 5830) and the `"No legal LiDAR crossing route found"` error (`src/py_router.rs:5820`) live; the function's overall body has been read once and its crossing-mode branching understood at the level described above (which flag enables which mode), but the fine-grained step-by-step logic inside the `lidar_pure_crossing` branch (roughly lines 5555-5825, i.e. offsets 80-350 from the function start) has only been skimmed for control flow, not verified line by line — that finer reading is Milestone 1's job, applied specifically to the `gc1_to_mmi_in2` case. `src/geometry_realization.rs` (roughly 8,000 lines) turns an accepted route (a sequence of grid cells) into physical waveguide geometry (actual polygons with bends of the correct radius); it has not been read at all as part of this walkthrough, and is not expected to be relevant to Milestone 1 (geometry realization happens only after a route is accepted and committed, and the failure under investigation happens before that point).

"Committed" and "crossing event" (used throughout `src/py_router.rs`, for example `remember_committed_route_centerlines_with_ports`, `rollback_committed_route`, `add_crossing_events`, and `validate_committed_crossings_for_route_with_ports`, all visible in the `route_single_net_and_commit_native` body) refer to the bookkeeping the router does once a candidate route is accepted for a net: its cells and centerline get recorded into the shared obstacle map (so later nets in the same batch see them as dynamic obstacles, and so it becomes possible to answer "which already-routed net owns this cell"), and every point where the new route physically crosses an already-committed route becomes a "crossing event" (a record of which two nets cross, and where). "Rollback" (`rollback_committed_route`) undoes this bookkeeping if a route is provisionally committed, then found on a subsequent check to violate crossing legality. `route_single_net_and_commit_native`'s body contains this commit-validate-reject-rollback pattern twice, at `src/py_router.rs:5691`-`5698` (guarding the "simple route" fast path, `:5600`-`5706`) and again at `src/py_router.rs:5795`-`5803` (guarding the crossing-aware search path, `:5728`-`5817`) — both call `validate_committed_crossings_for_route_with_ports`, and on `Err(error)` call `self.rollback_committed_route(net_id)` plus `self.remove_crossing_events_for_net(net_id)`. **Neither of these two call sites is what actually causes `gc1_to_mmi_in2`'s failure** (this was the original, now-corrected hypothesis for this plan's Milestone 1) — both require a route to have already been found by the corresponding search strategy, and for this net, the crossing-aware search itself returns `None` (finds nothing at all, not something it then rejects), so its commit-validate block at `:5795`-`5803` is never entered; execution instead falls through to `if lidar_pure_crossing_attempted { return Err("No legal LiDAR crossing route found".to_string()); }` at `:5819`-`5821`. See Progress for the full, corrected trace and the further finding that even the plain A* fallback path (reached only when `lidar_pure_crossing_attempted` is `false`, e.g. in `window` mode) fails the same way, for a reason not yet identified (its own search statistics are discarded on failure before Python ever sees them — see Progress).

The `translation/route_rust_crossing_verification.py` (889 lines), `translation/route_rust_crossing_components.py` (472 lines), and `translation/route_rust_crossing_plan.py` (614 lines) modules are Python-side crossing logic — verifying realized (already-geometry-generated) routes for illegal intersections, choosing which physical crossing component to place, and building a "crossing plan" (a report of where crossings happen and why they were judged legal) respectively. Function names visible from a directory listing (not yet read in detail): `_verify_realized_route_intersections` and `_populate_realized_intersections_from_native_crossing_events` in `route_rust_crossing_verification.py`; `_build_crossing_plan_info`, `_write_crossing_debug_artifacts`, and others in `route_rust_crossing_plan.py`.

From the command line, pass `--debug-svgs` (with no value, or a route selector like `5` or `2,5-10`) to `routing_flow.py`; this makes `routing_flow_config.py:183` set `debug_dir = Path("build")`, so artifacts land under `build/routes/`.
