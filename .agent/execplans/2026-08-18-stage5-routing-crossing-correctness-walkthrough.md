## Purpose / Big Picture

This repository (`TUMPhotonicRouter`) routes optical waveguides between components on a photonic chip layout, converting a schematic (a description of which component ports must be connected) into physical waveguide geometry that avoids obstacles and, where two routed waveguides must cross, does so in a way that is physically and optically legal ("crossing verification"). The routing itself happens on a discretized grid: physical micrometer coordinates are rounded to integer grid cells, and a pathfinding search (A*, "A-star", a standard shortest-path search algorithm that explores promising directions first using a distance estimate) finds a sequence of grid cells connecting a source port to a target port while avoiding cells marked as blocked.

Earlier work on this branch (recorded in `.agent/execplans/2026-08-17-restructure-translation-route-rust.md` and `.agent/execplans/2026-08-18-restructure-route-nets-rust.md`) made the Python orchestration code that drives this search readable, without changing its behavior. A separate, ongoing effort (not itself an ExecPlan yet, tracked informally and summarized in `.agent/REPOSITORY_STATE.md` under "Current Snapshot") is now walking through that same pipeline stage by stage, comparing what each stage's code actually does against what it is supposed to do, and fixing real correctness bugs found along the way (not refactoring for its own sake). Two such bugs have already been found and fixed this way: a rotation/mirror ordering bug in `translation/layout_from_schematic.py` (commit `fae111d`) and a dropped obstacle-handle/cell-set bug in `python/photonic_router/static_obstacle_builder.py` (commit `75edf33`). That walkthrough covered, in order: benchmark loading, `layout_from_schematic`, static obstacle map building, and grid snapping / port-to-grid-state conversion (`port_to_grid_state`, `_snap_nearly_collinear_states`, `_snap_same_heading_minimum_bend_offset` in `translation/route_rust.py`), all with no further bugs found beyond one flagged-but-unconfirmed, currently-dormant oddity noted below in Surprises & Discoveries.

This ExecPlan is the next stage of that same walkthrough: the actual routing search (A*), and the "crossing verification" logic that decides whether one routed waveguide is allowed to physically cross another. This is the largest and most architecturally significant part of the codebase — it spans a Python orchestration layer (`translation/route_rust.py` and the `translation/route_rust_crossing_*.py` modules) and a Rust search-and-geometry engine (`src/py_router.rs`, `src/astar.rs`, `src/geometry_realization.rs`) called from Python through a compiled extension module, `photonic_router._rust` (built with `maturin`, a tool that compiles Rust code into a Python-importable native module; see `_load_rust_backend()` in `python/photonic_router/static_obstacle_builder.py` for how Python locates and loads it). Unlike the earlier stages, which were self-contained Python functions a reader could review start to finish in one sitting, this stage requires understanding a protocol that spans two languages, so this plan starts with an orientation milestone before any specific bug-hunting.

Someone picking this plan up after a break should be able to read this document alone (no other prior context) and know: what "crossing mode" means and why it matters, where in the code a routing attempt is rejected and why, how to reproduce a concrete known failure with full debug output, and what has already been ruled out versus what remains uncertain.

## Surprises & Discoveries

- Observation: the CLI script's default crossing mode (`SCRIPT_CROSSING_MODE` in `routing_flow_config.py:47`) is `"lidar-pure"`, but the underlying library function `route_match_and_realize` in `translation/route_rust.py:252` and `route_nets_rust` in `translation/route_rust.py:7048` both default their own `crossing_mode` parameter to `"window"` when called directly (i.e., not through the CLI). This means a human running `python routing_flow.py TOY` and a test or script that calls `route_match_and_realize(...)` directly without passing `crossing_mode` explicitly will silently exercise different code paths for the same benchmark. This is not yet confirmed to be a bug (it may be an intentional "safer library default, more thorough CLI default" choice), but it is a real trap for reproducing issues: always check which `crossing_mode` a given repro path actually used.
  Evidence: `grep -n "SCRIPT_CROSSING_MODE\s*=" routing_flow_config.py` -> `SCRIPT_CROSSING_MODE = "lidar-pure"`; `grep -n "crossing_mode: str = " translation/route_rust.py` -> two hits, both `"window"`.
- Observation: `translation/route_rust.py`'s `_snap_same_heading_minimum_bend_offset` (around line 1081) special-cases ports that face the same cardinal direction and are exactly one grid cell short of the minimum perpendicular offset a pair of opposing 90-degree bends geometrically requires (`min_offset_cells = 2 * bend_radius_cells`, from its own docstring). When that "missing == 1" condition is hit, the function snaps the target to `min_offset_cells + 1` cells of separation, not `min_offset_cells` (the value its own docstring claims is the true minimum). This reads as a plausible off-by-one (the natural fix for a "one cell short" deficit is to add exactly one cell, landing on `min_offset_cells`, not `min_offset_cells + 1`), but it could also be a deliberate one-cell safety margin. It was traced and found to never actually fire on the `heater_s_mod` benchmark (instrumented with a monkeypatch counting calls where the target changed: `{'total': 81, 'fired': 0}` across all 81 nets), so it is currently dormant and not the cause of any known test failure. Flagged here for awareness; not yet worth fixing blind without a live case to validate against, and out of scope for Milestone 0/1 below unless it turns out to be relevant.
  Evidence: manual trace of `translation/route_rust.py:1081-1149`; instrumented repro script (see the session transcript around 2026-08-18) confirming `fired: 0` out of 81 calls for `heater_s_mod`.
- Observation: the Rust function that ultimately raises `"No legal LiDAR crossing route found"` is `route_single_net_and_commit_native` in `src/py_router.rs` (function starts at line 5476; the specific `return Err(...)` is at line 5820). The Python side calls into the compiled extension from `_dispatch_native_routing` in `translation/route_rust.py` (the traceback below shows the call landing around `translation/route_rust.py:4093`), but the exact Python-to-Rust call site and argument marshalling has not yet been read in detail — that is Milestone 0's job.
  Evidence: reproduction traceback (see Concrete Steps) ending in `File "translation/route_rust.py", line 4093, in _dispatch_native_routing` and `RuntimeError: No route found for gc1_to_mmi_in2: ... error=No route found`; `grep -n "fn route_single_net_and_commit_native" src/py_router.rs` -> line 5476; `grep -n "No legal LiDAR crossing route found" src/py_router.rs` -> line 5820.

## Context and Orientation

Read this section fully before starting Milestone 0; it defines every term of art this plan uses and orients you to the relevant files.

The repository root is `/home/benjamin/Documents/Repositories/working/TUMPhotonicRouter` (referred to below by paths relative to that root). The active git branch is `crossings/verification-foundation`.

A "benchmark" in this repository is a small Python script under `benchmarks/` (for example `benchmarks/TOY.py`) that describes a toy or realistic photonic circuit: which components exist, where they are placed, and which of their ports must be connected by a routed waveguide (a "net"). `routing_flow.py` is the command-line entry point that loads a benchmark, converts it to a physical layout, and routes it; running `python routing_flow.py TOY` from the repository root (with the project's virtualenv active, i.e. using `.venv/bin/python`) routes the `TOY` benchmark, which is small (4 nets) and fast, making it a good default reproduction case.

The routing itself happens on a "grid": physical micrometer coordinates are divided into square cells of a fixed size (`grid_size_um`), and every position in the router's search is an integer `(x, y)` cell coordinate plus an "angle", one of 8 possible directions in 45-degree increments (0 = east, 2 = north, 4 = west, 6 = south, with 1/3/5/7 as the diagonals), matching the `_angle_to_step` function read during Stage 4 of the broader walkthrough (`translation/route_rust.py:913`). A "state" (the Rust type `PyState`, exposed to Python as `rust_backend.State(x, y, angle)`) is one such `(x, y, angle)` triple; A* searches over states, not just cells, because the router also needs to track which direction a route is currently heading (turns cost more than straight travel, and only certain turn shapes are physically realizable as waveguide bends).

"Obstacles" are cells the router must not route through: physical device geometry (walked and understood in the prior obstacle-map-building stage of this walkthrough, see `python/photonic_router/static_obstacle_builder.py`) plus, dynamically, cells already used by previously-routed nets in the same run (so two waveguides do not simply overlap on top of each other, except where a deliberate, legal "crossing" is allowed).

A "crossing" is the case where two different nets' routed waveguides physically cross paths at one point on the grid. This is sometimes allowed (two waveguides can cross at a shallow or perpendicular angle without significantly leaking optical signal into each other, which is why the code frequently refers to a physical realization of a crossing as a "crossing component" or "component" placed in the layout at that grid location) and sometimes not (a shallow, near-parallel crossing, or one that runs for too many consecutive cells, is not physically realizable or leaks too much signal). "Crossing verification" is the set of checks that decide whether a specific candidate crossing is legal.

The router has three crossing modes, controlled by the `crossing_mode` parameter (see `translation/route_rust.py:769` for where it is normalized and validated) and by the `--crossing-mode` command-line flag (defined in `routing_flow.py` around line 239, one of `window`, `collision`, or `lidar-pure`; passing `pure` or `lidar` as shorthand is also accepted and normalized to `lidar-pure`, per `translation/route_rust.py:770`):

- `"window"`: an older, simpler mode. (Full behavioral detail not yet read for this plan; Milestone 0 should read and document it before relying on this description further.)
- `"collision"`: a mode using a "collision" formulation of crossing legality — the code frequently refers to functions like `try_route_with_collision_crossings` (`src/py_router.rs:4132`).
- `"lidar-pure"`: the newest and, per `SCRIPT_CROSSING_MODE` in `routing_flow_config.py:47`, the default mode used by the command-line script (though, per Surprises & Discoveries above, not the default when calling the underlying library functions directly). "LiDAR" here is almost certainly this project's own name for a specific crossing-legality model (not the sensor technology); Milestone 0 must find and record its actual definition rather than guessing.

The Python orchestration for a single net's routing attempt lives in `translation/route_rust.py`, inside the `_RouteNetsRustSession` class (the result of the Phase 2 restructuring recorded in `.agent/execplans/2026-08-18-restructure-route-nets-rust.md`; every routing concern that used to be a nested closure inside one giant function is now a named method on this class, with shared state as `self.attr`). The method `_dispatch_native_routing` (confirmed present via the reproduction traceback below, exact current line not yet pinned down for this plan — Milestone 0 should record it) is where a single net's source and target states, plus the current set of "opened" cells (temporarily unblocked cells near a port, so the route can leave the port's own component without being blocked by its own clearance margin) and dynamic obstacles, get handed to the compiled Rust extension.

The Rust engine lives in `src/`. `src/astar.rs` (roughly 10,000 lines) implements the core pathfinding search. `src/py_router.rs` (roughly 17,000 lines) implements the PyO3 bindings (PyO3 is the library used to expose Rust functions and types to Python) plus the higher-level per-net routing orchestration that decides when to retry, when a crossing is legal, and when to give up — this is where `route_single_net_and_commit_native` (starting at `src/py_router.rs:5476`) and the `"No legal LiDAR crossing route found"` error (`src/py_router.rs:5820`) live. `src/geometry_realization.rs` (roughly 8,000 lines) turns an accepted route (a sequence of grid cells) into physical waveguide geometry (actual polygons with bends of the correct radius). None of these three Rust files have been read in detail yet as part of this correctness walkthrough; that is explicitly out of scope until Milestone 0 orients the reader enough to know where to look.

The `translation/route_rust_crossing_verification.py` (889 lines), `translation/route_rust_crossing_components.py` (472 lines), and `translation/route_rust_crossing_plan.py` (614 lines) modules are Python-side crossing logic — verifying realized (already-geometry-generated) routes for illegal intersections, choosing which physical crossing component to place, and building a "crossing plan" (a report of where crossings happen and why they were judged legal) respectively. Function names visible from a directory listing (not yet read in detail): `_verify_realized_route_intersections` and `_populate_realized_intersections_from_native_crossing_events` in `route_rust_crossing_verification.py`; `_build_crossing_plan_info`, `_write_crossing_debug_artifacts`, and others in `route_rust_crossing_plan.py`.

Debug artifacts (essential for this kind of investigation) are written when a `debug_dir` is provided. From the command line, pass `--debug-svgs` (with no value, or a route selector like `5` or `2,5-10`) to `routing_flow.py`; this makes `routing_flow_config.py:183` set `debug_dir = Path("build")`, so artifacts land under `build/routes/`. For a specific failed net named `<net_name>` in a benchmark whose debug-file prefix is `<prefix>` (matching the benchmark name, lowercased, e.g. `toy`), you get up to three files: `build/routes/<prefix>_<net_name>_FAILED.txt` (written only on final failure, by `_write_failed_log` in `translation/route_rust.py:3699`), `build/routes/<prefix>_<net_name>_diagnostics.txt` (written for both success and failure by the function containing the code around `translation/route_rust.py:3126` and `:3500`), and one or more `.svg` files visualizing the attempted route(s) against the obstacle grid.
