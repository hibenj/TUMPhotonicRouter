This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. This document must be maintained in accordance with `.agent/PLANS.md`, which is checked into this repository at that path and describes the required structure and editing discipline for ExecPlans in general.

## Purpose / Big Picture

`.agent/PROJECT_GOAL.md`'s "Future Architecture Initiative" section (added 2026-08-18) sets the next major direction for this repository, once the readability-restructuring and open-benchmark-finding work reached a natural stopping point (both happened 2026-08-19, see `.agent/REPOSITORY_STATE.md`): give the routing pipeline's stages -- obstacle map building, grid snapping, the A* search itself, geometry realization, and path-length matching -- real, explicit interfaces (`typing.Protocol`/`abc.ABC` in Python, `trait` in Rust), so each stage can be tested in isolation with a focused fixture instead of only through full end-to-end benchmark runs, and so a different implementation could later be substituted without touching the rest of the pipeline. The repository owner's own frame of reference (a C++ background where functionality lives behind a header-declared interface that both the implementation and its tests answer to) is the target shape.

This plan is deliberately scoped to characterization only: read the current state of all five candidate stages (across both `translation/*.py` and `src/*.rs`), determine how entangled each one currently is with orchestration state and with the other stages, note what test coverage already exists at what granularity, and produce a concrete, evidence-based recommendation for which stage to extract first and in what order to tackle the rest. Per `.agent/PLANS.md`'s guidance against over-specifying before source inspection justifies the design, this plan does not yet commit to an interface design, a stage order, or an implementation approach for any specific stage -- that is deliberately left for a follow-up plan (or this plan's own later milestones, added once Milestone 0's findings justify them) once the terrain is actually known.

This plan also follows the repository owner's standing direction (2026-08-19) to use the Claude+Codex flow (`.agent/CLAUDE_CODEX_FLOW.md`) for implementation slices once a fix or extraction is bounded and well-specified -- diagnosis and design stay with Claude. Given this plan is characterization-only, no implementation work is expected within it; that begins in whatever follow-up plan this one recommends.

This plan directly follows the repository owner's 2026-08-19 decision (see `.agent/execplans/2026-08-19-fix-open-repair-and-dense-port-findings.md`'s Decision Log and Outcomes & Retrospective) to stop chasing benchmark-specific routing fixes for now and prioritize restructuring instead: three real, root-caused, open findings (`multiportmmi_8x8`'s `n_67`/`n_70`/`n_71` cluster, `multiportmmi_16x16`'s `n_50`, and the dense-port lateral-width allocation) remain deliberately unfixed and parked in `.agent/REPOSITORY_STATE.md`, on the reasoning that the code they live in (particularly `route_many_with_repair_and_commit` in `src/py_router.rs`) is a direct target of this restructuring and fixing it now risks being rewritten shortly after landing.

## Surprises & Discoveries

- **Stage 1+2 (obstacle map building, grid snapping): already the closest thing in this repository to the target shape.** `python/photonic_router/static_obstacle_builder.py:101` (`build_static_obstacle_map(component, config) -> StaticObstacleMapData`) is a single, stable, already-swappable entry point: it dispatches to a Rust-accelerated implementation (`_build_static_obstacle_map_rust`, calling into `src/static_obstacle_builder.rs`'s `build_static_obstacle_map_from_geometry`) when the PyO3 extension is loadable, and falls back to a pure-Python implementation (`build_static_obstacle_map_python_from_extracted`) otherwise -- both paths return the same `StaticObstacleMapData` type. This is literally the "different implementation could be substituted without touching the rest of the pipeline" pattern `.agent/PROJECT_GOAL.md` asks for, just not yet formalized as a `Protocol`/`trait`. Dependency direction is clean and one-way: `translation/route_rust.py:223,488,6300` imports and calls `build_static_obstacle_map` with explicit arguments (`self.unrouted_layout`, `config=self.resolved_obstacle_config`); `python/photonic_router/static_obstacle_builder.py` has zero imports back from `translation/` (confirmed by grep). Grid snapping (stage 2) is not a separate module -- `physical_to_grid`/`grid_cell_center` live inside this same file (and its Rust mirror `src/static_obstacle_builder.rs:457,464`), with a single canonical definition each side (no duplication found across `src/*.rs` or `translation/*.py`/`python/photonic_router/*.py`). Test coverage is already substantial at exactly this granularity: `src/obstacle_map.rs` (20 `#[test]`s) and `src/static_obstacle_builder.rs` (20 `#[test]`s) each have their own `mod tests`, plus dedicated integration coverage in `tests/obstacle_map_tests.rs` (183 lines), `tests/test_static_obstacle_builder.py` (616 lines), and `tests/test_route_rust_obstacle_config.py` (97 lines). Entanglement assessment: **cleanly separable already** -- formalizing a `Protocol`/`trait` here would be codifying an existing contract, not inventing a new boundary.

- **Stage 3a, single-net A* search: also already clean and well-tested, but this is only half of "the A* search."** `src/astar.rs`'s entry points -- `route_single_net`, `route_single_net_with_config`, `route_single_net_with_crossing_config` (`src/astar.rs:1688,1859,2403`), and siblings -- take fully explicit arguments (`&ObstacleMap, &PrimitiveLibrary, State, State, Option<&FxHashSet<CellKey>>, &AStarConfig`, plus a `&CrossingSearchConfig` for the crossing-aware variant) and return `Option<RouteResult>`. Zero `self`/session coupling. `src/astar.rs` has 97 `#[test]`s in its own `mod tests` (`src/astar.rs:7010`) -- the deepest unit-test coverage of any stage examined. Entanglement assessment for *this half*: **cleanly separable already**, comparable to stage 1+2.

- **Stage 3b, ripup/repair orchestration: the least separable code in the entire pipeline, and the real reason "the A* search" (as `.agent/PROJECT_GOAL.md` scopes it, "including router-discovered crossing legality and ripup/repair") is not actually one coherent stage today.** `route_many_with_repair_and_commit` (`src/py_router.rs:8645`+, spanning several thousand lines) is a method on `PyPhotonicRouter`, the struct holding this repository's entire mutable session state as plain fields: `obstacle_map: ObstacleMap`, `committed_center_routes`, `committed_realized_center_routes`, `committed_opened_cell_keys`, `crossing_context: CrossingContext`, `crossing_events: Vec<CrossingEvent>`, `registered_plm: RefCell<RegisteredPlmContext>`, congestion-tracking fields, and more (`src/py_router.rs:716-736`). Repair strategies read and mutate this shared state directly throughout rather than taking clean inputs and returning a clean output; this session's own history (three real bugs found in or adjacent to this exact function this session alone: the zero-event-acceptance bug, the silent partial-restore data-loss bug it surfaced, and the just-closed `n_67`/`n_70`/`n_71` congestion finding, whose root cause is specifically that this function's victim-set expansion logic at `src/py_router.rs:10038-10074` has no mechanism to reason about a victim's own secondary blocker) is itself evidence of how failure-prone this code is. There is no dedicated `#[test]` coverage of repair-strategy behavior in isolation -- what exists is either single-net search tests (astar.rs, unaffected by repair) or full-benchmark integration evidence. Entanglement assessment: **deeply interleaved, not ready for interface extraction** -- this needs its own dedicated restructuring pass (breaking the god-object state apart, giving individual repair strategies names and explicit inputs/outputs) before a trait boundary is even well-posed. Extracting a clean `AStarSearch` trait for stage 3 without addressing this would only cover the easy half.

- **Stage 4 (geometry realization): same "already free functions, but a wide, shared file" shape as stage 3a, complicated by real coupling to stage 5.** `src/geometry_realization.rs` (8,272 lines, 70 `#[test]`s in `mod tests` at `src/geometry_realization.rs:5970`) exposes free functions with no `self` coupling (`route_to_port_corrected_centerline_with_options`, `realize_route_polygon_with_endpoint_correction`, etc., `src/geometry_realization.rs:1077-3528`), which is a good sign. But the same file also defines the meander-geometry primitives (`AutoMeanderConfig`, `AutoRouteAnalyticMeanderPlan`, `plan_auto_analytic_meander_for_centerline_depth_sweep_with_prefix`) that `src/plm.rs` (stage 5) directly imports and depends on (`src/plm.rs:6-10`) -- so stages 4 and 5 are coupled at the Rust type level today, not cleanly separated. On the Python side, `translation/route_rust_endpoint_correction.py` (1,626 lines) is already its own file for the endpoint-correction sub-piece of this stage (with dedicated `tests/test_route_rust_realization.py` and `tests/test_route_rust_geometry.py`), but `translation/route_rust_meanders.py` (3,139 lines, the largest single Python file in `translation/`) straddles geometry realization and path-length matching in the same way the Rust side does. Entanglement assessment: **separable with moderate refactoring** -- the free-function shape is already there, but the stage 4/5 boundary needs to be deliberately drawn (which primitives belong to "realize this route's geometry" versus "plan delay-matching meanders") before either can get a clean interface.

- **Stage 5 (path-length matching): sharply bifurcated between an already-excellent half and an entangled half.** The *graph-construction* half, `python/photonic_router/path_length_graph.py` (324 lines), is genuinely already at the target shape: it defines `SchematicLike(Protocol)` (`python/photonic_router/path_length_graph.py:10`) -- an actual, already-existing precedent for the exact `typing.Protocol` pattern `.agent/PROJECT_GOAL.md` asks for -- plus clean dataclasses (`PortRef`, `RoutedEdgeKey`, `GraphNode`, `GraphEdge`, `MissingLengthRequirement`, `DelayInsertionCandidate`) and free functions (`build_graph_from_schematic`, `annotate_edge_lengths`, `list_edges_requiring_meander`). The *candidate planning / meander insertion* half is not: `src/plm.rs`'s free functions (`plan_registered_geometry_requirement_candidates`, `plan_registered_geometry_request_sequence`, `plan_registered_geometry_split_request`, `plan_registered_geometry_final_requests`, `src/plm.rs:391-791`) have **zero** `#[test]`s of their own (`grep -c '#\[test\]' src/plm.rs` = 0, no `mod tests` block at all) -- their only exercise is production call sites in `src/py_router.rs:13215-13467`, which are real `impl PyPhotonicRouter` methods reading from `self.registered_plm.borrow()` (a `RefCell<RegisteredPlmContext>` field on the shared session struct, `src/py_router.rs:731`) and several other `self.*` fields (`self.grid`, `self.primitive_cfg`), not a test module -- so this half has *no* stage-granular test coverage at all, only the full-pipeline `tests/test_path_length_graph.py` (2,983 lines, the largest Python test file in the repository) and `translation/route_rust_meanders.py` (3,139 lines) on the Python orchestration side. Entanglement assessment: **the graph-construction half is cleanly separable already; the candidate-planning half is separable with moderate-to-significant refactoring**, and depends on stage 4's boundary being settled first (see above).

- **Recommended extraction order, grounded in the above**: (1) **obstacle map building + grid snapping** first -- it is already fully at the target shape on both sides of the language boundary, with the deepest existing test coverage of any stage, so formalizing a `Protocol`/`trait` here is close to a documentation exercise and gives a low-risk reference pattern the later stages can be measured against; (2) **A* single-net search** (`src/astar.rs`'s entry points) next, for the same reason (already clean, already 97 tests) -- but explicitly extract only the single-net search, not "the A* search" as a whole, since ripup/repair is a separate problem; (3) **geometry realization**, once a deliberate line is drawn between it and path-length matching's shared meander primitives; (4) **path-length matching**, starting from the already-clean `path_length_graph.py` half and only then tackling `plm.rs`'s untested candidate-planning half, informed by whatever boundary decision stage 4's extraction settles on. **Ripup/repair orchestration (`route_many_with_repair_and_commit`) is deliberately not placed in this order** -- per the entanglement assessment above, it needs its own dedicated restructuring pass (untangling the shared `PyPhotonicRouter` state, naming individual repair strategies) before an interface extraction is even well-posed; attempting to fit it into a trait boundary alongside the already-clean single-net search would either force a leaky abstraction or block on solving the harder problem first. This also directly explains why this session's earlier attempt to fix the `n_67`/`n_70`/`n_71` finding inside this function was judged not worthwhile (see the closed `2026-08-19-fix-open-repair-and-dense-port-findings.md` plan) -- the function's entanglement is exactly what this restructuring initiative exists to fix.

## Outcomes & Retrospective

Milestone 0 delivered a concrete, evidence-backed extraction order (Surprises & Discoveries) and closes this plan. The headline finding: two of the five nominal stages -- obstacle map building/grid snapping, and single-net A* search -- are already at or near the target shape (stable signatures, no session coupling, deep existing test coverage), so the initiative's real work is not "extract five stages" but "extract three separable stages, then do a dedicated restructuring pass on ripup/repair orchestration before it is even extraction-ready, and settle the geometry-realization/path-length-matching boundary before extracting either." This reframes the initiative's own shape in a way `.agent/PROJECT_GOAL.md`'s original five-stage list did not anticipate, and directly validates this session's earlier decision (in the now-closed `2026-08-19-fix-open-repair-and-dense-port-findings.md` plan) not to patch `route_many_with_repair_and_commit` in its current form: independent evidence (three real bugs there this session, zero stage-granular tests, a god-object session struct) confirms that function specifically is the least-ready part of the whole pipeline for either a bug fix or an interface extraction.

This plan is now closed. The natural next ExecPlan is scoped extraction of stage 1+2 (obstacle map building + grid snapping) -- the lowest-risk, best-evidenced starting point per the recommended order above -- starting with formalizing the existing `build_static_obstacle_map` contract as an explicit `Protocol`/`trait` rather than inventing a new boundary.

## Context and Orientation

This section assumes no knowledge of any prior conversation or prior ExecPlan. Every fact needed to understand and execute this plan is repeated here.

### The five candidate stages, per `.agent/PROJECT_GOAL.md`

In roughly the order they occur in the routing pipeline:

1. **Obstacle map building**: turning a benchmark's placed layout (polygons, ports, layers) into the grid-based obstacle representation the router searches against.
2. **Grid snapping**: converting between physical (um) coordinates and the discrete routing grid.
3. **The A* search itself**: the core route-finding algorithm, including router-discovered crossing legality and ripup/repair.
4. **Geometry realization**: converting route records (grid-cell paths) into physical gdsfactory geometry, including PDK crossing components.
5. **Path-length matching**: adding delay structures for benchmarks that require matched path lengths (e.g. `heater_s_mod`).

### Known starting points (not yet verified to be complete or authoritative -- Milestone 0 must confirm)

A quick line-count and structure check (2026-08-19, at the start of this plan) found:

- `src/obstacle_map.rs` (1,452 lines) and `src/static_obstacle_builder.rs` (1,453 lines) already exist as dedicated Rust modules, with mostly free functions and structs (`build_static_obstacle_map_from_geometry`, `make_grid_spec`, `physical_to_grid`, `rasterize_polygon`, etc.) rather than being buried inside `src/py_router.rs`. This is a promising sign that obstacle-map-building and grid-snapping (stages 1-2) may already be closer to a clean extraction than the other three stages, but this needs confirmation: are these modules actually called through a narrow, stable entry point, or do callers reach into their internals from many places; is there already an implicit "contract" that just needs to be made explicit as a `trait`; how much of the *Python*-side orchestration for these same stages (in `translation/route_rust_obstacle_config.py` or similar) is entangled with other stages.
- `src/astar.rs` (10,608 lines) is presumably where stage 3 (A* search) lives, but this repository's own history (this session's Milestone 0/2 investigation into `route_many_with_repair_and_commit`, which lives in `src/py_router.rs`, not `src/astar.rs`) shows that ripup/repair -- arguably part of "the A* search" from a black-box perspective -- actually lives in `src/py_router.rs` (17,671 lines), the largest and most orchestration-heavy Rust file in the repository. This is a strong hint that stage 3's real boundary does not line up cleanly with any one file today, and this plan's Milestone 0 needs to establish where the real, defensible line is (if any) between "search" and "orchestration."
- `src/geometry_realization.rs` (8,272 lines) is presumably stage 4, and `src/plm.rs` (not yet sized/read this session) is presumably stage 5.
- On the Python side, `translation/route_rust.py` (7,451 lines, already the result of two prior restructuring phases -- see `.agent/execplans/2026-08-17-restructure-translation-route-rust.md` and `2026-08-18-restructure-route-nets-rust.md`) plus a dozen-plus sibling files (`route_rust_obstacle_config.py`, `route_rust_geometry.py`, `route_rust_meanders.py`, `route_rust_endpoint_correction.py`, `route_rust_realization.py`, `route_rust_records.py`, `route_rust_types.py`, `route_rust_crossing_*.py`, `route_rust_debug_artifacts.py`, `route_rust_analysis.py`) already exist as a result of that prior work. ## Plan of Work

### Milestone 0: characterize all five stages' current boundaries

For each of the five candidate stages, determine with direct source evidence (not inference from file names alone):

- Which Rust module(s) and Python file(s) currently implement it (confirming or correcting the hypotheses in Context and Orientation above).
- Its current entry point(s): is there already something close to a narrow, stable function signature that could become a trait/Protocol method, or is the stage's logic interleaved with orchestration/other stages throughout.
- What state it depends on beyond its own natural inputs (e.g. does it reach into a shared session object, mutate global obstacle-map state directly, or depend on results from a different stage mid-computation).
- What test coverage already exists at this granularity (a focused unit test exercising just this stage) versus only at full-benchmark granularity.
- A rough entanglement assessment: cleanly separable already / separable with moderate refactoring / deeply interleaved with other stages.

Record all five stages' findings in Surprises & Discoveries, then propose a concrete extraction order (which stage first, and why) as this milestone's conclusion -- informed by, not assumed from, the findings above. Do not begin designing a trait/Protocol for any stage yet; that is this plan's next milestone (added once Milestone 0 concludes, per `.agent/PLANS.md`'s guidance against over-specifying).
