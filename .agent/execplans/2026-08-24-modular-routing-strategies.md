# Modularize the routing pipeline: readable seams and swappable strategies

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. This document must be maintained in accordance with `.agent/PLANS.md`, which is checked into this repository at that path and describes the required structure and editing discipline for ExecPlans in general.

## Purpose / Big Picture

This repository, TUMPhotonicRouter, routes optical waveguides for photonic chips on a discrete grid. A "net" is one required connection between two component ports (for example, from a laser's output port to a modulator's input port); the router processes a chip's full list of nets one at a time, each as a graph search over a shared grid of cells, committing each net's chosen path as an obstacle for every net routed after it.

Today, three parts of this pipeline are readable only in isolation, not as a system a person can follow end to end:

1. The Python function that hands routing work to the Rust engine, `_RouteNetsRustSession.run()` in `translation/route_rust.py`, is about 1070 lines long with almost no internal method boundaries. It genuinely starts with one clean call, building the obstacle map, but everything after that (router configuration, route-job preparation, and finally dispatching to Rust) is inlined in one body.
2. The single-net path-search code in `src/astar.rs` already has four different variants (plain routing, a "dynamic expansion" variant used mid-repair, a collision-crossing-aware variant, and a fourth, `route_single_net_with_crossing_config`, confirmed during Milestone 2 to be a mathematically exact special case of the third with one parameter fixed to `None` -- see Decision Log), each of which separately re-implements the same "try a small search window, then expand it if the search fails" loop. A `SingleNetSearch` trait already exists (`src/astar.rs:1689`) that cleanly names these four variants as one interface, but nothing in production calls through it yet — only its own tests do.
3. The rip-up/repair logic that fixes a net when it collides with an already-routed net, `route_many_with_repair_and_commit` in `src/py_router.rs`, calls 18 separately named, historically-accumulated Rust methods in one fixed, hardcoded order. Each method exists because of a specific past bug or benchmark finding, not because of a general, reusable idea like "try net order A, then try net order B."

After this plan, a developer will be able to do three things they cannot do today: read `_RouteNetsRustSession.run()` top to bottom as a short list of named phases and understand the Python-to-Rust handoff without opening any other file; read `route_many_with_repair_and_commit` (already restructured once, see `.agent/execplans/2026-08-20-route-many-with-repair-restructuring.md`) and see its rip-up/repair strategies expressed as a small number of general, parameterized ideas rather than 18 bespoke methods, once a design for that generalization has been characterized and confirmed with the repository owner; and select which single-net search strategy runs, in which order, through one clean interface (the existing `SingleNetSearch` trait), instead of that logic being duplicated per route variant.

A person can see this working, at each phase, by reading the shortened function bodies directly and by running this repository's existing benchmark validation ladder (defined in Concrete Steps below) to confirm zero routing-behavior change after every refactor-only milestone, and — once Phase C's design is chosen and a second repair strategy is implemented — by running that second strategy against the same benchmark suite and comparing its routing outcomes (success/failure per net, warning counts, timing) against today's default strategy.

This plan also closes a documentation gap that a direct count exposed: `translation/route_rust.py` has 136 functions but only 24 docstrings (about 18%), and `_RouteNetsRustSession.run()` itself — the exact function Phase A decomposes — has none; `src/py_router.rs` has 294 functions but only 75 doc comments (about 25%), and `route_many_with_repair_and_commit` and every one of its 18 `try_*` repair methods has none. `routing_flow.py`, by contrast, already has a clear module-level docstring describing the pipeline as a numbered stage list and docstrings on 8 of its 9 functions, including a fully parameter-documented `run_routing_flow` — it needs no work from this plan. Rather than run a separate documentation pass (which would either document code about to be restructured, wasting the effort, or fall out of sync with it), this plan folds doc-writing into the milestones that already touch each piece of code: Milestone 1 gives each newly-named method a docstring as it is named; Milestone 4's characterization work doubles as the source material for a doc comment on each of the 18 `try_*` methods (and is applied directly to those methods once written, independent of whether Milestone 6 ultimately replaces them); Milestone 6 documents whatever new abstraction is built. See Decision Log for this choice and for one explicitly out-of-scope finding it surfaced (`run_routing_flow`'s parameter count).

## Surprises & Discoveries

- Observation: the initial framing of this plan (in conversation with the repository owner, before this document existed) assumed "JPS is duplicated across three call sites" in `src/astar.rs`. Direct reading shows this is only half true.
  Evidence: only one of the three single-net search variant functions, `route_single_net_with_config_reporting_stats` (`src/astar.rs:2036`), actually attempts JPS4 (Jump Point Search, a pathfinding optimization defined below) — it checks `config.enable_jps4 && jps4_eligibility.eligible` and calls `route_single_net_jps4` (`src/astar.rs:2079-2098`) before falling through to a simple-route attempt and then a windowed A* search. The other two variants (the dynamic-expansion variant, whose JPS-skip block is at `src/astar.rs:2278-2283`, and the collision-crossing variant, whose JPS-skip block is at `src/astar.rs:2458-2463`) never attempt JPS4 at all — they unconditionally set `stats.jps4_eligible = false` with a fixed explanatory string (`"dynamic expansion overlay uses dense A*"` / `"collision crossing search uses augmented A*"`) and go straight to their own search function. So there is no real JPS-specific logic to collapse.
  The real duplication is different and, on inspection, more clearly a shared shape than "duplicated JPS logic": all three variants separately re-implement the same "resolve anchor-open-cells from source/target/port_open_cells, then either search once (`!config.use_routing_window`) or loop over `compute_routing_bounds` with increasing `expansion_idx` up to `config.routing_window_max_expansions`" pattern, each calling a different underlying search function (`route_single_net_with_bounds`, `route_single_net_with_bounds_dynamic_expansion`, `route_single_net_with_bounds_crossing`). This is the actual unification target for Milestone 2, not JPS specifically.
- Observation: the `SingleNetSearch` trait (`src/astar.rs:1689`) already has four methods — `search`, `search_with_dynamic_expansion`, `search_with_collision_crossing`, `search_with_crossing_config` — that map one-to-one onto the plain / dynamic-expansion / collision-crossing / crossing-config variants just described. The trait boundary was already drawn correctly by the earlier Future Architecture Initiative work; it is simply unused. `AStarSingleNetSearch` (`src/astar.rs:1742`) is the sole implementation, and it is only exercised by its own tests (`src/astar.rs:7317`, `7356`, `7390`, `7407`) — zero non-test call sites exist as of this writing (confirmed via `grep -n "AStarSingleNetSearch" src/astar.rs`, which returns only the definition and the four test lines).

## Decision Log

- Decision: sequence this plan as Phase A (Python seam decomposition), then Phase B (single-net search strategy pluggability), then Phase C (repair-strategy characterization, owner decision, then implementation), in that order.
  Rationale: lowest-behavior-risk work first. Phase A is a pure Python refactor with no Rust rebuild required. Phase B finishes already-started, already-validated-safe scaffolding (the unused `SingleNetSearch` trait) rather than inventing a new abstraction. Phase C is the only phase that touches correctness-critical code with a real history of subtle bugs (the zero-event-acceptance bug, the partial-restore data-loss bug it surfaced, and the still-open n_67/70/71 and n_50 congestion findings all live in or near this code) and is therefore ordered last, after the "generalize behind an interface, validate byte-identical, then add a real alternative" discipline has been exercised twice on lower-stakes code.

## Context and Orientation

### Terms used in this plan

An **A\* search** (pronounced "A star") is a graph pathfinding algorithm: it explores candidate paths ordered by the sum of the cost already spent and an estimate of the remaining cost to the target, which lets it find a shortest (or lowest-cost) path without exploring the whole grid. This repository's A* implementation lives in `src/astar.rs`.

**JPS4** (Jump Point Search, 4-directional) is an optimization on top of A* search: instead of expanding every single grid cell along a straight run of open space, it "jumps" directly to the next cell where a real decision (a turn, an obstacle, the target) becomes possible. It is implemented in `src/astar.rs` (the primitive library it needs is built by `create_jps4_unit_grid_primitive_library`, `src/primitives.rs:184`) and is only attempted for the plain routing variant, gated by the `enable_jps4` boolean on `AStarConfig` (`src/astar.rs:76`).

An **obstacle map** is a grid data structure recording which cells are physically blocked — by placed chip components, by clearance keepouts, or by other nets already routed — so that a net's search avoids illegal paths. It is built once per benchmark run by `build_static_obstacle_map` and then updated as each net commits its route.

**Ripup/repair** describes what happens when a net cannot find a legal route because an earlier-routed net is in the way: the router can "rip up" (temporarily un-commit) that earlier net, called a **victim**, reroute the blocked net, and then try to reroute the victim elsewhere. This is implemented in `route_many_with_repair_and_commit` in `src/py_router.rs`.

**PyO3** is the Rust library this repository uses to expose Rust functions and structs to Python. `PyPhotonicRouter`, defined in `src/py_router.rs`, is the main PyO3-exposed class; Python code calls its methods (for example `route_many_with_repair_and_commit`) through the compiled extension module `photonic_router._rust`, built by running `maturin develop --release`.

A Rust **trait** is an interface: a named set of method signatures that any number of concrete types can implement, analogous to a C++ abstract base class or a Python `Protocol`. `SingleNetSearch` (`src/astar.rs:1689`) is one such trait in this repository.
