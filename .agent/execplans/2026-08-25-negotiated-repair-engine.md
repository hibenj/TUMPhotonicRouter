# Replace the repair-dispatch chain with a general, negotiated-congestion repair engine

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. This document must be maintained in accordance with `.agent/PLANS.md`, which is checked into this repository at that path and describes the required structure and editing discipline for ExecPlans in general.

## Purpose / Big Picture

This repository, TUMPhotonicRouter, routes optical waveguides for photonic chips on a discrete grid. When a net's own search fails to find a route (because another, already-routed net is in the way), a repair process has to "negotiate": decide which net yields, clear space, and try again. Today that negotiation is implemented as `route_many_with_repair_and_commit` (`src/py_router.rs`, currently starting around line 11555), a per-net dispatch chain that tries up to 17 separately-named `try_*` methods in a fixed sequence, each hand-built to handle a specific situation somebody hit while debugging a specific benchmark (`benes_4x4`, `multiportmmi_8x8`, etc.). None of these 17 methods are dead code -- `.agent/execplans/2026-08-25-unify-astar-kernel-and-clean-repair-baseline.md`'s Milestone 5 already verified that precisely, by tracing every call site -- but "not dead" is not the same as "a coherent algorithm." The repository owner's own words, said directly in the conversation that produced this plan: *"just becaus[e] all these strategies are somewhat called doesnt mean the[y] are really necessary or that the behaviour is kinda 'wild'."* Several benchmark files (`benchmarks/multiportmmi_8x8.py`, `benchmarks/multiportmmi_16x16.py`, `benchmarks/benes_8x8.py`, `benchmarks/benes_16x16.py`) even hardcode their own `STABLE_ROUTING_ENV`/`STABLE_ROUTING_FLAGS` bundle of specific environment-variable values (for example `PHOTONIC_ROUTER_LONG_STRAIGHT_CONGESTION_WEIGHT=0.05`) empirically found to make that specific benchmark route cleanly -- a visible symptom of an algorithm that needs per-benchmark tuning rather than working generally.

This plan's purpose is to replace that 17-method dispatch chain with a small number of general, composable repair mechanisms built around a real, principled algorithm: negotiated-congestion rip-up/reroute, the same family of algorithm real router literature (and a sibling reference implementation this plan studies directly, see Context and Orientation) uses. After this plan: a net's repair path is a short, readable loop a person can describe in a few sentences (route nets in a principled order; when a net fails, mark every net it conflicted with as needing a retry; apply a real, accumulating cost penalty to cells that caused conflicts so the next attempt avoids them; iterate until every net routes or a round limit is hit), not a sequence of 17 named special cases. A person can see this working by reading `route_many_with_repair_and_commit` and finding that short loop instead of the current dispatch chain, and by running the benchmark ladder (exact commands in Concrete Steps) with each benchmark's own *plain* configuration and observing it route as cleanly as it does today with the hand-tuned `STABLE_ROUTING_ENV` bundle -- the concrete, falsifiable signal that the new algorithm is actually general rather than differently benchmark-specific.

## Surprises & Discoveries

### Milestone 1: the current repair dispatch chain's real structure

`route_many_with_repair_and_commit` (`src/py_router.rs`) dispatches, per net, in order: `try_plain_normal_route` -> (if lidar-pure crossing routing is enabled and a `pending_straight_victim_hint_for` hint exists) `try_source_layer_center_out_repair` then `try_pending_straight_victim_repair` -> `try_lidar_direct_crossing_subset` -> `probe_net_for_repair` (builds a trial route and a **hand-assigned integer priority score**: realized-violation partners get 0, dynamic blockers get 0, static-blocker-event partners get 1, expected-pairs uncrossed partners get 2) -> `try_localized_crossing_keepout_retry` -> `try_commit_clean_probe` -> a **round-based loop** that brute-force-enumerates 4 orderings (`victim_first` x `reverse_victim_order`) per victim set, restoring a full obstacle-map/committed-routes snapshot between attempts, advancing rounds by **cumulatively adding more victims to the same fixed priority list** (never re-scoring based on what happened last round) -> `try_final_repair_fallback`.

Of the (as of Milestone 5) 17 `try_*` methods, a call-graph investigation (this same session, `.agent/execplans/2026-08-25-unify-astar-kernel-and-clean-repair-baseline.md` Milestone 5's own Surprises & Discoveries) found that 4 are not repair-dispatch-scoped at all (they are called from `route_single_net_and_commit_native`, the core per-net routing primitive, and must not be touched by this plan either), and the remaining 13 cluster into 5 groups by actual mechanism, not by name: bulk column-wide reroute (2 methods), crossing-partner search primitives that all wrap the same underlying crossing search with different partner subsets (3 repair-scoped methods, after excluding the 4 core-routing ones), single-victim ripup/reroute (4 methods, of which one -- `try_ripup_single_victim_and_reroute` -- is the only real primitive; the other 3 are thin wrappers or ordering variants of it, and the ordering variation they encode is *also* separately brute-forced by the outer round loop), a localized keepout-window retry (1 method), and terminal bookkeeping (commit-clean-probe, plain-first, final-fallback -- not really "repair").

**Verdict, in the repository owner's own words, confirmed by direct evidence, not assumed**: this is priority-computed-once, then brute-force enumeration of orderings/reservations with full snapshot/restore as the undo mechanism -- not a negotiation loop. Evidence: `prepare_repair_attempt` (`src/py_router.rs`, computes `repair_victim_sets` once via `compute_repair_victim_sets`); the round loop's own `for victim_first in [false, true] { for reverse_victim_order in [false, true] { ... } }` structure; `enqueue_targeted_illegal_crossing_repair_set`, which reactively appends victim IDs parsed out of *error message strings* mid-loop -- a string-parsing-driven adaptive mechanism, not a cost signal.

### Milestone 1: a sibling reference implementation with a real, principled algorithm

`/home/benjamin/Documents/Repositories/working/LiDAR` is a local checkout of the official implementation of "LiDAR: Automated Curvy Waveguide Detailed Routing for Large-Scale Photonic Integrated Circuits" (ISPD 2025, Zhou/Zhu/Gu). This is very likely the direct research-paper ancestor of this repository's own "lidar-pure" crossing-mode terminology -- its own benchmark generator at `src/picroute/benchmarks/MMIports.py` literally produces netlists named `f"multiportmmi_{N}x{N}"`, matching this repository's own `multiportmmi_8x8`/`multiportmmi_16x16` benchmarks by name. Its repair engine (`src/picroute/routing/drgridroute.py`, function `runNRR`, "route with ripup and reroute") is a real, working example of the algorithm family this plan wants to adopt the principles of (not literally port -- LiDAR is Python-only with its own A* kernel and data model, this repository has a Rust kernel already validated and staying in place):

- **Net ordering is topological, computed once.** `process_net_order` (`drgridroute.py:74`) walks the schematic's topology levels (`self._cirdb.topology_orders`) and assigns each net a `comp_dist` (topology depth). `Nets.__lt__` (`database/schematic.py:267`) sorts by `comp_dist` first, then declaration order as a tiebreak -- so nets closer to the signal source route before nets further downstream. This repository already computes equivalent topology metadata (`node_depths`, used by `translation/route_rust_crossing_plan.py`'s topology analysis) but `route_many_with_repair_and_commit` routes nets in raw netlist declaration order, not topological order -- already flagged, unaddressed, earlier this session.
- **History cost is applied systematically, on every successful commit, not from 3 narrow call sites.** `registar_net` (`drgridroute.py:443`), called every time any net successfully routes, unconditionally calls `updateHistoryMap` (`drgridroute.py:703`), which increments a per-cell-per-orientation history cost (`historyMap[x][y][ori_index] += historyCost`) for every cell the just-committed route used. This repository's own `add_history_for_native_route`/`add_history_cells` mechanism (`src/py_router.rs`) does the identical *kind* of thing (confirmed: `history_weight` is threaded through nearly every A*-config builder in the file, and a nonzero value does discourage future searches from reusing penalized cells) but is only invoked from 3 specific call sites inside specific repair strategies, not systematically on every commit.
- **Failure handling is one global loop with real negotiation, not per-net special cases.** `mark_conflict_nets` (`drgridroute.py:690`) adds *both* the failing net and every net it conflicted with to a single `global_failedNet` set. At the end of every iteration, `ripupfailedNets` (`drgridroute.py:455`) clears every net in that set and requeues it for the next iteration's pass through the priority queue -- now discouraged from repeating the same conflict by the history cost the previous attempt already accumulated. `runNRR` (`drgridroute.py:117`) is the outer loop: for up to `maxIteration` rounds, drain the whole net priority queue (routing each net with strict design-rule checking first, falling back to relaxed checking), then rip up and requeue every net that ended up in the failed set, repeat.
- **A genuine escape hatch exists for non-convergence.** `ripupfailedNets` resets the *entire* history-cost map to zero (`clearHistoryMap`, `drgridroute.py:685`) after the 2nd global ripup round (`if self._ripup_times == 2`) -- an explicit, deliberate "give the search a clean slate" mechanism if accumulated history cost itself has become a local-optimum trap, not an accident.
- **Escalation is failure-count-driven, not net-ID-driven.** `Nets.clearNet` (`database/schematic.py:216`) increments `failed_count` on every clear; once `failed_count > 4`, `enable_45` (whether the net's search may use 45-degree diagonal primitives) turns off, widening the effective search space for a net that keeps failing -- a general relaxation rule, not a special case naming a specific net or benchmark.
- **Conflict resolution between two nets contesting the same crossing uses a real distance-based heuristic**, not a hardcoded rule: `routeSingleNet`'s `clear` condition (`drgridroute.py:279`) compares `cur_net.failed_count == 0` against whether the crossing partner has significantly more Euclidean slack (`net.distance["Euler"] > cur_net.distance["Euler"] + 1000`) to decide whether the *partner*, not the current net, should be the one ripped up and rerouted around.

**Comparison, stated plainly**: this repository's repair engine has none of these five properties as a general mechanism. It has narrow, hand-built approximations of some of them (the `history_weight` machinery is real but underused; `probe_net_for_repair`'s hand-assigned integer priorities are a crude, non-cost-based stand-in for a real priority signal), assembled ad hoc, one bug at a time, rather than designed as one coherent loop. This is the concrete, evidence-backed answer to why 17 special-cased methods exist: without a real negotiation loop underneath, every new failure pattern needed its own bespoke method instead of being handled by the general mechanism.

### Milestone 1: known counter-examples outside the repair dispatch chain

The repository owner asked directly, in the conversation that produced this plan, whether other parts of the codebase also follow benchmark-specific rules rather than general principles. Two concrete, already-identified instances exist outside `route_many_with_repair_and_commit` itself, both evidence of the same underlying pattern this plan's redesign targets (a knob or magic value substituting for a general mechanism), and both are folded into this plan's later milestones rather than left as loose ends:

- **`routing_flow_config.py`'s `SCRIPT_*` constants are not neutral defaults -- they are `benes_16x16`'s own tuned configuration, applied blanket to every benchmark that does not explicitly override it.** Evidence: `SCRIPT_BENCHMARK = "benes_16x16"` (`routing_flow_config.py:22`) is the literal first constant in the block, followed immediately by `SCRIPT_ALLOW_45_DEGREE_TURNS`, `SCRIPT_BEND_RADIUS_UM`, `SCRIPT_MIN_STRAIGHT_CELLS_PER_CROSSING`, `SCRIPT_FOREIGN_PORT_KEEPOUT_CELLS`, `SCRIPT_FANOUT_ACCESS_MODE`, `SCRIPT_ROUTING_WINDOW_SCALE`, and more (`routing_flow_config.py:22-41`) -- a config block named and shaped around one specific benchmark's needs, silently inherited by every other benchmark's CLI invocation unless that benchmark's own file documents an override (only `benes_8x8`, `benes_16x16`, `multiportmmi_8x8`, `multiportmmi_16x16` currently do, via their own `STABLE_ROUTING_ENV`/`STABLE_ROUTING_FLAGS`). Milestone 7 (below) already targets removing the need for per-benchmark tuning bundles; this finding means Milestone 7 must also check whether the `SCRIPT_*` defaults themselves stop needing to be one specific benchmark's tuned values once the general algorithm lands, not only whether the separate `STABLE_ROUTING_ENV` overrides become unnecessary.
- **`RipupRerouteConfig.enabled` (`translation/route_rust_types.py:295-300`) is a user-toggleable boolean (`enabled: bool = True`, alongside `max_rounds: int = 4`, `max_victims_per_failure: int = 8`, `history_weight: float = 2.0`, `history_increment: int = 1`) for whether repair may run at all.** This was already flagged, unaddressed, earlier this session: the router structurally needs repair whenever a plain search fails (confirmed: even `benes_4x4`/`benes_8x8` fail immediately without it), so "should repair be allowed to run" is not really a user choice, only "should repair be *isolated out* for testing/diagnostic purposes" is (the one legitimate use this repository already has for disabling it, e.g. `test_benchmarks_route_with_astar_only`). Once this plan's negotiated-congestion loop makes repair an integral part of routing rather than a fallback phase bolted on after a separate dispatch chain, this toggle stops making conceptual sense as a general-purpose config knob. Resolving it (either removing the toggle in favor of an explicit test-only bypass, or leaving it with a corrected doc comment explaining the one legitimate use) is folded into Milestone 6, where the old dispatch chain's config surface is being cleaned up anyway.
- **A third instance, found while grounding Milestone 2's design in the actual net-ordering code**: `translation/route_rust.py`'s `_dense_source_fanout_route_order` (line 2420) is literally where today's net routing order gets decided, and it is governed by `PHOTONIC_ROUTER_DENSE_FANOUT_ORDER`, an undocumented-in-any-benchmark-file env var whose recognized values (`target-ascending`, `target-descending`, `second-target-lane-first`, `inversion-aware-extremes` -- the unlabeled default reordering applied when the env var is set to anything else recognized) are hand-tuned *geometric* heuristics (sorting by target port lane position, picking whichever job is closest to the median lane) rather than anything topological. When the env var is unset or `"original"` (today's actual default), declaration order passes through untouched. This is the concrete, natural implementation site for Milestone 3's topological ordering -- and a fourth counter-example, found by looking for where to make the fix rather than being reported to look for more.

### Milestone 3: `self.node_depths` is not a usable ordering signal in general

The plan's own Interfaces and Dependencies section flagged this for re-verification rather than assuming it, and re-verification found the metadata is not usable as-is. `self.node_depths` (`translation/route_rust.py:812`) is the *raw* input parameter, unresolved: `benchmark_metadata.py:146`'s `getattr(benchmark_module, "NODE_DEPTHS", {})` defaults to `{}`, not `None`, for every benchmark that does not hardcode `NODE_DEPTHS` (as of this writing, only `benes_16x16`/`benes_32x32` do). `_build_crossing_plan_info` (`translation/route_rust_crossing_plan.py:222`) only derives real depths via `analyze_schematic_topology`'s `_derive_node_depths` fallback when its input is `None` -- but `{}` is not `None`, so an empty dict silently skips derivation. Separately, `_build_crossing_plan_info` returns early for `crossing_mode == "lidar-pure"` (`route_rust_crossing_plan.py:204-220`) before ever calling that analysis, by deliberate design (protecting the router-discovered crossing path from topology-precomputed hints, per `.agent/ORCHESTRATOR.md`'s standing rule) -- and `lidar-pure` is exactly the mode every `STABLE_ROUTING_FLAGS` bundle uses. So for the benchmarks this plan's own validation ladder exercises, `self.node_depths` would have been unusable either way.

**Resolution**: `_topological_net_route_order` computes depth directly from each batch's own `route_jobs` list (treating `job.inst1 -> job.inst2` as a graph edge, depth = longest path from a true source), independent of `self.node_depths`, `NODE_DEPTHS` benchmark metadata, and `crossing_mode`. This is unconditional and general -- exactly matching LiDAR's own `process_net_order`, which always walks the real circuit topology, never gated by a downstream crossing-legality mode.

### Milestone 3: reordering is unsafe when repair is disabled

Running the full `pytest -q` suite after the first version of this change (full-list topological reorder, unconditional) produced 11 failures, all in benchmarks routed via `test_benchmarks_route_with_astar_only` or benchmarks that share its plain-A*-no-repair code path (`TOY`, `heater_s`, `heater_s_compact`, `mmi_heater*`, plus geometry/stats tests that route through the same path). Root cause: with repair disabled, nothing can recover from a bad net order -- an earlier net's committed route can permanently block a later net's only remaining path, and the old declaration order happened to avoid this for these benchmarks while the new topological order did not. Verified via `git stash`/re-run that these exact 11 failures are **pre-existing on the unmodified branch and unrelated to this change** -- so this was never actually a pytest regression -- but the underlying hazard (reordering can strand an astar-only run that declaration order happened not to) is real and worth avoiding on its own merits, not just working around a coincidence. Fix: `_finalize_route_jobs_and_static_handoff` now only applies `_topological_net_route_order` when `(self.ripup_reroute_config or RipupRerouteConfig()).enabled` is true -- ordering only helps a negotiation loop that can recover from a bad order, so leave declaration order untouched when there is no negotiation loop to benefit from it.

### Milestone 5: implementation shape (what actually got built)

`route_many_with_negotiated_repair_and_commit` is a new, separate pyo3 entry point (not a modification of `route_many_with_repair_and_commit`, which is untouched). Per net, in the order given (already topological, per Milestone 3): try `try_plain_normal_route` (unchanged, existing); on failure, `probe_net_for_repair` (unchanged, existing, already crossing-legality-aware -- reused as-is rather than reimplemented, since it already correctly distinguishes a real collision from a legal crossing); on a clean probe, `try_commit_clean_probe` (unchanged, existing); on a real conflict (`probe.candidate_blockers` non-empty), a new `try_negotiated_displacement`: rip up every blocker, try to commit the current net, then try to reroute and recommit every displaced blocker in turn -- if every step succeeds the displacement is kept, otherwise every touched field (`obstacle_map`, `committed_center_routes`, `committed_realized_center_routes`, `committed_target_terminal_bump_guards`, `committed_opened_cell_keys`, `crossing_events`, `batch.final_routes`) is restored from a snapshot taken before the attempt, a pure no-op. Displacement is gated to a net's first failure only (`failed_count == 0`, mirroring LiDAR's `cur_net.failed_count == 0` half of its `clear` condition -- the other half, the Euclidean-slack comparison, is not yet implemented, see below), matching this milestone's staged scope: loop mechanics now, the full distance/cost-based heuristic at Milestone 6. Failed-but-not-displaced nets requeue for the next round; after 2 consecutive rounds with no net resolved, `obstacle_map.clear_history()` and every net's `failed_count` reset (LiDAR's own escape hatch, `ripup_times == 2` -- see Milestone 1's Surprises & Discoveries), giving stuck nets a fresh first-failure shot. The loop terminates when the queue is empty or `max_rounds` is exhausted; both entry points share a new `build_native_batch_result_dict` helper (existing ~90-line result-dict-construction logic, extracted verbatim from the end of `route_many_with_repair_and_commit`, not duplicated) so their Python-visible result shape is identical, which is what makes true A/B comparison possible. Deliberately not reimplemented in this milestone: the crossing-specific repair strategies (`try_lidar_direct_crossing_subset`, `try_localized_crossing_keepout_retry`, the source-layer-center-out strategies), the dense-source-fanout static-cleanup restoration (`restore_source_layer_static_cleanup`/`source_layer_indices_by_x`), and cascading (multi-level) displacement -- a blocker that itself needs to displace someone else to reroute simply fails its slot and the whole displacement rolls back. These are honest scope boundaries, not oversights; Milestone 6 (or later) revisits them if the benchmark ladder shows they are load-bearing.

### Milestone 5: converges correctly and faster on `benes_4x4`/`benes_8x8`, does not yet converge on `benes_16x16`

`benes_4x4` (plain defaults): routes correctly (`crossing_verification.json` `success=true`, 16/16), in 1.7s wall-clock versus the old chain's 8.9s for the identical benchmark -- a genuine, unprompted speed improvement, not a target of this milestone but worth recording. `benes_8x8` (stable baseline): routes correctly (48/48), 15.3s versus the old chain's 29.0s. `benes_16x16` (stable baseline, default `--ripup-max-rounds 4`): does **not** converge -- fails with `"Negotiated repair did not converge for net 105 within 4 rounds; 3 net(s) still unrouted"`. Raising the round budget to 12 (`--ripup-max-rounds 12`) did not converge either; the run was still going after 10 minutes (killed) versus the old chain's 6.6 minutes for the same benchmark at its own default settings -- not just slower to converge, but a genuine per-round cost blowup, not merely "needs a few more rounds."

**Root cause, reasoned from the design, not yet independently re-confirmed by a targeted profiling run**: `history_weight` is not yet threaded into these searches (see `try_negotiated_displacement`'s own doc comment and the Milestone 4 Decision Log) -- `route_single_net_and_commit_native` falls back to `self.astar_cfg`'s baseline (effectively unweighted) rather than the batch's configured `history_weight`. Milestone 4's systematic history-cost *accumulation* is real and working (confirmed by Milestone 4's own validation), but nothing in this milestone's search calls yet *reads* it back into search cost. Every round, a stuck net's plain-route and probe attempts re-run the exact same expensive full-grid A* search with no cost-based pressure to try a different corridor, which is consistent with cost scaling up with round count rather than down. This is precisely the gap Milestone 6 (distance/cost-based conflict resolution, explicitly scoped to "replace the remaining hand-tuned decision points") is positioned to close, and is now understood to be load-bearing for practical convergence speed, not just decision quality.

**Consequence for how this ships**: the new loop stays behind `PHOTONIC_ROUTER_NEGOTIATED_REPAIR=1`, opt-in only; `route_many_with_repair_and_commit` remains the default for every benchmark, unmodified. This is exactly the "keep the old dispatch chain compiled and reachable... so a direct A/B comparison stays possible" design the plan called for -- Milestone 5 producing a partially-validated result (real win on two benchmarks, a real known gap on a third) rather than a silent regression is the expected, designed-for outcome at this stage, not a surprise requiring rework before proceeding.

### Milestone 4: the 3 old call sites penalized losers, not winners -- a real semantic gap from LiDAR, not just a scattering problem

Milestone 2's design assumed the 3 old call sites "each individually decide whether to call `add_history_for_native_route`" on a successful commit. Direct re-read at Milestone 4 found this was imprecise: none of the 3 penalized a successful commit at all. `prepare_repair_attempt` (line ~8170 before this milestone) penalized the *failing probe route* (the current net's own doomed trial attempt) before any repair round even starts. `ripup_repair_set_victims` and `try_ripup_single_victim_and_reroute` both penalized a *victim's* route right before ripping it up -- i.e. the loser of a negotiation, not the winner. `try_ripup_single_victim_and_reroute`'s version was additionally confirmed 100% dead in production: its `add_history_for_victim` parameter has exactly one caller (`try_pending_straight_victim_repair`), which passes `false` (and `history_weight=0.0`, `history_increment=0`) -- the doc comment already said as much ("the deleted caller needed it `true` while the surviving one needs it `false`"), now confirmed by direct trace, not just the comment.

This is a real algorithmic difference from LiDAR, not merely "3 places instead of 1": LiDAR's `registar_net`/`updateHistoryMap` penalizes *every successful route's own cells*, discouraging *future* congestion on an already-popular corridor regardless of who uses it next -- the actual PathFinder-family negotiated-congestion signal. This codebase's existing mechanism instead penalized a *loser's* vacated cells, closer to a tabu-search "don't immediately retry the same failed move" heuristic than to negotiated congestion. Per the plan's own target (adopt LiDAR's principles), Milestone 4 implements LiDAR's actual mechanism -- penalize on commit, not on rip-up -- rather than just relocating the old loser-penalizing calls to one spot.

### Milestone 4: the real single chokepoint already existed, one level up from where Milestone 2 assumed

Milestone 2 identified `commit_native_route_with_clearance_allowing_core_overlap` as the intended chokepoint. ### Milestone 2: design, grounded in this codebase's actual Rust structures

**Where per-net negotiation state has to live.** `NativeRouteJob` (`src/py_router.rs:756-767`) has no field remotely like LiDAR's `failed_count`/`crossing_budget` -- it is a plain, immutable-in-practice snapshot of one net's routing inputs (net id, source/target states, opened cells, port positions), rebuilt from Python data at the start of a batch. `RepairBatchState` (`src/py_router.rs:985-995`) is the mutable state that *does* persist across a whole batch (`final_routes`, `attempts`, `repair_count`, and today's narrower `retried_source_layers`) -- confirmed by direct read, not assumed. Milestone 5's real implementation needs a new field here, `net_failed_counts: FxHashMap<u64, u32>` (or similar), not a change to `NativeRouteJob` -- the per-net failure/negotiation state belongs with the rest of the batch-lifetime state, matching where `retried_source_layers` (a similar per-net, batch-lifetime flag set) already lives.

**Where systematic history cost has to hook in.** Today's 3 narrow call sites (`prepare_repair_attempt`, the `try_reroute_current_net_*_victims` pair, `try_ripup_single_victim_and_reroute`'s `add_history_for_victim` parameter) each individually decide whether to call `add_history_for_native_route`. Milestone 4 needs to find the single chokepoint every successful commit already passes through (`commit_native_route_with_clearance_allowing_core_overlap`, referenced from every `try_*` method that commits a route, including the ones Milestone 6 will delete) and move the call there, unconditionally, deleting the narrower call sites once the chokepoint covers them -- not adding a 4th call site alongside the existing 3.

**The bounded prototype (`.agent/execplans/2026-08-25-negotiated-repair-engine-prototype.py`, committed, runnable with plain `python3`) found a real design bug on its first run, not just proved the happy path.** The scenario: 4 synthetic nets (`A`, `B`, `C`, `D`) with topology depths `0, 1, 2, 3` declared out of that order (`D, A, C, B`) specifically to prove ordering-by-depth matters; `A` and `B` both want to use a shared resource `r1`, but only `A` has no alternative (`B` has a costlier fallback `r1b`, standing in for "a longer detour exists"); `C`/`D` form a symmetric second conflict over `r2`/`r2b`/`r2c`, to exercise the ordinary case where either side could equally yield.

The first version of the loop directly translated LiDAR's `mark_conflict_nets` ("add both the failing net and everyone it conflicted with to one failed set") followed by "unroute everyone in that set." Running it produced a **non-terminating oscillation**: `A` and `B` alternated failing forever, `A`'s already-successful route got torn up every round merely because `B`'s *later* conflict-discovery pass re-added `A` (the already-routed owner) to the same failed set, even though `A` had done nothing wrong that round. Evidence (captured, first run): `converged=False rounds=8`, `A: routed=False ... failed_count=8`, `B: routed=False ... failed_count=8`, while the unrelated `C`/`D` pair converged correctly in the same run -- proving the bug was specific to the asymmetric-slack case, not the mechanism in general. Root cause, once traced: LiDAR's own `mark_conflict_nets` only ever *marks* nets for the *next* iteration's fresh routing attempt; it does not itself decide who keeps what mid-iteration the way the prototype's first version tried to. The fix was to resolve each conflict pairwise, immediately, using the same slack comparison LiDAR's `routeSingleNet` `clear` condition uses, and to have exactly one side of any single conflict yield, never both.

Fixing that surfaced a second, subtler gap: once the fix made `B` correctly yield to `A` without unrouting `A`, `B` kept retrying the *same* losing candidate (`r1`) forever, because the prototype's only mechanism for discouraging a repeated choice was the shared `history` cost map -- and history cost was only being bumped on the *winning* side's resources (to discourage others from contesting a stable winner later), never on the losing side's own repeated bad choice. The real insight this forced: **a committed route is a hard obstacle to a net that has already lost a negotiation over it, not merely an expensive one** -- exactly how the real A* kernel already treats another net's committed cells (blocked outright, unless a legal crossing hook applies), as opposed to `history_weight`'s soft, spread-things-out cost. The fix added a per-net `blocked_resources` set (cleared only on a full history reset, matching "a reset is a genuine restart, not just a cost decay") that makes a losing candidate infeasible for that specific net until something changes, forcing its next attempt to consider its fallback candidate the same way a real A* search would naturally route around an obstacle it cannot legally cross. After both fixes, the scenario converges in exactly 2 rounds: `A` keeps `r1` (correctly, it had no alternative), `B` and `D` both find their fallback candidates immediately once blocked from the contested resource, and `C` wins its own contest by virtue of routing earlier in topological order. The naive one-shot baseline the script also runs, for direct comparison, leaves `B` and `C` failed outright with no negotiation at all.

**Consequence for Milestone 5's real design**: the real implementation needs two distinct signals, not one -- (1) a genuine hard-obstacle check (does this candidate route collide with a *currently committed* competing net's cells at all -- this repository already has this, it is exactly what `probe_net_for_repair`/`invalid_crossing_intersections_for_route` already detect), and (2) `history_weight`'s existing soft cost, now applied systematically (Milestone 4) to discourage *repeated* contests over the same corridor even among candidates that are not outright blocked. Milestone 5 must not conflate these the way the prototype's first draft did.

## Context and Orientation

### Key terms, defined for a reader new to this repository

"Repair" / "rip-up-reroute": when a net's own search attempt fails because another, already-committed net is in the way, the process of removing ("ripping up") that other net's route, then re-routing both nets, possibly across several rounds, until an arrangement is found where both succeed (or a round limit is reached and the net is reported as failed).

"Negotiated congestion": a repair strategy where, instead of a fixed sequence of special-cased attempts, every routing decision consults a shared, accumulating cost signal (here: a per-cell "history cost" that goes up every time a cell is used by a committed route) so that repeated conflicts over the same physical space become progressively more expensive to keep repeating, naturally pushing the search toward alternatives -- this is the general shape of the well-known "PathFinder" family of algorithms from FPGA/PCB routing literature, and it is what this plan's sibling reference implementation (LiDAR, see below) actually does.

"Topological order" / "topology depth": in this repository's netlist model, nets connect instance ports that form a directed graph (signal flows from inputs toward outputs through a chain of components). "Topology depth" is how many hops a net's source is from the netlist's true inputs; routing nets in increasing depth order means routing signal-source-side nets before the nets that depend on them being placed, matching the netlist's own natural dependency order instead of an arbitrary declaration order.

"The 17 `try_*` methods": every method in `src/py_router.rs` whose name starts with `try_`, as of the end of `.agent/execplans/2026-08-25-unify-astar-kernel-and-clean-repair-baseline.md`'s Milestone 5 (`grep -n "    fn try_[a-z_]*(" src/py_router.rs`; re-run this before trusting the exact count, since it may have changed since this plan started). 4 of these (`try_route_with_collision_crossings` and its 2 default-argument-chain siblings, plus `try_route_through_expected_crossing_partner`) are load-bearing core per-net routing infrastructure, not repair-dispatch strategies, and are out of scope for removal in this plan -- confirmed by direct call-graph tracing in the sibling plan's Milestone 5, not assumed.
