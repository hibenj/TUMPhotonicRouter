# Waive the waveguide clearance in a run-in corridor at every port, so nets serving ports closer than the clearance can still reach them

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. This document must be maintained in accordance with `.agent/PLANS.md`.

## Purpose / Big Picture

A component's ports can sit closer together than the routing clearance the user asks for: a 2x2 MMI's two inputs are 1.25 um apart, while `heater_s_mod`'s stable 90-degree configuration asks for 3 um between waveguides. Today the first net committed to one of those ports reserves a clearance keepout that covers the sibling port and its entire approach, so the second net can never be routed -- not by search, not by repair, because the target cell itself is inside another net's reservation. The repository owner's direction (2026-08-28): by default, the clearance may be violated close to ports, because the component defines that pitch, not the router.

After this plan: every net's search and commit ignore *other nets' clearance halos* (never their cores) inside a run-in corridor behind each of its own two endpoints, sized from the existing port-lane length and the keepout radius. `heater_s_mod` with `--allow-45-degree-turns false --bend-radius-um 10 --waveguide-clearance-um 3.0` routes 81/81, `test_heater_s_mod_90_degree_plm_regression[3.0]` passes (the known-failing pytest set drops from 11 to 10), and every other benchmark baseline is unchanged or every difference is explained.

## Surprises & Discoveries

- Observation: the verifier (`verify_photonic_routing`, `translation/photonic_verification.py`) has no clearance check at all, only a physical overlap-area check (`min_route_overlap_area_um2=2.0`). Two 0.5 um guides 1.25 um apart do not overlap, so the plan's originally-proposed "teach the verifier the same waiver" milestone is a confirmation, not an implementation.
  Evidence: `grep -n -i clearance translation/photonic_verification.py` returns only the `min_route_overlap_area_um2` parameter.

(Found 2026-08-28 while implementing Milestone 1, in the order found:)

- Observation: a fixed-length corridor is the wrong rule. Net 1 (`gc_in_0_to_mmi_a_0_upper_in`, target row 449) turns onto its final row 20 cells before the port; the port lane is 12 (+2 radius). How long two sibling nets must run side by side is decided by whichever routes first, so the corridor follows the net's own opened approach cells instead (the router's own notion of the port's approach region; here x=85..104 on row 448).
  Evidence: `dynamic_clearance_exempt_cells_count` 18 -> 160 -> still `corridor_clearance_target_region_size=1`; `opened_dynamic_overlap_owners={1: (85..90, 448)}` outside the 14-cell corridor.
- Observation: "until the next static obstacle" does not work as a bound either -- the cells in front of a port are static for every other net (port-lane reservations, `opened_static_overlap_count=520`), and in free space the walk ran across the whole chip (15 200 cells, x 0..2961). Hence the opened-cell bound.
- Observation: the exemption was defeated one step *before* the search: `opened_cells_without_dynamic_overlap` strips every opened cell that any committed net touches, so row 448 (static underneath, opened for net 2 only) was re-blocked statically as soon as net 1's halo covered it. `corridor_clearance_last_connected_radius` went 0 -> 1 only after that filter learned about the exempt set.

## Decision Log

- Decision: implement option (a) from the finding -- a direction-aware corridor per endpoint, waiving only the clearance halo (existing "other core refs must be zero" rule kept) -- and not the pitch-scaled same-instance-sibling variant (b).

Length is bounded to the port lane so the waiver stays where the component's own pitch justifies it.

## Outcomes & Retrospective

Outcome against the purpose: the routing half is done and the owner's rule is the default. Two nets whose ports sit closer than the clearance now approach side by side at the component's pitch; `heater_s_mod` 90-degree / 3 um routes 81/81 with clean verification in both crossings-off (33 s) and lidar-pure (60 s) modes, where before it failed at net 2. The plan's literal acceptance test, `test_heater_s_mod_90_degree_plm_regression[3.0]`, still fails -- now in path-length matching, a distinct problem of the 3 um configuration that nobody could see while routing died at net 2. Scope decision left to the repository owner (see Decision Log).

What it took: the finding named one mechanism (`route_dynamic_clearance_exempt_cells`'s 3x3 box) and the fix touched four: the corridor shape, the opened-cell filter that silently undid the exemption before the search, lidar-pure's "no crossing found means repair" short-circuit, and a missing trace for a silent fall-through. Each was found by running the real benchmark after the previous step, not by reading ahead. The diagnostics that already existed (`corridor_clearance_*`, `opened_dynamic_overlap_owners`, `PHOTONIC_ROUTER_TRACE_CROSSING_NET`) carried most of the evidence; the one that was missing (per-stage outcome of the plain route) is now `PHOTONIC_ROUTER_TRACE_PLAIN_ROUTE_NET`.

Lessons: (1) a "bounded" corridor needs a bound the router already owns -- the opened cells -- not a constant and not the static map; both wrong guesses were cheap to disprove with the exempt-cell count in the diagnostics. (2) A waiver has to be honored by every stage that can block a cell, and the stages here were not where the design docs point (the opened-cell filter, the lidar-pure fallback order). (3) Halo-only conflicts are a class lidar-pure had no name for, because every stable crossing benchmark runs at clearance 0 where halo == core; the guard is a no-op there by construction, which is what made the ladder safe to trust. (4) The CLI's two clearance flags are one knob; an experiment built on the belief they were two wasted a run.

Not done / open: the PLM failure at 3 um; the 3 residual repairs in lidar-pure at 3 um (heater_s_mod's stable config runs crossings off, so not pursued); route-by-route byte comparison against a pre-change build was not done -- validation relied on clean verification, unchanged route/repair counts (`benes_8x8` 0 repairs, `benes_16x16` 0 repairs, `multiportmmi_8x8` 2 repairs as before), and the by-construction argument for clearance-0 configs.

## Context and Orientation

Routing runs on a cell grid (2 um cells in the stable configs). When a net is committed, `src/obstacle_map.rs` registers its centerline cells as *core* dynamic obstacles and, when a clearance is configured, also registers an inflated *keepout* around them (`dynamic_route_commit_keepout_radius_cells`, from `OpticalRouteClearancePolicy.from_dimensions` in `translation/route_rust_types.py`: `ceil((width/2 + clearance)/grid)`, 2 cells for width 1 um, clearance 3 um, grid 2 um). Later searches treat both as blocked, and additionally expand dynamic obstacles by `dynamic_obstacle_search_expansion_radius_cells` (`src/astar.rs`, the `blocked_cells` build around line 830).

Every net already carries a per-net set of *dynamic clearance exempt cells*: cells where another net's keepout is ignored by the search (`src/astar.rs:824-893`, only when the cell is not another net's core), by the commit check (`src/obstacle_map.rs:468-491`, `allowed_clearance_overlap = exempt && other_core_refs == 0`), and by the simple-route probe (`src/simple_routes.rs:225`). The sets are computed once per run by `PyPhotonicRouter::build_dynamic_clearance_exempt_cells_for_routes` (`src/py_router.rs`, ~line 11982) calling `route_dynamic_clearance_exempt_cells` (`src/py_router.rs:1273`), batched from `_RouteNetsRustSession` in `translation/route_rust.py` (~line 7554, into `self.batch_clearance_exempt_cells_by_id`). That helper currently returns a box of radius `commit_radius_cells.clamp(0, 1)` around the source and target cells and ignores the state angle -- 18 cells for the failing net, none of them on the 20-cell approach.

State angles are eighths of a turn (`route_angle_to_step`: 0 = +x, 2 = +y, 4 = -x, 6 = -y, odd = diagonals). A *source* state's angle is the heading the route leaves the port with; a *target* state's angle is the heading the route arrives with (`port_to_grid_state(..., as_target=True)` flips the port orientation). So the source run-in lies at `source + k*step`, the target run-in at `target - k*step`, for `k = 0..length`.

`port_lane_length_cells` (`translation/route_rust.py:6744`, `max(3, 2*bend_radius_cells + 2)`, 12 cells in the heater config) is the length the router already uses for the port lane reservation and is the natural corridor length. `route_collect_inflated_step_cells` (`src/py_router.rs:1193`) already walks `length` steps from a base cell along a step and inflates each by a half-width, clipped to the forward half-plane -- exactly the corridor shape needed.
