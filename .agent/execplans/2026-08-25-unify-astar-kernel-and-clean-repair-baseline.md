# Unify the two A* search kernels into one swappable kernel, and reduce the repair dispatch chain to a clean, standalone ripup/reroute module

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. This document must be maintained in accordance with `.agent/PLANS.md`, which is checked into this repository at that path and describes the required structure and editing discipline for ExecPlans in general.

## Purpose / Big Picture

This repository, TUMPhotonicRouter, routes optical waveguides for photonic chips on a discrete grid, using an A* pathfinding search (`src/astar.rs`) to build each route out of "primitives" (short pre-defined path segments) and, when a net's own search fails, a rip-up/reroute repair process (`src/py_router.rs`) that clears space by re-routing a conflicting "victim" net.

Today this repository has **two separate, independently-implemented search kernels** doing fundamentally the same job: `route_single_net_with_bounds_dynamic_expansion` (the "plain kernel", `src/astar.rs`, currently spanning lines 3433-4315, about 880 lines) for nets not currently searching for a crossing, and `route_single_net_with_bounds_crossing` (the "crossing kernel", same file, currently spanning lines 4316-4933, about 615 lines) for nets that are. These are not the same algorithm with a flag -- they are two independently-maintained implementations that have already been found, twice this session, to drift apart in ways that produced real, user-visible bugs (see `.agent/execplans/2026-08-24-crossing-cost-function-soundness.md`'s `n_7`/`n_8` finding, and this same session's `benes_4x4` net-7 investigation). Separately, the per-net dispatch loop that decides how to route each net (`route_many_with_repair_and_commit`, `src/py_router.rs:11833`) tries up to **19 different named strategies** (`grep -n "    fn try_[a-z_]*(" src/py_router.rs` lists them all, see Context and Orientation below) in a long, deeply-nested sequence before falling back to what should be the actual rip-up/reroute repair loop -- including at least one strategy (`try_guided_collision_crossing`) gated behind an undocumented environment variable (`PHOTONIC_ROUTER_ENABLE_GUIDED_COLLISION_CROSSING`) that appears nowhere in any CLI flag, benchmark config, or existing documentation.

The repository owner's own target architecture, worked out directly in conversation this session and this plan's whole reason for existing, is precise enough to build from directly:

1. **Simple routes (L-shaped and Z-shaped direct connections) are tried first, always**, regardless of whether crossings are enabled -- this part already matches the current implementation and is not changing.
2. **There is exactly one A* search kernel, not two.** Every step of the search proceeds identically to today's plain kernel -- same cost, same state, no extra bookkeeping -- until it reaches a cell that is currently blocked by another net's committed route. Only at that point does the kernel make one additional, pluggable call: "can a legal crossing be inserted here?" When crossings are disabled, that call is a no-op that always answers no (identical behavior to today's plain kernel, which is why crossing-disabled routing must not change or slow down at all under this plan). When crossings are enabled and the call answers yes, the cell becomes passable, the crossing's cost is added to the path cost, and only the search states that come *after* that point carry any extra bookkeeping (the existing `pending_after_crossing_cells`/`pending_after_crossing_angle` "must stay straight for N more cells" tracking) -- never the rest of the search. This is what keeps the unified kernel exactly as fast as today's plain kernel for every net that never encounters a crossing candidate, while making the crossing-legality check and the cost model the swappable, pluggable parts instead of the search algorithm itself -- which is also what makes a future swap of the underlying search algorithm (A* for jump-point search, as raised earlier this session, or anything else) possible without touching crossing logic at all.
3. **Rip-up/reroute is its own standalone module**, invoked only when a net's single search attempt through the unified kernel fails outright, with its own internal strategies that can be refined independently of the search kernel. The 19-strategy pre-repair dispatch chain described above does not match this model at all and needs to be reduced to it, keeping only what turns out to be genuinely necessary.

After this plan: `src/astar.rs` has one production search kernel function, not two; a net's routing behavior only differs based on whether a live-discovered collision was found and legalized, never based on which of two duplicate implementations happened to run it; and the rip-up/reroute repair path is a clean, small, well-understood module a person can read start to finish, not a 19-branch dispatch chain accumulated over time. A person can see this working by reading `src/astar.rs` and finding a single search kernel function (not two), by reading `route_many_with_repair_and_commit` and finding a short, clean sequence (simple route attempt, one unified-kernel attempt, then the standalone repair module) instead of the current 19-strategy chain, and by running the full benchmark ladder (exact commands in Concrete Steps) and observing identical or improved results compared to this plan's own recorded starting baseline.

## Surprises & Discoveries

- Observation: the two kernels are not a recent or accidental duplication -- `route_single_net_with_bounds_crossing` was added as a genuinely separate implementation, and this session already found and fixed two distinct ways the two kernels' behavior had drifted apart in cost-affecting ways (the `bend_weight`/`heuristic_weight` override in `.agent/execplans/2026-08-24-crossing-cost-function-soundness.md`, and the topology-precomputed-crossing-plan leak in this same session, `.agent/execplans/2026-08-24-endpoint-correction-cascade-soundness.md`'s sibling work). Both fixes closed real, user-visible anomalies (`n_7`/`n_8`'s all-90-degree bends; a general soundness violation of the "lidar-pure" mode's own design intent) without needing the kernels to be unified -- meaning kernel duplication is not merely a style complaint, it is a demonstrated, repeat source of real bugs, each one only found by a person noticing a visually wrong route shape and an agent tracing it back by hand. This is the direct motivation for this plan, not a hypothetical concern.

- Observation (refined by Milestone 1, see below): the `pending_after_crossing_*` *fields themselves* are confirmed only meaningful post-crossing, as originally hypothesized -- but Milestone 1 found the surrounding state *storage* is not similarly scoped. See Milestone 1's findings below for the complete, corrected picture.

- Observation: `route_many_with_repair_and_commit` (`src/py_router.rs:11833`) tries, per net, in order, before reaching what should be the actual repair loop: `try_preemptive_crossing_ripup`, `try_plain_normal_route`, a four-condition-gated branch that itself tries `try_source_layer_center_out_repair` then `try_pending_straight_victim_repair`, `try_lidar_direct_crossing_subset`, `probe_net_for_repair` (builds a trial route several of the following strategies reuse), `try_guided_collision_crossing` (gated behind the undocumented `PHOTONIC_ROUTER_ENABLE_GUIDED_COLLISION_CROSSING` / `PHOTONIC_ROUTER_DISABLE_GUIDED_COLLISION_CROSSING` environment variables), `try_localized_crossing_keepout_retry`, and `try_commit_clean_probe` -- nine distinct strategies, before `prepare_repair_attempt` (the actual multi-round rip-up loop) is ever reached. Full catalog of all 19 methods now complete, see below.
  Evidence: direct reading of `src/py_router.rs:11917-12100` (the per-net dispatch loop's opening sequence) and `grep -n "    fn try_[a-z_]*(" src/py_router.rs` (19 total matches, 2026-08-25).

### Milestone 1 findings: kernel comparison

Both kernels read in full: plain kernel `route_single_net_with_bounds_dynamic_expansion` (`src/astar.rs:3433-4103`), crossing kernel `route_single_net_with_bounds_crossing` (`src/astar.rs:4316-4929`).

**Identical (no divergence found)**: primitive/neighbor generation and iteration order; tie-breaking (`heap_tie_score`); bounds/windowed-expansion handling (both go through the shared `run_windowed_single_net_search` helper from `.agent/execplans/2026-08-24-modular-routing-strategies.md`'s Phase B work, confirmed, not assumed).

**Structurally necessary for crossing-legality reasoning (A), not simple drift**: per-primitive crossing metadata lookup; the `pending_after_crossing_*` field semantics themselves (confirmed: genuinely gated off for the common non-crossing case); the additive `crossing_progress_heuristic` term on every f-score; two extra target-arrival conjuncts (`pending_after_crossing_cells == 0`, and the require-all-partners mask check).

**Incidental drift a unified design should not carry forward (B)**: the crossing kernel has no cheap `tentative_g_lower_bound >= best_next_g` pre-check before doing expensive footprint/geometry work (the plain kernel has one); closed-set marking happens in a different order relative to the target-arrival check; the crossing kernel never uses the plain kernel's `OpenSet`/indexed-heap optimization (`config.use_indexed_heap` is referenced zero times in the crossing kernel); the crossing kernel has a fully dead `use_monotonic_pruning = false` code block (hardcoded false, unreachable, and the plain kernel has no equivalent code at all -- self-contained cruft, not kernel-parity drift); the crossing kernel is missing the plain kernel's fine-grained per-neighbor-loop timing instrumentation.

**The one genuinely open, unresolved design question for Milestone 2**: the crossing kernel's *legality computation* is already collision-triggered today (a cheap `crossing_no_contact_outcome` fast path handles the common no-contact case; the expensive partner-segment intersection test only runs on genuine contact potential) -- positive, already-precedented evidence that a collision-triggered hook is achievable. But the crossing kernel's *state storage* is not similarly scoped: every single state in a crossing search uses a sparse `FxHashMap`-keyed representation (`CrossingAStarKey`, 7 fields including `crossed_mask`/`next_partner_index`/`straight_run_cells`) and a heavier per-node representation (`CrossingAStarNode`, two `Vec<CellKey>` fields allocated per node) via a raw `BinaryHeap`, instead of the plain kernel's dense-array-indexed storage and indexed heap -- for *every* state, not just ones near an actual crossing candidate. Whether this storage overhead is avoidable in a unified design (versus an unavoidable consequence of being able to track crossing state at all) is not resolvable by reading the current code alone and is explicitly Milestone 2's job to resolve, ideally via the bounded prototype that milestone already calls for.

### Milestone 2: unified kernel design and bounded prototype

**The design, resolving Milestone 1's open storage question.** Reading both kernels' neighbor-expansion loops side by side (plain: `src/astar.rs`, `route_single_net_with_bounds_dynamic_expansion`; crossing: `route_single_net_with_bounds_crossing`) shows the exact point they diverge: on an accepted primitive, the plain kernel does `if !footprint_free { continue; }` and otherwise proceeds with dense-array bookkeeping (`storage.g_costs[next_idx]`, `storage.parent_idx[next_idx]`, an `IndexedOpenSet`/`BinaryHeap` keyed by a flat array index). The crossing kernel instead calls `crossing_no_contact_outcome` or `crossing_move_outcome_with_segments` on *every* accepted primitive (not just blocked ones), builds a `CrossingAStarKey` (7 fields) for every resulting state, and stores it in a `FxHashMap`/`FxHashSet`-backed `SparseCrossingStateStorage` with a plain `BinaryHeap<CrossingAStarNode>` arena -- for every state the search visits, whether or not that state's own path has crossed anything yet.

The design that resolves this: **two-tier state storage**, with the tier boundary drawn at "has this state's own path ever accepted a crossing," not at "are crossings enabled for this search."

- **Tier 1** is exactly today's plain kernel's storage: `DenseSearchStorage`'s flat arrays (`g_costs`, `best_generation`, `parent_idx`, `parent_primitive`, `closed`), indexed by `(x, y, angle)`. Every state that has never touched a crossing lives here, whether or not crossings are enabled for the search -- so a crossing-enabled search's states that never get near an actual crossing candidate (the large majority of any real search, confirmed by the bounded prototype's stats-parity assertions below) cost exactly what they cost today in the plain kernel, not what they cost today in the crossing kernel.
- **Tier 2** is a small side table (`extended_best_cost: FxHashMap<(State, CrossingExtension), f64>`, `extended_closed: FxHashSet<(State, CrossingExtension)>`, plus a growable `Vec<UnifiedExtendedNode>` node arena for parent-chain reconstruction), entered only by the specific state an accepted crossing produces, and only re-entered while that state's `CrossingExtension` (the `crossed_mask`/`next_partner_index`/`straight_run_cells`/`pending_after_crossing_*` fields, moved out of `CrossingAStarKey` into their own small struct) stays non-default. Since `crossed_mask` only ever gains bits, a state can never drop back to Tier 1 once it has crossed something -- but that is a small, bounded subset of any real search's states, not all of them.

**The collision-triggered hook.** One trait, `CrossingLegalityHook`, with one required method (`evaluate`, called only when a step's destination is blocked or the current state already carries a non-default `CrossingExtension`) and two optional methods with zero-cost defaults (`goal_extra_ok`, `heuristic_bonus`, both no-ops unless overridden). `NoCrossingHook` (crossings disabled) always returns `None` from `evaluate` and is never actually called in the fast path at all, since that path is gated by `footprint_free && current_extension.is_default()` before the hook is even consulted -- this is what makes "crossings disabled" and "today's plain kernel" the literal same code path, not just similar. `LiveCrossingHook` (crossings enabled) reuses today's crossing kernel's own legality functions (`crossing_no_contact_outcome`, `crossing_move_outcome_with_segments`) completely unchanged, closing over the same setup (`DenseDynamicCoreOwnerGrid`, partner segments, reservation config) the crossing kernel already builds once per search. Because the kernel loop is generic over `H: CrossingLegalityHook` (monomorphized, not a trait object), `NoCrossingHook`'s no-op `evaluate` has no runtime cost beyond the one boolean branch every accepted primitive already needs.

**Bounded prototype, built and validated, not just designed on paper.** `src/astar.rs`, `mod unified_kernel_prototype` (`#[cfg(test)]`-gated end to end -- structs, trait, both hook impls, the unified kernel function itself, and its tests -- so it adds zero cost and zero surface to production builds; confirmed with `cargo build --release`). Three tests, all passing:
- `unified_kernel_matches_plain_kernel_when_crossings_disabled`: three scenarios (straight route, route forced around a wall, a 90-degree-turn route) run through both today's plain kernel and the unified kernel with `NoCrossingHook`, asserting `states`, `primitives`, `cells`, `compressed_waypoints`, `total_length_um`, `total_cost`, and `reached_target` are identical, plus `expanded_states`/`heap_pushes`/`heap_pops` stats parity -- not just "a route exists," but the same route via the same amount of search work.
- `unified_kernel_inserts_legal_crossing_via_hook`: the same hand-built two-wall-plus-perpendicular-partner fixture the production crossing kernel's own tests already use (`crossing_search_fixture`, replicated here as `crossing_fixture` since it lives in a separate `#[cfg(test)]` module and cannot see the production test module's private helpers), routed through the unified kernel with `LiveCrossingHook`, asserting the returned route actually passes through the partner's column -- proving the hook, not an unrelated detour, produced the route.
- `unified_kernel_rejects_crossing_when_no_hook_allows_it`: the identical obstacle map from the crossing fixture, routed with `NoCrossingHook` instead, asserting the route fails outright -- proving the previous test's success is genuinely due to the hook legalizing a crossing, not an incidental gap in the obstacle map.

`cargo test --lib` (397 tests total) and `cargo clippy --lib --tests` are both clean with this prototype present.

**Known, explicitly out-of-scope gaps in this bounded prototype**, deferred to Milestone 3's full production implementation (not silently dropped -- each is called out in the prototype module's own doc comment in `src/astar.rs` too):
- `AStarConfig::use_indexed_heap`'s `IndexedOpenSet` optimization is not implemented for either tier in the prototype (both tiers use a plain `BinaryHeap`). This does not affect the parity tests above, since `use_indexed_heap` defaults to `false` and both kernels being compared use a plain `BinaryHeap` by default already. Milestone 3 should decide whether Tier 1 gets the full indexed-heap treatment (recommended, since it is a pure performance optimization with no behavior change, and the plain kernel already has it) and how or whether Tier 2 participates.
- `crossing_candidate_hits_active_local_crossing_reservation`'s local self-overlap guard (preventing a route from crossing the same partner segment at two different points in a way that conflicts with itself) is not reproduced. Irrelevant to the single-partner fixtures tested here, but load-bearing for any route that crosses the same partner more than once; Milestone 3 must carry it forward.
- The prototype's `LiveCrossingHook` does not carry the crossing kernel's local-reservation bookkeeping (`active_local_reservation_keys`/`pending_local_reservation_keys` on `CrossingAStarNode`) at all -- a consequence of the point above, not a separate gap.

### Milestone 3: production implementation, both gaps closed, one real bug found and fixed

**Indexed heap for Tier 1.** `OpenSet`/`IndexedOpenSet` (the plain kernel's own existing open-set types, `src/astar.rs`) gained one small additive method, `peek() -> Option<&OpenEntry>`, so the unified kernel can compare Tier 1's best candidate against Tier 2's without popping either. Tier 1 now uses `OpenSet::new(config.use_indexed_heap, ...)` unchanged -- the exact type the plain kernel uses -- so `use_indexed_heap = true` is honored for the tier that matters (Tier 1 is the overwhelming majority of states in any search). Tier 2 keeps a plain `BinaryHeap<OpenEntry>`, which is never slower than what today's *entire* crossing kernel already does for *every* state unconditionally. Each iteration peeks both heaps and pops whichever holds the better candidate, falling back to the only one that is non-empty, or stopping when both are.

Also discovered while writing this: `use_indexed_heap` is not the rarely-set benchmark-only flag it might look like from `src/astar.rs` alone. `translation/route_rust.py:6277` sets `self.astar_cfg.use_indexed_heap = bool(self.use_indexed_heap or self.allow_45_degree_turns)` -- meaning it is forced on for *any* benchmark using 45-degree primitives, which is the common case, not an edge case. The parity test (`unified_kernel_matches_plain_kernel_when_crossings_disabled`) now runs every scenario under both `use_indexed_heap` values for exactly this reason, not just the struct default.

**Reused `OpenEntry`/`entry_is_better` instead of inventing a parallel type.** Milestone 2's prototype invented its own `UnifiedOpenEntry`/`UnifiedOpenRef` heap-entry type. Rereading today's crossing kernel while implementing the reservation guard (below) surfaced that it already reuses the plain kernel's own `OpenEntry` struct for its own arena, giving `idx` a second meaning ("index into `nodes: Vec<CrossingAStarNode>`") rather than inventing a new entry type -- so Tier 2 does the same here: `BinaryHeap<OpenEntry>` where `idx` means "index into `extended_nodes`". `UnifiedOpenRef` still exists, but now only as bookkeeping for provenance (Tier 1 vs. Tier 2 index) passed around outside the heaps, not as the heap's own element type. This is both a simplification and a closer match to the codebase's existing convention than Milestone 2's version was.

**Local self-overlap reservation guard, made cheaper by construction, not just ported.** `unified_candidate_hits_active_local_crossing_reservation` reproduces `crossing_candidate_hits_active_local_crossing_reservation`'s behavior (walk the current state's ancestor chain, reject if a candidate primitive's witness cells collide with an ancestor's `active_local_reservation_keys`). But because Tier-1 (dense) states structurally can never carry a reservation -- confirmed by construction, not by convention, since `UnifiedExtendedNode` is the only place `active_local_reservation_keys` is ever populated -- the walk here stops the instant it reaches a `UnifiedParentRef::Dense` ancestor. Today's crossing kernel has no such stopping point: every state lives in the same flat `nodes` arena, so its equivalent walk goes all the way back to the search's own source on every call, regardless of how far the current state actually is into an active corridor. This is a genuine, structural efficiency improvement the two-tier design produces as a side effect, not something separately engineered.

**A real correctness bug found in Milestone 2's prototype, fixed here.** Rereading the crossing kernel's primitive loop line by line (not just its two legality functions) surfaced that the "is this primitive a valid continuation of an active post-crossing corridor" check -- angle must match `pending_after_crossing_angle`; the primitive must complete or correctly extend the required straight run -- lives in *the loop itself* (`src/astar.rs`, right before `next_x`/`next_y` are even computed), not inside `crossing_no_contact_outcome`. That function's own body computes a `remaining_pending_after_crossing` value unconditionally, with no awareness of whether the current primitive actually respects the pending corridor at all. Milestone 2's prototype called `crossing_no_contact_outcome` directly on its cheap-path branch without first performing this check, meaning a primitive that broke a pending straight-run requirement would have been silently accepted whenever its destination happened to be free -- `crossing_move_outcome_with_segments` (the expensive path) does perform this check internally and would have caught it there, but the cheap path had no equivalent guard. The bounded prototype's fixtures (`crossing_half_size_cells: 0`, `bend_runout_cells: 0`, giving `capped_required_margin = 1`) never exercised a long enough pending corridor to hit this, so the gap produced no test failures -- it was found by rereading the original code side by side with the port, not by a failing assertion. Fixed by porting the same pre-check into the unified kernel's own loop, in the same place, before the hook is ever consulted.

**Test additions beyond what Milestone 2 had**: `unified_kernel_matches_plain_kernel_when_crossings_disabled` now runs under both `use_indexed_heap` values (see above). (insufficient_straight_margin)"` rejections. ### Milestone 5: Milestone 1's classification was wrong for 4 of the "6 artifacts" -- caught by a call-graph fork before any code was deleted

**The correction, in full, since it changes what this milestone actually is.** Milestone 1 (a read-only investigation done before Milestone 2-4's actual kernel unification existed) classified 6 `try_*` methods as artifacts of having two kernels: the 3-level `try_route_with_collision_crossings` → `_with_loss` → `_using_primitives` chain, `try_route_through_expected_crossing_partner`, `try_lidar_direct_crossing_subset`, and `try_guided_collision_crossing`. Before deleting any of them, a fork was sent to map the real call graph (every call site, every caller's actual role, git history for the two env-var experiments) rather than trusting the earlier classification's framing at face value. It found:
- `try_route_with_collision_crossings` (all 3 levels) and `try_route_through_expected_crossing_partner` are called from `route_single_net_and_commit_native` -- the core per-net routing primitive used across dozens of sites in `src/py_router.rs`, not from the 19-strategy repair dispatch chain at all. That function's own comment: *"Fresh/native routing: try the plain, non-crossing attempt first... a lidar-pure collision-crossing search only happens later, deferred, if that plain attempt fails."* This chain **is** the crossing-aware search step of the repository owner's own architecture (Purpose section, point 2) -- not a redundant path to a since-merged kernel. It already reaches the unified kernel via `AStarSingleNetSearch.search_with_collision_crossing`, exactly like everything else post-Milestone-4. Left untouched.
- `try_lidar_direct_crossing_subset` has exactly one caller (the repair dispatch loop) and is a real, purposeful, single-purpose strategy that happens to reuse the shared search primitive above -- reclassified from "artifact" to the same bucket as the 11 already-legitimate strategies Milestone 1 found. Left untouched.
- Only `try_guided_collision_crossing` and the separately-tracked `try_preemptive_crossing_ripup` (both off by default, both single-caller, both scoped to the repair dispatch loop) matched Milestone 1's real target. Git history on both (`git log -p` across every commit touching either) found only mechanical "extract Phase N into a named method" refactors and terse administrative checkpoint commits -- no commit anywhere explains why either should be opt-in rather than always-on or deleted.

**Practical consequence: the actual repair-dispatch chain shrinks by 2 strategies (19 → 17), not the 6 Milestone 1 predicted.** The Purpose section's aspirational "short, readable repair dispatch instead of 19 strategies" language should be read against this: most of the 19 methods are genuinely necessary complexity for a working rip-up/reroute system, not duplication left over from two kernels. Milestone 1's own classification already said as much for 11 of them ("legitimate, already-reasonably-factored repair-module strategies"); this milestone's correction extends that verdict to 3 more items Milestone 1 had mis-scoped, leaving only the 2 truly undocumented experiments as the real cleanup target.

**The repository owner's decision, made after reviewing the git-history findings directly** (not decided by the assistant): delete both `try_guided_collision_crossing` and `try_preemptive_crossing_ripup`. Deleted along with every helper that existed only to serve them, verified via the same "delete, recompile, follow the compiler's own dead-code warnings" discipline Milestone 4 used: `crossing_local_ripup_candidates` and its 3 exclusive `CROSSING_LOCAL_RIPUP_*` constants, `preemptive_crossing_ripup_enabled`, `env_flag_enabled` (itself only ever called by `preemptive_crossing_ripup_enabled`), and the `GuidedCrossingOutcome`/`PreemptiveCrossingRipupOutcome` enums. `try_route_through_collision_partner_set` (the shared primitive `try_guided_collision_crossing` called) was confirmed still needed -- `try_crossing_aware_victim_reroute`'s own "guided" per-victim attempt also calls it -- and was left untouched.

**A near-miss during the deletion itself, caught immediately by the compiler, not silently shipped.** The dispatch loop's `guided_collision_crossing_enabled` local variable looked, at a glance (and per the investigating fork's own read), like it was computed once right before the now-deleted `try_guided_collision_crossing` call and never read elsewhere -- consistent with Milestone 1's separately-flagged "dead local variable" finding. Deleting that declaration alongside the call broke the build: `try_crossing_aware_victim_reroute`, called much later in the same function's round-based repair loop, also takes this exact flag as a parameter for its own "guided" attempt. The declaration was restored (without the deleted call), with a comment explaining why it survives. This is a concrete instance of why every deletion in this plan has gone through an actual compile-and-test cycle rather than a grep-based dead-code judgment alone -- a `grep`-only pass (which is what the fork itself used to reach its "unused" conclusion) can miss a read that occurs far from the write in a very large function.

**Milestone 1's misattached-doc-comment finding, fixed as part of this same removal.** `try_preemptive_crossing_ripup`'s own doc comment was physically sitting above `try_ripup_single_victim_and_reroute`'s `fn` instead of its own (already flagged, unfixed, in Milestone 1). With `try_preemptive_crossing_ripup` now deleted, that orphaned doc-comment fragment was removed, and `try_ripup_single_victim_and_reroute`'s own doc comment (correctly attached, just concatenated with the fragment above it) was updated to describe its current single remaining caller (`try_pending_straight_victim_repair`) instead of the two it used to have.

## Context and Orientation

### Key terms, defined for a reader new to this repository

"Kernel" (this plan's own shorthand): one complete A* search function -- given a source, a target, an obstacle map, and a cost configuration, it explores grid states and returns a route or failure. "Plain kernel": `route_single_net_with_bounds_dynamic_expansion`. "Crossing kernel": `route_single_net_with_bounds_crossing`. Both are in `src/astar.rs`; re-locate their exact current line numbers with `grep -n "^fn route_single_net_with_bounds_dynamic_expansion\|^fn route_single_net_with_bounds_crossing" src/astar.rs` before relying on the line numbers quoted in this plan, since other work may shift them.

"Collision-triggered": a design where extra logic only runs at the specific point a search would otherwise fail (a blocked cell), not on every step of the search -- as opposed to logic that runs unconditionally throughout, which is what having a whole second kernel implementation effectively does today even though only a fraction of any given search actually touches a crossing.

"Rip-up/reroute" / "repair": when a net's own search attempt fails outright, the process of removing ("ripping up") a conflicting, already-routed "victim" net and re-routing both nets, possibly across several rounds, to find an arrangement where both succeed. `RipupRerouteConfig` (`translation/route_rust_types.py:295`) is the user-facing (currently) configuration for this; see `.agent/REPOSITORY_STATE.md`'s Next Engineering Step for the separate, already-recorded observation that this should likely not be a user-toggleable flag at all, since the router genuinely needs it whenever plain search fails -- out of scope for this plan to resolve, but relevant context for Milestone 5's design of the "standalone repair module."

"The 19 `try_*` methods": every method in `src/py_router.rs` whose name starts with `try_`, found via `grep -n "    fn try_[a-z_]*(" src/py_router.rs` (2026-08-25): `try_route_source_layer_center_out_native`, `try_route_with_collision_crossings`, `try_route_with_collision_crossings_with_loss`, `try_route_with_collision_crossings_using_primitives`, `try_route_through_collision_partner_set`, `try_route_through_expected_crossing_partner`, `try_guided_collision_crossing`, `try_localized_crossing_keepout_retry`, `try_commit_clean_probe`, `try_plain_normal_route`, `try_reroute_current_net_before_victims`, `try_crossing_aware_victim_reroute`, `try_reroute_current_net_after_victims`, `try_ripup_single_victim_and_reroute`, `try_preemptive_crossing_ripup`, `try_source_layer_center_out_repair`, `try_pending_straight_victim_repair`, `try_lidar_direct_crossing_subset`, `try_final_repair_fallback`.
