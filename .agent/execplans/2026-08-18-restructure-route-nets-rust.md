This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds.

This document follows `.agent/PLANS.md` in this repository. It is informed by `.agent/PROJECT_GOAL.md`, by `.agent/CLAUDE_CODEX_FLOW.md` (Claude plans, reviews, and verifies; Codex CLI does the mechanical edits via `.agent/scripts/codex_task.sh`), and by `.agent/execplans/2026-08-17-restructure-translation-route-rust.md` ("Phase 1"), which this plan continues as "Phase 2." Phase 1 is complete and committed: it moved about 100 free-standing helper functions out of `translation/route_rust.py` into topic modules, shrinking the file from 11,327 to 6,865 lines, with zero behavior change verified after every one of its 7 slices. Phase 1 deliberately left one thing untouched, and that thing is this plan's entire subject.

Purpose / Big Picture

After Phase 1, `translation/route_rust.py` is almost entirely one function: `route_nets_rust`, which starts at line 648 and runs to the end of the file, roughly 6,218 lines. Inside that one function body there are 120 nested `def` statements (Python lets you define a function inside another function; a function defined this way is called a closure, because it can read and change variables from the function it's nested inside, the way a closure "closes over" its surroundings). This is the actual reason `translation/route_rust.py` still looks unreadable even after Phase 1 removed everything else: one function, ~6,200 lines, ~100 nested helper functions all silently sharing state through Python's closure mechanism instead of through explicit parameters you could read at a glance.

The user's underlying request (2026-08-17) was that the codebase should be readable, structured with known good practice, and not have huge files where everything is mixed together. This plan is the concrete continuation of that request for the piece of code that most embodies the problem.

The goal of this plan is not to shrink line count for its own sake and not to change routing behavior at all, not even a little. The goal is to turn `route_nets_rust`'s implicit, closure-captured shared state into an explicit Python class, where the shared state becomes named attributes (`self.something`) that a reader can see declared in one place, and each of the ~100 nested closures becomes a method on that class. This is a much bigger change in kind than Phase 1: Phase 1 only moved code (cut, paste, add an import); this plan changes how the code is written (closures become methods, implicit capture becomes explicit `self.`), while being just as careful to prove that behavior does not change.

You will be able to see this plan working, milestone by milestone, the same way Phase 1's slices were verified: after each milestone, the exact same benchmark commands used before the milestone produce byte-identical verification JSON (aside from timestamps), and the exact same test suite passes and fails the exact same tests. At the end of the whole plan, `route_nets_rust` itself should be a short function: build a session object, call one or two driver methods on it, return the result. A human reading `translation/route_rust.py` afterward should be able to find "the part that handles fanout stub geometry" or "the part that does final crossing repair" by looking at a list of method names on one class, instead of scrolling through thousands of lines hunting for a `def` buried inside another `def`.

Because this is genuinely riskier than Phase 1 (see Decision Log for why), this plan is written to be executed milestone by milestone with a stop-and-check-in point after Milestone 5 and, separately, before Milestone 8, rather than run straight through unattended the way Phase 1's 7 slices were. (These milestone numbers reflect a mid-execution restructuring recorded in the Decision Log; the plan originally had 8 milestones and now has 9.)

Surprises & Discoveries

- Observation: `route_nets_rust` is 6,218 lines (line 648 to end of file, 6,865), not the roughly 6,200-from-line-5110 estimate made during Phase 1 planning; Phase 1's own edits shifted the start line down.
  Evidence: `grep -n "^def route_nets_rust" translation/route_rust.py` reports line 648; `wc -l translation/route_rust.py` reports 6865.
- Observation: of 331 names assigned somewhere in `route_nets_rust`'s own body, only 98-111 are ever referenced inside a nested closure (depending on how nested-closure-of-closure captures are counted); the rest are pure driver-code locals no closure touches. The candidate list of things that need to become `self.attr` is smaller than the raw line count suggests.
  Evidence: AST-based capture analysis performed by the research fork, cross-checked against direct reads of the initialization block.
- Observation: two objects, `router` (the native `PyPhotonicRouter` instance, created at line 1002) and `route_bookkeeping` (a `RouteBookkeeping` instance from `translation.route_rust_records`, created at lines 3154-3157), are mutated constantly through their own methods and through native Rust calls, but a naive scan for Python-level reassignment (`x = ...`, `x[...] = ...`, `x.attr = ...` on the name itself) would wrongly report zero mutations on them. Both must be treated as core, heavily-mutated session state regardless of what a simple static scan says.
  Evidence: research fork's AST scan plus direct reads of the dispatch block, where `router.route_single_net_and_commit(...)`, `router.route_many_with_repair_and_commit(...)`, and similar calls appear repeatedly without ever rebinding the name `router`.
- Observation: `lateral_position` is defined three separate times as three separate closures at three different nesting depths: line 2453 (inside `_dense_source_port_runway_lengths`), line 2503 (inside `_dense_target_port_runway_lengths`), and line 2946 (directly inside a top-level `for` loop body in `route_nets_rust` itself, redefined fresh every loop iteration, not nested inside any other closure).
  Evidence: research fork's closure inventory, confirmed by name.
  Consequence: naively promoting all three to methods of one class would collide. They need three distinct names. The third one (line 2946) additionally must not be "hoisted" into a method defined once outside the loop while still assuming it can see the loop variable by closure capture; it needs to either stay a true per-iteration local closure inside whatever method that loop becomes, or take the loop variable as an explicit parameter.
- Observation: `_grid_cell_center_um` is defined both as a `route_nets_rust` closure (line 925) and as a top-level function already living in `translation/route_rust_records.py` (a Phase 1 module). This is the same class of issue Phase 1 hit twice (`_centerline_tuple` and `_port_center_um` in Slice 1 and Slice 4). Resolved during planning for Milestone 3 (Cluster A): read both definitions and confirmed they are NOT true duplicates (different signatures: the records-module version takes a single `cell: tuple[int, int] | None` plus explicit `grid_size_um`/`origin_x_um`/`origin_y_um` keyword arguments and handles `None`; the closure version takes `cell_x`/`cell_y` as two separate non-nullable arguments and derives `grid_size_um` from the captured `grid` object). Since the closure becomes a method (`self._grid_cell_center_um`), it lives in a different namespace than the module-level function entirely, so there is no actual name-collision risk from the conversion itself, only a minor same-name-different-thing readability note; kept both under the same name, matching the accepted `_port_center_um` precedent from Phase 1.
  Evidence: research fork's closure inventory cross-referenced against Phase 1's sibling modules.
- Observation: 8 names across 6 locations use Python's `nonlocal` keyword, which is Python's explicit, required way of saying "this nested closure is going to reassign (not just read) a variable from its enclosing function." These are the strongest, least ambiguous signal of "this really is mutable shared state, and here is exactly where it gets written": `raw_static_rect_ranges_by_y`, `heater_opening_rect_ranges_by_y`, `raw_static_cells_by_y` (three small memoization caches), `total_expanded_states` and `simple_route_count` (declared inside `_finalize_committed_route`, line 4549), `photonic_probe_index`, `last_photonic_probe_layout`, `last_photonic_probe_records` (declared around line 6414-6448).
  Correction, Milestone 3 (2026-08-18): this entry originally said the first three were "declared inside sub-closures of `_rect_ranges_by_y`," i.e. nested *inside* it. That was wrong, inherited uncritically from the original research fork's report and never independently checked before Milestone 2 used it to decide these three needed no promotion. They are actually sibling closures at the same nesting depth as `_rect_ranges_by_y` (confirmed by comparing indentation directly in the source: `_rect_ranges_by_y`'s own `def` and `_raw_static_rect_ranges_by_y`'s `def` are both indented identically, both direct children of `run()`), so their `nonlocal` declarations are relative to `run()`, exactly like the other 5. This was a real gap in Milestone 2 (these 3 should have been among the 71 promoted names and were not), fixed as part of Milestone 3; see that Progress entry for the fix and its verification. Lesson: a fact inherited from an earlier report should still get checked against the actual source before being used to justify skipping something, not just cited.
  Evidence: `grep -n "nonlocal "` inside the function body, confirmed by the research fork's reads of each declaration site.
  Consequence: when converting these to `self.attr`, every site that currently has `nonlocal X` must have every read of `X` become `self.X` and every write to `X` become `self.X = ...` (or `self.X += ...`). Missing a write site would silently create an unused local variable shadowing the real attribute, rather than raising any error, so this needs deliberate line-by-line review at whichever milestone touches each one, not just a mechanical find-and-replace.
- Observation: the function is not "define ~100 closures, then one driver block at the end." It is 7 repeating phases: define a batch of closures, immediately followed by driver statements that use them, then the next phase. The single densest block of actual sequential routing logic is 414 lines (roughly 4586-5000): it branches between a native batch-plus-repair path (`router.route_many_with_repair_and_commit(...)`) and a different path when repair is disabled, and is where most of the closures from earlier clusters actually get called.
  Evidence: research fork's read-through of the full function, reporting cluster boundaries by line range and confirming the call graph is strictly forward (a cluster's closures only call closures defined earlier in the same or an earlier cluster, never a later one).
- Observation: no recursive closures were found, and the dispatch block's native/Rust calls receive plain data (tuples, a grid spec, and similar), not closures passed as callbacks; the "a closure gets passed into Rust code, so its exact call signature matters" risk does not appear to apply here.

- Observation: two closures are large enough that converting them to methods just relocates the readability problem rather than solving it: `_write_route_diagnostics` (486 lines, with 3 of its own nested depth-1 helpers plus one depth-2 helper; the single largest closure in the function) and `_route_attempt_diagnostics` (247 lines).
  Evidence: research fork's line-range measurements.

- Observation: a first attempt at a capture-analysis script (checking every `ast.Name` reference inside a closure against a candidate name list, without resolving Python's actual scoping rules) produced 144 "captured" names, most of which were false positives: many closures reuse the same common parameter names (`job`, `net_id`, `record`, `cell`, `item`, and so on) for their own, unrelated local parameters, and a naive scan cannot tell "this closure's own parameter happens to share a name with something in `run()`" from "this closure genuinely reads something from `run()`'s scope."
  Evidence: comparing the naive script's 144-name output against a corrected, scope-resolving version (which computes each closure's own local names -- its parameters plus anything it assigns -- and only counts a reference as a real capture if the name is not shadowed by the closure itself or any closure between it and `run()`) that produced 68 names.

All 71 have a confirmed single first-creation line within `run()`'s own top-level body (not inside any closure), which is the basis for Milestone 2's task file.
  Consequence, separately: 3 more `nonlocal`-declared names (`raw_static_rect_ranges_by_y`, `heater_opening_rect_ranges_by_y`, `raw_static_cells_by_y`) turned out to be declared `nonlocal` *relative to `_rect_ranges_by_y`* (a Cluster A closure), not relative to `run()` itself; they are small memoization caches private to `_rect_ranges_by_y`'s own sub-closures. These do NOT need promotion to `self.attr` at all: once `_rect_ranges_by_y` becomes a method (Milestone 3), its own nested sub-closures can move with it completely unchanged, since Python closures nested inside a method work exactly like closures nested inside a function. This corrects the plan's earlier Surprises & Discoveries entry about these three names, which had lumped them in with the genuinely `run()`-level `nonlocal` names without checking which closure each was actually relative to.

Decision Log

- Decision (mid-execution restructuring, 2026-08-18, after Milestone 1): insert a new Milestone 2 that promotes ALL remaining genuinely-captured shared state to `self.attr` in one dedicated pass, covering the whole `run()` method at once, before converting any closure to a real method. The originally-planned Milestone 2 ("convert Cluster A") becomes Milestone 3, and every later milestone shifts up by one (the plan now has 9 milestones instead of 8); the two user check-in points shift accordingly, to after Milestone 5 (was 4) and before Milestone 8 (was 7).
  Rationale: the original plan assumed each cluster's conversion would handle its own newly-needed shared state as it came up. Hands-on work on what was going to be Milestone 2 showed this would mean repeating a subtle, error-prone scope-correct capture analysis 7 separate times (see the Surprises & Discoveries entries above about the naive-vs-scope-correct capture script, and about `nonlocal`-only variables that a plain read-reference scan misses entirely), with real risk of a mistake compounding silently across milestones. Promoting all 71 remaining names to `self.attr` first, verified with the same from-scratch-AST-audit discipline Milestone 1 used, means every subsequent closure-to-method move in Milestones 3-9 becomes a genuinely pure "cut this closure out, paste it as a method, add `self`" operation with zero state-analysis risk left to get wrong per closure, since anything a closure could possibly reference is already sitting on `self` before the move happens.
  Date/Author: 2026-08-18 / Claude.

- Decision: convert `route_nets_rust`'s shared closure state into a class, with shared locals becoming `self.attr` and nested closures becoming bound methods, rather than trying to make each closure a free (module-level or nested) function with fully explicit parameters.
  Rationale: a class preserves the exact same sharing semantics closures already have (`self.x` reads/writes the same underlying value from any method, exactly like closure capture does from any nested `def`), so the conversion can be close to mechanical for the majority of closures. Redesigning every closure into a pure function with explicit parameters would require deciding, for each of ~100 closures, exactly which of the 98-111 shared names it needs passed in and in what order, which is a much larger design surface and a much larger chance of silently passing the wrong value or a stale copy. This matches the "safest first" approach the user chose for Phase 1's ordering and is the same reasoning, applied to a harder problem.
  Date/Author: 2026-08-18 / Claude, based on the research fork's structural audit.
- Decision: sequence the 8 milestones in the order listed in Progress, following the function's own natural cluster boundaries (A through G, in the order they appear in the file) rather than, for example, converting the two largest/riskiest closures first.
  Rationale: the research fork found the call graph is strictly forward (each cluster only calls closures already converted or about to be converted in an earlier or the same cluster), so converting in file order means every milestone's new methods can immediately call already-converted methods from earlier milestones without any temporary shims or forward references. It also front-loads the mechanical, low-risk milestones (1, 2, 5, 8) and isolates the two genuinely trickier ones (3's naming collision, 4's `nonlocal` boundary, and especially 7's control-flow surgery) so each can get focused attention instead of being buried in a larger diff.
  Date/Author: 2026-08-18 / Claude.
- Decision: add two stop-and-check-in points, after Milestone 5 and before Milestone 8 (numbers reflect the restructuring above), instead of running all milestones straight through the way Phase 1's 7 slices ran without a pause.
  Rationale: Milestone 5 (Cluster C) is where the class's real mutable session state that Milestone 2 did not already cover -- the `router` object, `route_bookkeeping`, and the remaining job/counter setup -- gets fully established; getting that boundary wrong would compound through every later milestone, so it is worth a deliberate look before continuing rather than only finding out at the end. Milestone 8 (the dispatch block) is the one part of this whole plan that is not a mechanical closure-to-method conversion: it is converting real branching control flow (414 lines dispatching between two different native routing calls) into a method, which the research fork explicitly flagged as "the one genuine judgment call in the whole plan." Both check-ins are with the user, not just an internal note, given how much more consequential a mistake here would be than in Phase 1's pure code motion.

Context and Orientation

Read `.agent/execplans/2026-08-17-restructure-translation-route-rust.md` first if you have not already; it explains the Phase 1 module layout (`translation/route_rust_geometry.py`, `translation/route_rust_crossing_verification.py`, `translation/route_rust_crossing_components.py`, `translation/route_rust_crossing_plan.py`, `translation/route_rust_endpoint_correction.py`, `translation/route_rust_debug_artifacts.py`, `translation/route_rust_obstacle_config.py`) and the compatibility-re-export pattern this plan will keep following for anything outside `translation/route_rust.py` that still imports a name from it.

A closure, for readers unfamiliar with the term: in Python, you can define a function inside another function. The inner function can read (and, if you use the `nonlocal` keyword, reassign) variables that belong to the outer function, even after the outer function has moved on to later lines. This is exactly how `route_nets_rust` shares state across its ~100 helper functions today: instead of passing values as arguments, each nested `def` just reaches out and touches whatever outer-function variable it needs. That is convenient to write and very hard to read, because there is no single place that lists what state exists or which functions touch it; you have to read the whole 6,200-line function to find out.

`route_nets_rust`'s body divides into 7 sequential clusters, each a batch of closure definitions immediately followed by driver code that calls them, in this order (line numbers current as of 2026-08-18, before this plan's own edits shift them):

Cluster A, lines ~840-2362, about 30 closures: grid and geometry primitives, and static fanout stub geometry. Mostly pure functions of the grid spec, origin coordinates, and bend radius; low coupling to other clusters. Includes `_pipeline_timer_start`, `_record_pipeline_timing`, `_orientation_to_angle`, `_angle_to_step`, `port_to_grid_state`, `_rect_ranges_by_y` (with 3 memoized sub-closures using `nonlocal`), `_heater_pad_port_open_cells`, `_grid_cell_center_um` (name-collision risk, see Surprises & Discoveries), `_append_circular_stub_bend`, `_two_bend_static_stub_centerline_um`, `_build_static_fanout_anchors`, and about 20 more.

Cluster B, lines ~2364-2838, about 10 closures: dense port runway length computation (`_dense_source_port_runway_lengths`, `_dense_target_port_runway_lengths`, each containing their own `lateral_position` closure) followed by driver code that builds the `crossing_plan_info` report dict through about 15 sequential subscript assignments (lines 2577-2629), then port-opening/keepout helpers.

Cluster C, lines ~2969-3167: `_dense_source_fanout_route_order` (with the third `lateral_position` defined directly in a `for` loop just before it, at line 2946), then driver code building `route_jobs` and handling `--debug-stop-after-route` truncation, then the block that creates the function's real mutable session state: `router` was already created earlier at line 1002, but `route_bookkeeping`, `route_jobs_by_id`, `route_order`, `total_expanded_states`, `simple_route_count`, `repair_count`, `route_attempt_records`, `native_repair_trace_records`, and `route_timing_buckets` are all created here, at lines 3149-3167. This is the natural boundary for where a class's `__init__` should end and its "everything after this point is mutable session state" section begins.

Cluster D, lines ~3182-3538: native batch/timing helpers (`_timing_start`, `_record_elapsed`, `_record_native_batch_timings`, `_report_long_straight_congestion`) and per-job state/opening precompute, including a driver block that precomputes `route_state_openings_by_id` and `batch_clearance_exempt_cells_by_id` for every job up front.

Cluster E, lines ~3546-5169: diagnostics and logging closures, including the two largest ones (`_write_route_diagnostics`, `_route_attempt_diagnostics`), plus `_finalize_committed_route`, followed by the 414-line main dispatch block (roughly 4586-5000) that branches between the native repair-batch path and the simpler path, then two more large closures for checked endpoint corrections.

Cluster F, lines ~5413-6255: crossing-aware endpoint correction closures, driver code assembling `routed_net_records`, then final crossing repair closures ending with `_repair_final_illegal_crossings` (197 lines).

Cluster G, lines ~6257-6865: photonic verification repair closures, ending with the function's true tail: a repair-round loop, an `illegal_realized_crossings` check, debug artifact writing, and the function's `return` statement.
