## Purpose / Big Picture

`translation/route_rust.py` is 11,327 lines, the second largest file in the repository after `src/py_router.rs` (17,399 lines). After this plan's Phase 1, a human should be able to open `translation/route_rust.py` and find a short file that mostly imports and re-exports from clearly named sibling modules (`translation/route_rust_geometry.py`, `translation/route_rust_crossing_verification.py`, and so on, matching the naming convention already used by the existing `translation/route_rust_realization.py` and `translation/route_rust_records.py`), plus the two top-level orchestration entry points `route_match_and_realize` and `route_nets_rust`. Nobody should have to scroll through unrelated geometry math, crossing-component placement, and endpoint-splicing logic to find the function they need.

This plan explicitly does not fix the single worst offender inside this file: `route_nets_rust` itself is one function running from line 5110 to the end of the file (line 11327), roughly 6,200 lines, containing about 100 nested closures that all read and mutate shared local state (grid, jobs, timing accumulators, and so on). Restructuring that function safely means turning shared closure state into explicit parameters or an object's attributes, which is a real behavioral-risk refactor, not a pure code move. The user chose to start with the safest available work first (see Decision Log), so this plan's Phase 1 only moves the roughly 100 free-standing top-level functions that already sit before `route_nets_rust` (lines 102 through about 5109) into topic modules, with zero intended behavior change. Phase 2 (decomposing `route_nets_rust` itself) and Phase 3 (the large Rust files: `src/py_router.rs`, `src/astar.rs`, `src/geometry_realization.rs`) are named here for context but are explicitly out of scope for this plan; each needs its own ExecPlan once Phase 1 has proven the working pattern.

You can see this plan working by, at the end of Phase 1: opening `translation/route_rust.py` and seeing it under roughly 7,300 lines (down from 11,327) with `route_match_and_realize` and `route_nets_rust` as its only substantial function bodies; running the full existing Python test suite and seeing the same pass/fail result as before the change; and running the `benes_4x4` and `benes_8x8` crossing benchmarks and seeing byte-identical `build/verification/*_crossing_verification.json` and `*_photonic_verification.json` reports (modulo timestamps, if any) compared to a baseline captured before Phase 1 started.

## Surprises & Discoveries

- Observation: `route_nets_rust` is not a normal large function; it is a single 6,200-line function body containing about 100 nested `def` closures that share its local scope (grid state, job lists, timing accumulators, and helper caches).
  Evidence: `sed -n '5110,11327p' translation/route_rust.py | grep -c '^    def '` reported 100; `grep -n '^def |^class ' translation/route_rust.py` showed no further top-level definition after `route_nets_rust` at line 5110 through the end of the file at line 11327.
  Consequence: these closures cannot be mechanically cut-and-pasted into module-level functions without deciding how to pass or hold their shared state (parameters, or an explicit session object with attributes). That is real design work and is why this decomposition is Phase 2, not part of this plan.
- Observation: at least two function names appear to be duplicated between `translation/route_rust.py` and the already-separate `translation/route_rust_records.py`: `_port_center_um` (route_rust.py line 2160, route_rust_records.py line 20) and `_centerline_tuple` (route_rust.py line 204, route_rust_records.py line 223).
  Evidence: `grep -n '^def _port_center_um\|^def _centerline_tuple' translation/route_rust.py translation/route_rust_records.py`.
  Consequence: whoever implements Slice 1 must check whether these are true duplicates (same behavior, copy-pasted during an earlier split) that should be consolidated into one shared definition, or subtly different functions that happen to share a name. Do not silently move a duplicate without checking; record the finding here either way.

## Context and Orientation

`translation/route_rust.py` is the Python-side bridge between the Rust routing engine (`photonic_router._rust`, built from `src/`) and the rest of the pipeline in `routing_flow.py`. It is responsible for: converting schematic/placement data into Rust-side route jobs and obstacle configuration; invoking the native batch router; verifying that realized route geometry has legal crossings and no invalid intersections; placing PDK/gdsfactory crossing components into the final layout; correcting route endpoints so they connect cleanly to component ports while protecting crossing-bearing route segments; and writing debug/verification artifacts under `build/verification/` and `build/`.

The file currently has two natural halves. Lines 1 through roughly 5109 are about 100 free-standing top-level functions (plus a handful of small classes), each one only calling other functions in the same half or built-in/library code, not closing over shared mutable state. Lines 5110 through 11327 are a single function, `route_nets_rust`, which is the native-router driver: it sets up grid state, builds jobs, calls the Rust batch router, and reports timing, using about 100 nested closures to avoid re-passing that shared state as parameters everywhere. `route_match_and_realize`, at lines 4220 through 4629, sits near the boundary between the two halves: it is a top-level function (so mechanically it is in the "safe" first half), but it is itself a 409-line orchestrator that calls many of the helper functions this plan is about to relocate, so its own body will need its internal calls' import paths updated even though it does not move.

Every module this plan creates lives in `translation/`, alongside the existing `translation/route_rust_realization.py`, `translation/route_rust_records.py`, `translation/route_rust_meanders.py`, `translation/route_rust_types.py`, and `translation/route_rust_analysis.py`. Read a couple of these first (they are short, 400-1300 lines) to see the established style: a one-line module docstring, explicit type hints matching the rest of the file, and no behavior changes relative to whatever they were extracted from.

## Validation and Acceptance

A slice is acceptable only if: `py_compile` passes for every touched file; every targeted test file listed for that slice passes with the same pass/fail counts as the baseline (an already-failing test staying failed for the same reason is fine; a newly-failing test is not); and `git diff` for the slice shows only code motion plus import changes, no logic edits, when read function by function. Phase 1 as a whole is acceptable only when the full test suite's pass/fail counts match the baseline exactly and the `benes_4x4`/`benes_8x8` verification JSON reports match the baseline (timestamps aside). If any slice's validation surfaces a real behavior difference, stop, do not paper over it with a "looks fine" judgment call, and record it as a blocking finding in Surprises & Discoveries before deciding whether to fix the move or fix a pre-existing latent bug the move exposed.

## Idempotence and Recovery

Each slice is one commit. If a slice's validation fails and the cause is not immediately obvious, `git revert` that one commit rather than trying to hand-patch a partially-moved state; the next attempt at the same slice can start clean from the pre-slice commit. Because every slice is a pure code move with no intended logic change, a failed validation almost always means either a missed call site (an import or reference to the old location that was not updated) or an accidental behavior change introduced during the move (for example, a subtly different default argument), both of which are easier to find by reverting and re-reading than by debugging forward from a broken intermediate state.
