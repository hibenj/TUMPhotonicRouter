# Make crossing-aware endpoint correction sound: one checked strategy per port-facing segment, no unchecked fallback cascade

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. This document must be maintained in accordance with `.agent/PLANS.md`, which is checked into this repository at that path and describes the required structure and editing discipline for ExecPlans in general.

## Purpose / Big Picture

This repository, TUMPhotonicRouter, routes optical waveguides for photonic chips on a discrete grid. After the A* search (see `.agent/execplans/2026-08-24-crossing-cost-function-soundness.md` for search-kernel background this plan does not repeat) produces a route as a sequence of grid-aligned "primitives" (short pre-defined path segments), a separate pipeline stage called "endpoint correction" runs afterward to nudge the route's two ends so they land exactly on the real port position and angle, instead of merely close to it (the grid is coarser than the exact sub-micrometer port geometry, so a route built purely from grid-aligned primitives is only approximately aligned with a port until this stage runs). A "net" is one logical point-to-point connection to route, identified by an integer `net_id` and a name like `n_67`. A "crossing" is a point where two different nets' waveguide paths physically cross on the chip, legal only under certain geometric conditions when the router's `enable_crossings` option is on.

Today, endpoint correction for a net that has one or more crossings on its route runs through a long, multi-tier fallback cascade (all in `translation/route_rust_endpoint_correction.py`, primarily inside `_apply_crossing_aware_endpoint_correction_to_record`, starting at line 1088 as of this writing): a first, "checked" tier that treats the port-to-first-crossing and last-crossing-to-port segments independently (much like a crossing-free net's own correction already does), and, only if that does not produce an accepted result, a second, materially weaker tier that computes a single "rich" correction across the *entire* route while ignoring the crossing entirely, then splices the crossing-safe middle section back in -- and that second tier has its own three further fallback levels for each end (the spliced rich correction itself, a second, "guard-window-limited" solver called `_absorbed_terminal_centerline`, and, as an absolute last resort, the route's raw, uncorrected geometry for that end).

This session (2026-08-24, immediately before this plan was written, working through `.agent/execplans/2026-08-24-crossing-cost-function-soundness.md`) found concrete, reproducible evidence that this cascade is not sound: a real bug in the second tier's acceptance check let it silently commit a route whose corrected geometry did not actually touch its own source port (`n_67` in `multiportmmi_8x8`, fixed in commit `2755a22`, but the underlying net is still left unable to route at all -- see Context below); a second net (`n_68`, same benchmark) falls through to the same second tier's weakest, "raw baseline" level for one end, which is a documented, accepted warning rather than an error but is still a materially worse-quality correction than the first tier would have given; a geometric scan found 11 of 111 routed nets in that same benchmark overshoot their own source/target port position by more than 5 micrometers, in a pattern consistent with an uncorrected or under-corrected terminal segment; and the repository owner independently spotted and screenshotted two visible geometry defects in the routed GDS output that plausibly share this same root cause (a bowtie/hourglass-shaped pinch in a route's width where it crosses a component footprint, and a small spurious loop in a route near a cluster of heater components) but that link has not yet been confirmed net-by-net.

The repository owner's own proposed design, stated directly in that session: a net with no crossings already gets one, consistent, checked correction; a net with one or more crossings should treat its port-to-first-crossing and last-crossing-to-port segments the same way -- as two independent, ordinary correction problems, using the exact same checked logic, not a separate, weaker mechanism. The first tier of today's cascade (`_checked_terminal_segment`, inside the same function, using the native `router.centerline_port_corrected_checked` call) already implements close to this design, but it does not fully cover every case today, and this plan's first job is finding out exactly why, with real evidence, before deciding what to change.

After this plan: every crossing-aware endpoint correction either succeeds via one clearly-understood, checked strategy applied uniformly to a net's two terminal segments (matching how a crossing-free net is corrected), or fails with a real, honest, geometrically-explained error -- never by silently accepting a fallback whose own quality was never actually verified against the port it claims to reach. A person can see this working by re-running `multiportmmi_8x8` under both its bare-defaults and stable-baseline (`--crossings true --crossing-mode lidar-pure --fanout-access-mode static-stubs --routing-window-scale 0.35 --foreign-port-keepout-cells 0`) configurations (exact commands in Concrete Steps) and observing that the `endpoint_correction_fallback_used` warning this plan starts from is gone (or replaced by a different, better-understood outcome with a recorded reason), that the geometric overshoot measurement described in Context returns zero or a much smaller, explained count, and that the two screenshotted visual defects are either resolved or conclusively shown to be unrelated to this cascade (with evidence either way, not a guess).

## Surprises & Discoveries

(carried over from the prior session's investigation, recorded here so this plan is self-contained; add new entries below as this plan's own milestones proceed)

- Observation: endpoint correction is not a single pipeline phase. It is invoked from three separately-evolved call sites in `translation/route_rust.py`, all after the *entire* batch of nets has already been routed (never per-net, mid-routing): `_finalize_routing_results` (line 7184 as of this writing, the primary pass, called immediately after `_dispatch_native_routing` finishes routing and repairing every net in `run()`), `_repair_final_illegal_crossings` (line 5640, triggered only for nets touched while repairing an illegal realized crossing, later in the pipeline), and `_repair_final_photonic_issues` (line 6068, triggered only for nets touched while repairing a general photonic-verification issue, later still). A net's final corrected geometry can therefore be the product of up to three separate endpoint-correction invocations at different pipeline stages, against whatever the obstacle/repair state happened to be at each point.
  Evidence: `grep -n "_apply_all_endpoint_corrections_for_net_ids(\|_apply_checked_endpoint_corrections_for_net_ids(\|_apply_checked_fanout_stub_endpoint_corrections_for_net_ids(\|_apply_unrestricted_and_fanout_stub_endpoint_corrections_for_net_ids(" translation/route_rust.py` and matching each call site's line number to its enclosing method.

- Observation: `_classify_net_for_endpoint_correction` (`translation/route_rust.py:4537`) decides, per net, which of three correction paths applies: `UNRESTRICTED` (a crossing-free net, corrected by the native `self.router.apply_checked_endpoint_corrections` call inside `_apply_checked_endpoint_corrections_for_net_ids`, `translation/route_rust.py:4619`), `FANOUT_STUB_*` (a net anchored to a multi-port fanout instance, not otherwise discussed in this plan), or `CROSSING_AWARE` (any net with `self.enable_crossings and net_id in crossing_net_ids`, corrected by `_apply_crossing_aware_endpoint_correction_to_record`, `translation/route_rust_endpoint_correction.py:1088`). This plan is entirely about the `CROSSING_AWARE` path; the `UNRESTRICTED` path is the "already sound, already checked" reference behavior the repository owner's proposed design wants the crossing-aware terminal segments to match.
  Evidence: `translation/route_rust.py:4537-4617`.

- Observation: `_apply_crossing_aware_endpoint_correction_to_record` has a zero-crossing early branch (`translation/route_rust_endpoint_correction.py:1124-1221`) that, for a net classified `CROSSING_AWARE` but whose specific route happens not to have any crossing points on it after all, defers to `apply_port_endpoint_corrections` -- a Python-level function, not the same native call the `UNRESTRICTED` path uses, but conceptually the same "one checked correction over the whole route" shape. The interesting case this plan is about is the non-empty-`crossing_points` branch starting at `translation/route_rust_endpoint_correction.py:1223`.
  Evidence: `translation/route_rust_endpoint_correction.py:1124-1236`.

- Observation: for the non-empty-crossing case, the function first computes a three-way split of the route's raw, as-routed centerline (`baseline`) via `_crossing_endpoint_splice_parts` (`translation/route_rust_endpoint_correction.py:183-264`): a `prefix` (port to just past the first crossing, cut at most 4 length-units into the crossing's protected zone -- see `_guarded_cut`, same file, lines 214-245), a `middle` (the crossing-safe zone itself, always left as raw, uncorrected geometry, never touched by any correction tier), and a `suffix` (just before the last crossing to the target port, same 4-unit guard). If either `prefix` or `suffix` ends up with fewer than 2 points after this cut, `_crossing_endpoint_splice_parts` itself returns `None` for the *entire* split (`translation/route_rust_endpoint_correction.py:262-263`), not just the short side -- meaning tier 1 (below) is skipped entirely for both ends whenever either one is too short, not only the short one.
  Evidence: `translation/route_rust_endpoint_correction.py:183-264`.

- Observation: when the split succeeds, tier 1 (`_checked_terminal_segment`, a nested function at `translation/route_rust_endpoint_correction.py:1266-1334`, called separately for `prefix` at line ~1342 and `suffix` at line ~1351) calls the native `router.centerline_port_corrected_checked`, passing the *segment itself* as the route to correct and the real port plus the crossing-cut point as its two endpoints. This is architecturally the closest thing today's code has to the repository owner's proposed design. If both `_checked_terminal_segment` calls fail (or the initial split failed), or the combined checked candidate does not anchor-match the real ports (`_terminal_anchor_matches`, `translation/route_rust_endpoint_correction.py:668-680`, tolerance approximately 1e-6 units), the function falls through to tier 2.
  Evidence: `translation/route_rust_endpoint_correction.py:1266-1422`.

- Observation: tier 2 (the `_candidate`/`candidate_modes` loop, `translation/route_rust_endpoint_correction.py:1424-1501`) tries up to 4 combinations of `(use_source, use_target)` -- `(True,True)`, `(True,False)`, `(False,True)`, `(False,False)` -- each computing a single, *unchecked* correction over the entire route (`route_port_corrected_centerline`, note the caller's own `allow_unchecked_bumps` parameter name) and splicing it onto the crossing-safe `middle` via `_spliced_crossing_endpoint_centerline` (`translation/route_rust_endpoint_correction.py:682-868`), which has its own further 3-level fallback per end: the spliced rich correction itself, then `_absorbed_terminal_centerline` (a second, independent, "weaker, guard-window-limited" solver, same file lines 439-...), then, if that also fails, the raw uncorrected `baseline_prefix`/`baseline_suffix` unchanged. Until 2026-08-24 (commit `2755a22`), this tier's acceptance check (`_realization_accepts`) verified only that the resulting shape realizes as a valid waveguide polygon -- never that it actually reaches the real port, unlike tier 1's `_terminal_anchor_matches` check. This let a candidate identical to one tier 1 had already correctly rejected be silently accepted.
  Evidence: `translation/route_rust_endpoint_correction.py:1424-1501` (post-fix version, with the `source_ok`/`target_ok` checks added); the pre-fix trace and the fix itself are documented in full in `.agent/execplans/2026-08-24-crossing-cost-function-soundness.md`'s Surprises & Discoveries and the commit `2755a22` message.

- Methodology finding, discovered while re-investigating item 2 and needed for every diagnostic script from here on: `routing_flow_config.py` defines dozens of `SCRIPT_*` module-level constants (`SCRIPT_ENABLE_CROSSINGS = True`, `SCRIPT_CROSSING_MODE = "lidar-pure"`, `SCRIPT_FANOUT_ACCESS_MODE = "legacy-runway"`, `SCRIPT_ROUTING_WINDOW_SCALE = 0.05`, `SCRIPT_FOREIGN_PORT_KEEPOUT_CELLS = 6`, `SCRIPT_MAX_ITERATIONS = 5_000_000`, and about 30 more) that are used as `routing_flow.py`'s own argparse defaults -- meaning bare `routing_flow.py <benchmark>` (no flags) runs with all of these applied. `run_routing_flow()` (`routing_flow.py:769`), the underlying Python function, has its own, different keyword-argument defaults (`enable_crossings: bool = False`, etc.) that apply only when the function is called directly in Python, bypassing the CLI's argument parser entirely. These are two genuinely different configurations that both look like "bare defaults" but are not interchangeable -- a diagnostic script calling `run_routing_flow(benchmark_name)` with no extra keyword arguments silently exercises a different code path than the actual CLI does. A scratch script written this way for `n_67` showed it cleanly classified `UNRESTRICTED` with a valid 146-point corrected centerline and no error at all -- directly contradicting the real, reproducible CLI failure -- purely because of this gap, not because of any real run-to-run nondeterminism. Confirmed and fixed by switching to `routing_flow.main(argv_list)` (`routing_flow.py:597`, accepts an explicit `argv` list and goes through the real argument parser), which reproduces the CLI's actual behavior exactly. Three options, informed by everything above. None is pre-selected; the repository owner's choice, recorded below in the Decision Log once made, is what Milestone 3 implements.

**Option A: remove tier 2 entirely.** Delete the `_candidate`/`candidate_modes` loop and its dependency on `_spliced_crossing_endpoint_centerline`'s 3-level internal fallback (the rich-corrected splice, `_absorbed_terminal_centerline`, and the raw-baseline last resort) from `_apply_crossing_aware_endpoint_correction_to_record`. When tier 1 (the checked, per-segment strategy) does not produce an accepted result for a net's two terminal segments, that net gets a genuine `endpoint_correction_error` -- the same honest-failure behavior `n_67` already has today (post the `crossing-cost-function-soundness` plan's anchor-match fix) -- instead of falling through to an unchecked strategy whose own soundness this plan exists because of. This is the most direct match to the repository owner's own stated principle ("i usually dont want any fallbacks in the code... normal code should handle everything") and their own proposed design (a crossing net's two terminal segments should be corrected the same way a crossing-free net's is, with no separate weaker mechanism). Measured consequence: in `multiportmmi_8x8` stable-baseline, this converts exactly one currently-succeeding-but-degraded net (`n_68`) into a hard failure, and changes nothing for the other 110 nets in that run. The unmeasured risk is whether other benchmarks/configurations have more nets relying on tier 2 than this one does -- Milestone 4 would need to confirm the actual new-failure count stays small before this is considered done, and if it turns out large, that would be new evidence worth returning to the repository owner rather than silently accepting a worse benchmark pass rate.

**Option B: root-cause and fix tier 1's `NoMeanderCandidateSegment` gap first, then reassess tier 2 separately.** Dig into which of the roughly 28 call sites in `src/geometry_realization.rs`/`src/auto_meander.rs` actually produced `n_67`'s prefix-segment failure (Milestone 1's item 1 stopped at "confirmed, specific, not yet pinned to an exact site"), understand whether it represents a genuine geometric impossibility or a fixable gap in the meander-candidate or bump-offset search, and fix it if fixable. This is the option most likely to make currently-unroutable nets (`n_67` in bare-defaults) actually route, not merely fail more honestly -- but it is native Rust geometry code this session has not yet read at all, with real, currently-unknown effort and outcome (the fix might turn out to be a one-line search-range widening, or might reveal the failure is a genuine geometric impossibility with no fix available at this layer at all).

**Option C: do Option A now, and treat Option B as a separate, optional follow-up.** Soundness (never silently accept a candidate that does not reach its port) and routability (make more nets succeed at all) are two different goals -- this plan's own Purpose is about the former. Option C delivers the former immediately, with the measured, small, and well-understood consequence Option A above describes, and leaves the latter (which has a real chance of actually fixing `n_67`, not just failing it honestly) as explicit, recorded future work rather than something this plan is blocked on.

Recommendation, for the repository owner to accept, reject, or amend: **Option C.** The measured risk of Option A alone is small (1 net in the one benchmark checked) and directly satisfies this plan's actual Purpose; Option B's effort and outcome are both currently unknown, and gating Option A's clear, low-risk soundness win on Option B's uncertain, deeper investigation would be over-cautious given the evidence gathered so far.

## Context and Orientation

### Key terms, defined for a reader new to this repository

"Net": one logical point-to-point waveguide connection to be routed, identified by an integer `net_id` and a human-readable name like `n_67`.

"Centerline": the sequence of `(x, y)` coordinate points (in micrometers) tracing the middle of a routed waveguide's path. A `RoutedNetRecord` (defined in `translation/route_rust_types.py`) carries both an uncorrected, grid-derived centerline (reconstructed from the route's primitive sequence via `_primitive_centerline_for_record`) and, after endpoint correction runs, a `corrected_centerline_um` field.

"Endpoint correction": the pipeline stage, entirely in Python (`translation/route_rust_endpoint_correction.py` and its callers in `translation/route_rust.py`), that adjusts a route's centerline near its two ends so they land exactly on the real port position and angle rather than merely the nearest grid-aligned point.

"Crossing": a point where two different nets' waveguide centerlines physically cross on the chip, legal under specific geometric conditions when `enable_crossings` is on. A net can have zero, one, or several crossings along its route.

"Tier" (this plan's own shorthand, not an existing repository term): one of the several distinct correction strategies `_apply_crossing_aware_endpoint_correction_to_record` tries in sequence for a `CROSSING_AWARE`-classified net -- "tier 1" for the checked, per-segment strategy (`_checked_terminal_segment`), "tier 2" for the unchecked, whole-route-then-spliced strategy (the `_candidate`/`candidate_modes` loop), and "tier 2's own three levels" for the further fallback inside `_spliced_crossing_endpoint_centerline` (rich-corrected, then `_absorbed_terminal_centerline`, then raw baseline).
