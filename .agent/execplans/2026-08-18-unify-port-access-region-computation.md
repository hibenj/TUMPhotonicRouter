# Unify port access/keepout region computation into one analytic source of truth

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. This document must be maintained in accordance with `.agent/PLANS.md`, which is checked into this repository at that path and describes the required structure and editing discipline for ExecPlans in general.

## Purpose / Big Picture

This repository (`TUMPhotonicRouter`) routes optical waveguides between component ports on a photonic chip layout. Before routing starts, every port in the design gets a small region of grid cells "opened" around it -- temporarily un-blocked, even though a port normally sits right up against its own component's obstacle clearance -- so a route can actually leave or enter that port instead of being trapped by its own device's geometry. This same region also matters in the opposite direction: when a *different* net is being routed near someone else's port, that port's region should stay blocked (a "keepout"), so nets don't accidentally route through a neighboring, unrelated port's access lane.

Today, the code that decides the size and shape of this region is not one computation -- it is seven independently-parameterized, uncoordinated pieces of logic scattered across two files and two languages (documented in full, with exact citations, in Context and Orientation below). This was discovered while investigating a real routing failure (see `.agent/execplans/2026-08-18-stage5-routing-crossing-correctness-walkthrough.md`, its "candidate Milestone 2"): a one-line fix to widen one of the seven pieces had zero effect on the actual routing outcome, because a *different*, uncoordinated piece of the same overall computation was the real bottleneck. The person who originally wrote this code (this repository's owner) confirmed this arose from debugging individual benchmarks over time and patching in new special-case rules one at a time, without a single place that owns "how big is this port's access region" -- exactly the kind of inconsistency this walkthrough exists to find and remove.

After this plan is complete, there will be exactly one place that answers "what cells does this port's physical access region cover" (a pure geometry computation, given the port's position, orientation, and what *kind* of port it is -- ordinary optical waveguide, electrical/heater pad, or an explicit custom override), and every consumer of that answer (opening cells for the net that owns this port, keeping cells blocked as a keepout for every other net, and the port-opening diagnostics already recorded in `FAILED.txt`) will consume the exact same computation instead of five-to-seven different ones. A person can verify this is working by running the `TOY` benchmark reproduction in Concrete Steps below and observing that the previously-mysterious `gc1_to_mmi_in2` net either routes successfully or fails with a diagnosis that is now traceable to one clear, single piece of sizing logic rather than an intersection of several uncoordinated ones.

## Surprises & Discoveries

- Observation: the fallback single-box sizing can exactly use the current lane-zone dimensions after the uncommitted precursor fix, because the current entry zone is contained in the lane zone for representative non-negative bend radii. The explicit throwaway check used `bend_radius_cells` in `{0, 1, 3, 5}` and `commit_radius_cells` in `{0, 1}`. It produced: `bend=0 commit=0 entry=(2,1) lane=(3,1)`, `bend=0 commit=1 entry=(2,2) lane=(3,2)`, `bend=1 commit=0 entry=(3,2) lane=(4,2)`, `bend=1 commit=1 entry=(3,3) lane=(4,3)`, `bend=3 commit=0 entry=(5,4) lane=(8,4)`, `bend=3 commit=1 entry=(5,5) lane=(8,5)`, `bend=5 commit=0 entry=(7,6) lane=(12,6)`, and `bend=5 commit=1 entry=(7,7) lane=(12,7)`. In every case `entry_length_cells <= port_lane_length_cells` and the entry/lane half-widths were equal.
- Observation: the old base-radius patch does not need to be preserved as an extra minimum for the default routing-flow configuration checked in this milestone. `routing_flow_config.py` defines `SCRIPT_GRID_SIZE_UM = 2.0`, and `translation/route_rust.py` still defaults `port_open_radius_um` to `0.5` when the obstacle config lacks the value. The existing Rust binding computes `port_open_radius_cells = ceil(port_open_radius_um / grid_size_um)`, so the typical value is `ceil(0.5 / 2.0) = 1`, which is already no larger than the new fallback floors of length `3` and half-width `1`.
- Observation: the new private Rust helper intentionally triggers an unused-function warning during `maturin develop --release` because Milestone 1 does not wire it into a PyO3 method or routing call site. The warning is expected for this additive milestone and should disappear when Milestone 2 or 3 introduces a real consumer.
- Observation: the old dense-runway override did not beat an explicit custom port-access rule. In the replaced loop, every port was grouped by a dense runway length when present, but `build_route_port_openings` immediately returned the custom access candidate for `is_custom_access` ports and ignored the grouped runway length, entry length, lane length, and runway cells. The Milestone 2 implementation pass preserved that precedence by applying `dense_port_runway_length_by_spec` only when neither `access_length_um` nor `access_width_um` is present.

The Milestone 2 implementation pass deliberately made `port_access_candidate_cells_by_spec` the raw pre-subtraction unified footprint plus heater extra cells, because that keeps static-overlap diagnostics informative, and made `port_runway_cells_by_spec` the raw unified footprint without heater extra cells, because runway diagnostics and reservation/debug aggregation should describe the physical footprint before the must-stay-blocked subtraction.

## Decision Log

- Decision: split the new design into two composable pieces -- a pure, obstacle-map-agnostic sizing function, and a separate, explicitly-named "subtract must-stay-blocked cells" step applied only by the consumer that actually opens cells for real routing -- rather than one fused function that both sizes and filters.
  Rationale: the two real consumers want different things from the same sizing computation. Opening cells for the net that owns a port wants the sized region *minus* real device material belonging to other components (so it never opens into someone else's obstacle). Building a keepout region for *other* nets near this port wants the sized region *unmodified*, as the full reserved footprint. Fusing the subtraction into the sizing function would force the keepout consumer to either duplicate the sizing logic (recreating today's exact bug) or receive an already-trimmed shape it does not want. A pure sizing function lets both consumers share one implementation and diverge only in whether the must-stay-blocked subtraction is applied afterward.
  Date/Author: 2026-08-18, agreed with the user in conversation before this plan was written.
- Decision: port "kind" (ordinary optical waveguide vs. electrical/heater pad vs. explicit custom override) is a first-class, explicit input to the sizing function, not an external special case layered on afterward.
  Rationale: a heater pad's access requirement (contact-pad-sized clearance) is a genuinely different physical fact from an optical port's requirement (bend-radius-driven waveguide clearance), not an ad hoc patch. Treating it as an explicit, named parameter that selects which sizing rule applies keeps the "one function, one source of truth" property intact, rather than reintroducing a parallel, uncoordinated computation for heater pads the same way `foreign_port_keepout` currently duplicates the optical-port computation.
  Date/Author: 2026-08-18, agreed with the user in conversation before this plan was written.
- Decision: `--foreign-port-keepout-cells` stops being used as an independently-tunable *size* and becomes purely an on/off switch (`self.foreign_port_keepout_cells > 0` still gates whether foreign-keepout logic runs at all, preserving `--foreign-port-keepout-cells 0` as the existing way to disable it) -- keepout size is always identical to whatever the unified sizing computation gives that same port for its own self-opening, with no separate margin.
  Rationale: this was originally left as an open placeholder to investigate during a since-merged Milestone 3, but the merge itself supplies the evidence: a self-opening-only migration attempt caused real, confirmed regressions (7 new failing tests, a newly-broken `multiportmmi_8x8`) specifically because self-opening size and keepout size drifted out of sync with each other. Keeping them forced to always match by construction (same computation, same inputs, reused rather than recomputed) is what prevents that class of bug from recurring, and is a stronger guarantee than "an optional extra margin, remembered to be kept in sync by whoever edits either side in the future." This decision is contingent on Milestone 2 (merged)'s required search of `tests/`/`benchmarks/` for any explicit reliance on independently-tunable keepout size finding nothing -- if that search finds something, this decision must be revisited before implementation proceeds, not silently overridden.
  Date/Author: 2026-08-18, agent authoring this plan, after the merge decision below.
- Decision: merge the former Milestone 2 (self-opening) and Milestone 3 (foreign-keepout) into one milestone, executed and committed as a single change.
  Rationale: a self-opening-only implementation attempt (recorded in Progress) found that the two are not actually independent, sequentially-migratable concerns -- widening self-opening without also updating keepout sizing broke real, previously-passing behavior, because the old keepout logic was implicitly calibrated against the old self-opening size. Migrating them together, using the exact same per-port raw footprint computation for both rather than computing it twice with different inputs, removes the possibility of that drift by construction rather than by discipline. The user was consulted and explicitly approved this merge before it was made.
  Date/Author: 2026-08-18, decided with the user in conversation, after the self-opening-only attempt's regression was found and independently confirmed.
- Decision: `_RouteNetsRustSession._resolve_port_footprint_cells` returns integer grid-cell counts, not micrometer values.
  Rationale: the surrounding Python session already stores `bend_radius_cells`, `commit_radius_cells`, `port_entry_length_cells`, `port_lane_length_cells`, and the lane half-width as resolved cell counts. Returning cells keeps this resolver consistent with those attributes and avoids a second representation inside the Python routing session. The only duplicated unit conversion is for explicit custom per-port access rules, and it deliberately matches the existing Rust branch in `route_port_access_cells`: length is `ceil(access_length_um / grid_size_um)` with a minimum of `1`, and half-width is `ceil((access_width_um / 2.0) / grid_size_um)` with a minimum of `0`.
  Date/Author: 2026-08-18 16:35Z, Codex implementation engineer.
- Decision: in the first Milestone 2 implementation pass, keep `port_access_candidate_cells_by_spec` as the raw unified footprint before must-stay-blocked subtraction, and keep `port_runway_cells_by_spec` as the same raw unified footprint without heater-pad extra cells.
  Rationale: the candidate field is useful precisely when it can show how much of the raw intended port footprint touched static or dynamic geometry before filtering. The runway field is used by diagnostics and reservation/debug aggregation, so the raw footprint is more informative than making it identical to the filtered opened-cell set. This choice still needs review because the focused validation shows the broader raw footprint currently composes poorly with foreign keepout and sibling-port tests.
  Date/Author: 2026-08-18, Codex implementation engineer.
- Decision: preserve the old custom-access-versus-dense-runway precedence by letting explicit custom access rules win over dense-runway length overrides.
  Rationale: the old grouped call site computed dense runway groups for all ports, but the Rust `is_custom_access` branch returned the custom candidate immediately and did not use the grouped runway length. Applying dense length on top of a custom access rule would be a behavior change beyond this migration.
  Date/Author: 2026-08-18, Codex implementation engineer.

## Context and Orientation

Read this section fully before starting Milestone 1; it defines every term of art this plan uses, names every piece of the current scattered logic with exact citations, and orients you to the relevant files. Do not start editing code based on a partial read of this section -- the whole point of this plan is that the current logic is spread across more pieces than are obvious at first glance, and missing one of them while "consolidating" would just add an eighth uncoordinated rule instead of removing the problem.

The repository root is `/home/benjamin/Documents/Repositories/working/TUMPhotonicRouter`. The active git branch is `crossings/verification-foundation`. A "grid cell" is an `(x, y)` integer tuple; the routing grid discretizes physical micrometer space into cells of a fixed size (`grid_size_um`). A "port" is a named connection point on a placed component (for example `gc_1,o1` or `mmi_0,o1`, written as `<instance_name>,<port_name>`) with a physical position in micrometers and an orientation in degrees (which way it points, e.g. `0` for east). "Opening" a cell means removing it from the set of cells the router treats as blocked, so a route can pass through it; a "keepout" is the opposite -- a cell that stays blocked specifically to prevent routes from passing through it, even though nothing physically occupies it.

### The seven pieces of the current scattered logic

All of the following were read in full during the investigation that led to this plan (recorded in `.agent/execplans/2026-08-18-stage5-routing-crossing-correctness-walkthrough.md`); this section restates the essential facts so this plan is self-contained, per `.agent/PLANS.md`'s requirement, but does not repeat every detail of that investigation's narrative -- read that plan's relevant Progress entries if you want the full story of how each piece was found.

1. `route_port_access_cells` in `src/py_router.rs` (starts at line 1109). Computes a "candidate" region as two separate, independently-parameterized directional boxes glued together -- a short "entry" zone (`port_entry_length_cells`, `port_entry_half_width_cells`) and a longer "lane" zone (`port_lane_length_cells`, `port_lane_half_width_cells`) -- built using the shared primitive `route_collect_inflated_step_cells` (line 1055, which walks `length_cells` steps forward from the port's base cell along its orientation, and at each step widens by `half_width_cells` in every direction, excluding cells behind the starting point). *Or*, if the caller supplies an explicit `access_length_um`/`access_width_um` override (used for custom per-port access rules, resolved in Python by `_keyed_port_access_rule` at `translation/route_rust.py`, search for that function name), this whole two-box computation is replaced by one box sized directly from that override -- this "custom override" branch already has the shape this plan wants to make the *only* shape, see Plan of Work.
2. `route_base_port_open_cells` in `src/py_router.rs` (line 1169). A small, non-directional (symmetric in every direction, no orientation dependence) patch of cells right at the port's exact physical coordinate, sized by `port_open_radius_cells` (derived from `port_open_radius_um`, which defaults to `0.5`, i.e. well under one grid cell at typical grid resolutions). Entirely independent of bend radius.
3. `route_port_runway_cells` in `src/py_router.rs` (line 1179). A second directional box, shaped like piece 1 but built with its own independently-computed length/width: in the caller (`build_route_port_openings`, piece 5 below), `runway_length_cells = bend_radius_cells.max(0) + 1` and `runway_half_width_cells = commit_radius_cells.max(0)` -- note this uses the raw `bend_radius_cells`/`commit_radius_cells` parameters passed into the Rust binding directly, *not* the `port_lane_half_width_cells` value the Python side computes and also passes in. `commit_radius_cells` is a different concept entirely from bend radius: `self.commit_radius_cells = self.clearance_policy.dynamic_route_commit_keepout_radius_cells` (`translation/route_rust.py:6175`) controls how much buffer to leave around *other nets' already-committed routes*, not how much physical space this port's own route needs. In the common case `commit_radius_cells` is `0`, so this runway is permanently pinned to its minimum width regardless of bend radius -- this is the piece that turned out to be the actual, undefeated bottleneck when Milestone 2 of the Stage 5 plan tried widening piece 1 alone and observed zero change in the real opened-cell count.
4. `route_port_endpoint_bump_candidate_cells` in `src/py_router.rs` (line 1205). An L-shaped region (a short region directly behind the port, plus wide lateral spreads on each side, reaching `bend_radius_cells` sideways) that feeds only into the *diagnostic* candidate-cell report (`port_access_candidate_cells_by_spec` in Python), not into the actual cells used for real routing legality. Out of scope for this plan's core fix (it does not affect routing correctness), but worth knowing about so it is not mistaken for a live consumer of the sizing logic being unified.
5. The combination formula in `build_route_port_openings` (the `#[pymethods]` PyO3-bound function in `src/py_router.rs`, starts at line 8360). This is where pieces 1-3 actually get combined into the final `effective_cells` (the first element of its returned tuple, which Python assigns directly to `self.port_access_cells_by_spec[port_spec]` at `translation/route_rust.py:6521`-`6523`, the cells that actually determine what real routing treats as open for this port). The combination is *itself* a sixth independently-tunable rule: if `route_clearance_um <= 0.0` (the waveguide clearance setting, a different concept from bend radius, defaulting to `0.0` in the CLI), `effective_cells = (candidate_cells ∩ base_open_cells) ∪ runway_open_cells`; otherwise it is `(candidate_cells \ raw_static) ∪ (candidate_cells ∩ base_open_cells) ∪ runway_open_cells`. In the `<= 0.0` case (the default, and the case exercised by every reproduction used to find this bug), the wide `candidate_cells` region from piece 1 gets *intersected down* to the tiny `base_open_cells` patch from piece 2 before it can contribute anything at all -- this is why widening piece 1's width parameters, as this plan's precursor fix did, had no effect on the final result.
6. `foreign_port_keepout_cells_by_spec`, built in Python at `translation/route_rust.py:6539`-`6567` (inside the `if self.foreign_port_keepout_cells > 0:` block). This is a *second, wholly separate call* to the exact same `build_route_port_openings` Rust function, but with its own independent sizing: `foreign_length_cells = foreign_half_width_cells = int(self.foreign_port_keepout_cells)` (a CLI-tunable value, `--foreign-port-keepout-cells`, defaulting to `6`, entirely unrelated to bend radius or the port_entry/lane values used by piece 1). Only the raw `runway_cells` (the fourth tuple element, unfiltered) is kept from this call, used to mark cells that should stay blocked for every net *except* the one that owns this specific port.
7. Heater-pad-specific extra opened cells, from `self._heater_pad_port_open_cells(...)` (`translation/route_rust.py:6461`), stored per-port in `port_rule_extra_open_cells_by_spec` and unioned into the final `port_access_cells_by_spec` after the main Rust call (`translation/route_rust.py:6527`-`6530`). This is scoped to electrical/heater ports specifically (out of scope for the optical-port bug that motivated this plan, and out of scope for path-length matching / electrical routing generally, which the user has separately deferred), but it is architecturally the same pattern -- a special case bolted on as an external addition rather than expressed as a legitimate input to one sizing computation. Milestone 1 should design the new `kind` parameter (see Plan of Work) so this can eventually become a first-class `ElectricalPad` variant instead of an external union, but *implementing* that migration for heater pads specifically is optional/deferred scope for this plan -- the required scope is unifying the optical-port path (pieces 1-6) and `foreign_port_keepout` (piece 6/piece 6-duplicate).

### Why this matters beyond the one `TOY` bug

The Stage 5 plan's Milestone 1 (see `.agent/execplans/2026-08-18-stage5-routing-crossing-correctness-walkthrough.md`) found that `TOY`'s `gc1_to_mmi_in2` net cannot route because its target port, `mmi_0,o1`, has no legal approach once real clearance is required -- and that a targeted one-line fix (making `port_lane_half_width_cells` scale with bend radius, mirroring `port_entry_half_width_cells`'s already-correct formula) did not fix it, because the actual final opened-cell computation (piece 5 above) does not meaningfully use that value in the common case. That fix is real (the formula genuinely was inconsistent) but insufficient, and remains uncommitted pending this plan; Milestone 2 below should decide whether to fold it into the new unified computation or discard it as superseded. Beyond this one benchmark, the same seven-piece inconsistency affects the opened-cell sizing for every port in every benchmark on this branch, since `build_route_port_openings` and `foreign_port_keepout` are called for every port in every routing session -- any benchmark whose ports sit close enough together to depend on getting the *right* amount of clearance (not too little, which causes exactly this kind of unroutable-port failure, and not too much, which could cause unwanted overlaps or crossings) is exposed to whichever of the seven pieces happens to dominate for its specific geometry, unpredictably.

### Milestone 1: add the new unified sizing computation, additive only

Goal: implement the new "one function, one source of truth" sizing computation in both Rust and Python, as new code nothing calls yet. This milestone must not change any observable behavior -- it only adds new functions and new tests for them.

In `src/py_router.rs`, add a new function (name it clearly, for example `route_port_footprint_cells`, distinct from the existing `route_port_access_cells`/`route_base_port_open_cells`/`route_port_runway_cells` so nothing accidentally shadows the old names during the transition) that takes exactly: the port's `x_um`, `y_um`, `orientation`, and a single resolved `(length_cells, half_width_cells)` pair (plain integers -- resolving *which* length/width applies for a given port's kind is a Python-side responsibility, described next, not something this Rust function decides). If, while implementing, you find a real reason the base-radius patch (piece 2) needs to be preserved as a *minimum* size rather than fully retired (for example, if some port's resolved `length_cells`/`half_width_cells` could legitimately come out smaller than what is needed to keep the port's own exact coordinate open), fold that in as an explicit `.max(...)` floor inside this one function with a clear comment explaining why, rather than reintroducing it as a separate computation -- but do not assume this is needed without checking; investigate first (see Surprises & Discoveries, record what you find).

### Milestone 2 (merged): migrate self-opening and foreign-keepout together

Goal: replace the old entry/lane/base-radius/runway/`effective_cells` computation (pieces 1, 2, 3, 5 in Context and Orientation) *and* the separate `foreign_port_keepout_cells_by_spec` computation (piece 6) with the new unified computation from Milestone 1, in one change, so self-opening and keepout are never mutually inconsistent even transiently. This is the milestone expected to change real routing behavior and carries real regression risk -- see the finding recorded in Progress above about why the two were merged: a self-opening-only precursor attempt caused real, confirmed regressions (7 new failing tests, all foreign-keepout/sibling-port territory, plus a newly-broken `multiportmmi_8x8`) because the old foreign-keepout sizing was calibrated against the old self-opening size, and widening one without the other broke that implicit calibration.

The precursor attempt's self-opening half is a good starting point and should be reused, not redone from scratch (its design was independently verified as correct in isolation): in the main port-opening loop (`translation/route_rust.py`, search for `port_opening_inputs` and the loop that follows it, around where the old `build_route_port_openings` call used to be at roughly line 6497 before the precursor attempt's edits), resolve each port's `(length_cells, half_width_cells)` via the Milestone-1 `_resolve_port_footprint_cells`, apply the dense-port-runway-length override (`dense_port_runway_length_by_spec`, a per-port **length-only** override for MMI-fanout staggering that the ExecPlan's original "seven pieces" enumeration missed -- read `_dense_source_port_runway_lengths`/`_dense_target_port_runway_lengths`, `translation/route_rust.py:2188` and `:2299`, in full before touching this) only when no custom access rule is present (custom access rules win; this precedence was verified against the old code and is correct, keep it), batch all ports into one call to a new PyO3-bound Rust method wrapping Milestone 1's `route_port_footprint_cells` (a `build_port_footprint_cells(ports) -> Vec<(String, Vec<(i32,i32)>)>` method returning the raw, unfiltered footprint per port is the right shape), then compute `open_cells = raw_footprint_cells - self._cells_in_raw_static_geometry(raw_footprint_cells)` per port (the one explicit must-stay-blocked subtraction step, reusing the existing Python method, not new Rust filtering) for `self.port_access_cells_by_spec`, preserving the existing heater-pad `extra_open_cells` union afterward unchanged.

The genuinely new work for this merged milestone is the keepout half, and it should reuse the *exact same raw per-port footprints* computed above, not call the Rust batch method a second time with different sizing: set `self.foreign_port_keepout_cells_by_spec[port_spec] = raw_footprint_cells` (the same unfiltered footprint each port already got for its own opening -- a keepout region should represent the full reserved footprint, not a trimmed one, since it exists to say "nothing else may enter here," matching the Decision Log entry above about splitting sizing from must-stay-blocked filtering).
