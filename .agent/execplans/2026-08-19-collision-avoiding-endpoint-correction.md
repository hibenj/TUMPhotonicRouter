# Make endpoint correction collision-avoiding, not just collision-rejecting

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. This document must be maintained in accordance with `.agent/PLANS.md`, which is checked into this repository at that path and describes the required structure and editing discipline for ExecPlans in general.

## Purpose / Big Picture

This repository (`TUMPhotonicRouter`) routes optical waveguides on a discrete grid, then "corrects" the very start and end of each route so its centerline lands exactly on the real, physical port it connects to. A prior plan, `.agent/execplans/2026-08-19-restructure-port-endpoint-correction.md` (now complete), fixed a real, confirmed bug where this correction step could silently accept a candidate that physically overlapped a different net's already-routed waveguide -- two different optical signals occupying the same physical space, which is not buildable hardware. That fix made the checked corrector correctly *reject* an unsafe candidate instead of silently accepting it. Reject is safer than silent-accept, but it is not the same as *succeeding*: on the real benchmark that surfaced this bug (`multiportmmi_16x16`, under its documented "stable crossing-router baseline" configuration), exactly two nets -- `n_196` and `n_203` -- now cleanly fail to connect to their target port at all (`target_port_not_connected`) instead of silently colliding, because the correction mechanism that was rejected has no alternative to fall back to.

After this plan is complete, `n_196`, `n_203`, and any other net with the same shape of problem should route successfully -- their corrected centerline should reach their real port *and* not physically overlap any other net's waveguide. A person can see this working by running `multiportmmi_16x16` under its documented stable-baseline configuration (the exact command is in Concrete Steps below) and reading `build/verification/multiportmmi_16x16_photonic_verification.json` directly: today it reports `success: false` with `n_196`/`n_203` failing as `endpoint_correction_error`/`missing_corrected_centerline`/`target_port_not_connected`; after this plan, it should report `success: true` with those two nets fully connected and no `cross_net_waveguide_overlap` regression.

## Decision Log

- Decision: give `try_apply_45_degree_endpoint_delta_correction` an optional `collision_check: Option<&dyn Fn(&[(f64, f64)]) -> bool>` parameter and a new `route_to_port_corrected_centerline_with_options_and_collision_check` sibling entry point, rather than threading a full `&ObstacleMap` reference through the whole `geometry_realization.rs` call chain or rather than building new candidate-generation logic for a different strategy.
  Rationale: Milestone 1's tracing found the actual responsible strategy already has a working multi-candidate structure (`axis_only`, then every `(source_adjustment, target_adjustment)` pair), so the smallest correct fix is making its existing acceptance points collision-aware, not building new search logic.   Date/Author: 2026-08-19, Claude, recorded here.
- Decision: the real collision-check closure built inside `route_port_corrected_centerline_checked_and_commit_native` checks only dynamic other-net ownership (`self.obstacle_map.dynamic_owners_at`, excluding `net_id` itself), not static obstacles or clearance/halo cells.
  Rationale: the confirmed bug (`n_196`/`n_203`) was specifically a dynamic cross-net collision; the function's own existing post-construction check (unchanged by this plan, still runs as a backstop) already covers static/out-of-bounds/clearance cases for whatever the strategy ultimately returns. Scoping the new in-search check to exactly the failure mode that was actually observed keeps the change minimal and avoids duplicating logic that already exists and already works.

### What "endpoint correction" means, and the two-layer mechanism relevant here

The router finds paths on a discrete grid (`grid_size_um` micrometers per cell). A port's real, physical connection point is an arbitrary `(x, y)` coordinate in micrometers, essentially never exactly on a grid cell boundary. "Endpoint correction" adjusts the very start and end of a routed net's centerline so it lands exactly on the real port.

For a net that is not involved in an optical crossing (the case this plan is about -- `n_196`/`n_203` are confirmed, via `build/verification/multiportmmi_16x16_crossing_verification.json`'s `crossings` list, to have zero crossing events), correction happens in `src/py_router.rs`'s `route_port_corrected_centerline_checked_and_commit_native` (line 6852 as of this writing). That function first asks `full_straight_offset_bump_candidates_rs` for a list of candidate "bump" placements, which only exist when the route's baseline centerline is fully straight or fully vertical; if there are candidates, each is validated strictly against the obstacle map (`commit_route_with_clearance_overlap`, `src/obstacle_map.rs` line 397, which never allows overlap with another net) and the first one that passes is used -- this path already avoids collisions correctly, by trying alternatives until one works.

`n_196`/`n_203` are not fully-straight routes, so `full_straight_offset_bump_candidates_rs` returns an empty list for them, and control falls into the other branch (`candidates.is_empty()`, starting at line 6885). That branch calls `route_to_port_corrected_centerline_with_options_rs` (`src/geometry_realization.rs`, `route_to_port_corrected_centerline_with_options`, line 1094) exactly once to construct a single candidate corrected centerline, then checks that one candidate's cells against the obstacle map (as of the prior plan's fix, using the strict `commit_route_with_clearance_overlap`, which correctly rejects any collision with another net's committed geometry). If that single candidate collides, the whole correction fails -- there is no second attempt, because `route_to_port_corrected_centerline_with_options` itself only ever produces one answer per call.

`route_to_port_corrected_centerline_with_options` is a strategy chain, tried in this order, first one that succeeds wins (all in `src/geometry_realization.rs`): `try_apply_full_straight_port_correction` (line 1515) -> `try_apply_full_diagonal_straight_port_correction` (line 1555) -> `try_apply_shared_axis_port_shift` (line 1479) -> `try_apply_45_degree_endpoint_delta_correction` (an intermediate strategy not otherwise named in this plan) -> `absorb_endpoint_delta_into_existing_axis_runs` (line 1945, adjusts the length of an existing off-axis segment already in the route) -> if `allow_unchecked_bumps` is true (it is, for this call site: pass 1/pass 2 always call with `allow_unchecked_fallback=true`) -> `try_apply_full_straight_offset_bump_correction` (line 1597, a *different* bump mechanism than the case-4 candidates above, used only when the centerline degenerates to straight/vertical at this point) -> if that also fails -> `absorb_endpoint_delta_into_axis_runs` (line 1900, the final fallback, which itself tries "dogleg absorption" -- reusing slack already present in the route's own primitive structure, `insert_source_delta_dogleg`/`insert_target_delta_dogleg`, lines 2735/2774 -- before falling to `insert_source_delta_bump`/`insert_target_delta_bump`, lines 2953/2989, which construct genuinely new detour geometry).

None of these strategies take an `&ObstacleMap` parameter or any other awareness of other nets' geometry (confirmed directly by reading every one of their signatures during the prior plan's Milestone 0.5 investigation -- see that plan's Surprises & Discoveries, 2026-08-19 entries, for the full confirmation trail). Two of them -- `build_ordered_compact_offset_bump` (line 1675, used by `try_apply_full_straight_offset_bump_correction`) and `insert_source_delta_bump`/`insert_target_delta_bump` via `first_viable_delta_bump_run` -- already have an internal "try several candidate placements, use the first that is geometrically valid" structure, for purely geometric reasons (finding a placement that does not overlap the route's *own* other geometry or go out of primitive-library bounds). Neither the dogleg-absorption mechanism nor `absorb_endpoint_delta_into_existing_axis_runs` has any such multi-candidate structure; each produces exactly one deterministic answer.

**What is not yet known, and must be determined before designing the fix**: which specific strategy in this chain actually produced the collision for `n_196`/`n_203`. Milestone 0.5's investigation confirmed the *mechanism class* (a strategy without obstacle awareness) but did not need to identify the *specific* strategy, because its fix (making the caller-side check strict) worked regardless of which strategy ran. This plan's fix does need to know, because the right place to add obstacle-awareness differs depending on whether the winning strategy already has a multi-candidate loop to extend (the two bump mechanisms) or has no such structure at all (`absorb_endpoint_delta_into_existing_axis_runs`, dogleg absorption) and would need one built.

### Milestone 2: design the fix for the identified strategy

Once the exact strategy is known, the fix shape depends on which one it is:

If it is `try_apply_full_straight_offset_bump_correction`/`build_ordered_compact_offset_bump`, or the final-fallback `insert_source_delta_bump`/`insert_target_delta_bump`: these already try multiple candidate placements for geometric reasons. Thread an obstacle-awareness check into their existing candidate loop as one more acceptance condition, so a colliding candidate is skipped and the next geometric candidate is tried, the same "try several candidates, use the first that validates" shape `build_ordered_compact_offset_bump` (line 1675) and `first_viable_delta_bump_run` already have, just with collision added to what "validates" means. This needs either an `&ObstacleMap` reference or an equivalent, cheaper-to-check cell-membership query threaded down through the call chain from `route_port_corrected_centerline_checked_and_commit_native` (which already has `&self.obstacle_map`) through `route_to_port_corrected_centerline_with_options` and into the specific strategy function -- read how `DenseOccupancyPrefix::from_obstacle_map` (`src/geometry_realization.rs` line 120) is already used elsewhere in this same file for exactly this kind of query before inventing a new representation.

If it is `absorb_endpoint_delta_into_existing_axis_runs` or the dogleg-absorption mechanism: neither has a multi-candidate structure today. Decide during implementation, after reading each function's actual body fresh (not assumed from this plan's summary), whether the right fix is (a) giving it real alternative candidates to try (for example, if there is more than one existing off-axis run the delta could be absorbed into, try each), or (b) falling through to the next strategy in the chain when the chosen candidate collides, rather than accepting it unconditionally. Prefer whichever preserves the existing chain's overall philosophy (try increasingly invasive strategies in order, stop at the first success) rather than inventing a new control-flow shape.

Whichever strategy is responsible, do not change `route_port_corrected_centerline_checked_and_commit_native`'s own caller-side check (the strict `commit_route_with_clearance_overlap` from the prior plan's Milestone 0.5 fix) -- that check should remain as a correctness backstop even after the strategy itself gains collision-awareness, matching this repository's `.agent/WORKFLOW.md` guidance that post-construction verification is a safety net for gaps, not a replacement for avoiding the problem at the source.

### Milestone 3: implement, with a focused regression test

Implement the fix identified in Milestone 2. Add a focused Rust unit test reproducing the exact collision shape (two committed nets, a correction candidate for one that would land on the other's cells at the specific strategy identified in Milestone 1, asserting the corrected candidate now lands somewhere collision-free instead of either colliding or failing outright) -- follow the pattern already established in `tests/test_port_alignment_diagnostics.py::test_checked_no_bump_endpoint_correction_rejects_other_net_dynamic_overlap` (added by the prior plan) for how to set up a minimal two-net collision scenario via direct Rust-binding calls, adapting it to assert success-with-different-placement instead of rejection.
