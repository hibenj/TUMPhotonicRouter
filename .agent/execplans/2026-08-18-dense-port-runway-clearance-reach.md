# Equalize dense-port runway reach so siblings cannot self-block

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. This document must be maintained in accordance with `.agent/PLANS.md`, which is checked into this repository at that path and describes the required structure and editing discipline for ExecPlans in general.

## Purpose / Big Picture

This repository (`TUMPhotonicRouter`) routes optical waveguides between component ports on a photonic chip layout. Some components (for example a "multiport" MMI, a device with many optical ports packed closely together on one face) have several ports spaced only a few grid cells apart. When many nets need to leave or enter ports on the same crowded face, the router narrows each port's own access lane so neighboring ports do not fight over the same cells; this narrowing already exists and is not being changed by this plan. This plan fixes a separate, previously undiscovered problem: a port's raw (un-narrowed) reservation is shared globally as "keep this blocked for every other net," and if two sibling ports on the same crowded face are given different forward reaches (an existing mechanism, "staggering," meant only to avoid two neighbors overlapping), the *longer*-reaching sibling's wide raw reservation can seal the *shorter*-reaching sibling in behind it -- even though nothing physically stands in the way. The router then reports "No route found" for every net that needs the shorter-reaching port, even though there is nothing physically wrong with that port, and even though giving it the same reach as its longest sibling would let it escape.

After this plan is complete, every port in such a group gets the same forward reach as whichever port in that group already reaches furthest -- removing the self-inflicted gap without needing to lengthen anything beyond what some sibling already legitimately reserves. A person can see this working by running the `multiportmmi_8x8` benchmark (see Concrete Steps below): before this plan, it fails immediately with `RuntimeError: No route found for n_24: mmi0_ps_array_0_heater_1,o2 -> mmi0_multiport_0_0,o2`, and never gets any further; after this plan, that specific net routes successfully, and the whole 111-net benchmark's routing stage completes (a later, unrelated stage -- photonic geometry verification -- can still fail for other, separately-diagnosed reasons on a small number of nets; this plan does not promise a fully clean benchmark end to end, only that this specific, already-diagnosed cause is gone).

## Context and Orientation

This section assumes no knowledge of any prior conversation or prior ExecPlan. Every fact needed to understand and execute this plan is repeated here.

### The grid and "cells"

The router works on a discrete grid: the whole chip layout is divided into square cells, each `grid_size_um` micrometers wide (a benchmark-specific number; for the `multiportmmi_8x8` benchmark used throughout this plan, `grid_size_um = 2.0`). A "cell" is identified by its integer `(x, y)` grid coordinates. A cell can be "blocked" (the router will never route through it) or "open"/"unblocked" (available for routing, unless something else blocks it dynamically, such as another net's already-committed route).

### Ports, their "access region", and why it needs opening

Every net the router places connects two "ports" -- named connection points on component instances, each with a physical `(x, y)` position in micrometers and a facing direction ("orientation", one of 8 compass-like directions at 45-degree increments). A component's own solid body is itself blocked (the router must never route through real device material), which means a port sitting right at the edge of its own component would be permanently trapped unless some of the cells right around it are deliberately un-blocked ("opened") specifically so a route can leave or enter that port. This repository already has exactly one place that computes the shape of that opened region for an ordinary port: the Python method `_RouteNetsRustSession._resolve_port_footprint_cells` in `translation/route_rust.py` (around line 1210), which returns a `(length_cells, half_width_cells)` pair, and the Rust function `route_port_footprint_cells` in `src/py_router.rs` (around line 1169), which turns that pair into the actual set of `(x, y)` cells. This single-source-of-truth design (one function decides the size, used by both the port's own opening and by keeping the region blocked for every *other* net -- "foreign keepout") was itself the outcome of a prior, now-complete ExecPlan, `.agent/execplans/2026-08-18-unify-port-access-region-computation.md`; that plan's own history is not needed to follow this one, but its result -- this one sizing function -- is the foundation this plan builds on and must not bypass.

The exact geometry `route_port_footprint_cells` produces (read directly from `src/py_router.rs`, functions `route_port_state_cell`, `route_angle_to_step`, and `route_collect_inflated_step_cells`, lines 1033-1092) is: first, compute a "base cell" `(base_x, base_y)`, which is the port's physical center shifted one grid cell further in its own facing direction (so the base cell is just outside the port, not on top of it). Then, for `step_idx` from `0` up to `length_cells - 1`, take the cell `(base_x + step_x * step_idx, base_y + step_y * step_idx)` (where `(step_x, step_y)` is the unit step in the port's facing direction -- for example `(-1, 0)` for a port facing due "west" / left) as the center of a square of side `2 * half_width_cells + 1`, and union all `length_cells` of these overlapping squares together, discarding any resulting cell that lies *behind* the base cell (opposite the facing direction). Worked through algebraically, the *total* forward reach of the resulting shape -- the distance in cells from the base cell to the furthest cell included, along the facing direction -- is exactly `length_cells + half_width_cells - 1`, because the last square (centered `length_cells - 1` steps out) itself extends another `half_width_cells` further out in every direction, including forward. This formula was verified empirically during this plan's investigation and is essential to understanding why sibling ports with different `length_cells` values, but the *same* `half_width_cells` (staggering only ever changes length, never width), end up with reservations that reach different distances but are always exactly as wide.

### Ports, own footprints, and global reservations

Two facts about how a port's footprint is used, both already true before this plan and unchanged by it, are essential to understanding the bug this plan fixes:

First, a port's own raw footprint (the shape described above, before any narrowing) is stored per port spec in `self.port_runway_cells_by_spec` (`translation/route_rust.py`, inside `_RouteNetsRustSession.run()`), and the union of *every* port's own raw footprint across the whole design is folded into `self.static_blocked_cells_before_port_reservations` -- the set of cells the router treats as blocked, for the purposes of any net that is not that specific port's own net, unless that other net has an explicit exemption. This union happens at `translation/route_rust.py` line 6757 in the current code (`self.static_blocked_cells_before_port_reservations = set(self.raw_static_cells)`, followed immediately by three `.update(...)` calls that add in `port_runway_static_cells`, `foreign_port_keepout_static_cells`, and `fanout_stub_static_cells` -- `port_runway_static_cells` itself being the union of every entry in `port_runway_cells_by_spec`). This is a deliberate, pre-existing, and correct design: it is what stops one net from accidentally routing straight through space that is meant to be another port's own access lane.

Second, some components place several ports very close together on the same face -- for example, in the `multiportmmi_8x8` benchmark, the component `mmi0_multiport_0_0` has (among others) six ports (`o1` through `o6`) on one face, spaced only 5 micrometers apart (2.5 grid cells at this benchmark's `grid_size_um = 2.0`). The generic, non-dense-aware `half_width_cells` used by `_resolve_port_footprint_cells`'s fallback path is `max(1, bend_radius_cells + commit_radius_cells + 1)`; for this benchmark, `bend_radius_cells = 3` and `commit_radius_cells = 0`, giving `half_width_cells = 4`, i.e. each port's raw, un-narrowed footprint is 9 grid cells wide (`2 * 4 + 1`). Six neighboring ports, each 9 cells wide but only 2.5 cells apart, obviously produce heavily overlapping raw footprints.

Two *separate*, pre-existing mechanisms already try to manage this overlap, and this plan does not change either of them -- it adds a small correction that neither of them currently makes:

1. Length staggering (`_dense_target_port_runway_lengths` for target ports, `_dense_source_port_runway_lengths` for source ports, both in `translation/route_rust.py`): for any qualifying group of densely-packed ports on the same component instance and facing the same direction ("angle"), these functions assign each port a *different* `length_cells` value, so that not every port's raw footprint extends exactly as far forward as its neighbors'. For `_dense_target_port_runway_lengths`, the formula is `base_cells + spacing_cells * rank`, where `base_cells = max(1, bend_radius_cells + 1)` (4 for this benchmark), `spacing_cells` defaults to 3 (via the environment variable `PHOTONIC_ROUTER_TARGET_PROTECTED_LANE_SPACING_CELLS` or its fallbacks), and `rank` depends on the port's lateral position within the group (ports are split into a "lower" half and an "upper" half, and rank counts outward from the middle of each half, so the group's two most-central ports get the *longest* reach and the two most-outward ports get the *shortest*). For the six `mmi0_multiport_0_0` target ports, before this plan's fix this produced lengths `o1=4, o2=7, o3=10, o4=10, o5=7, o6=4`. The source-side function (`_dense_source_port_runway_lengths`) has a similar shape but two separate branches depending on `self.fanout_access_mode_normalized` (a `static-stubs` branch and a `legacy-runway` branch); this repository's benchmarks default to `legacy-runway`, set by `SCRIPT_FANOUT_ACCESS_MODE = "legacy-runway"` in `routing_flow_config.py`, line 36. Either function's result feeds into the main port-opening loop in `_RouteNetsRustSession.run()`: `custom_runway_length = dense_port_runway_length_by_spec.get(port_spec); if custom_runway_length is not None and not custom_access: length_cells = max(1, int(custom_runway_length))` -- this *replaces* the generic fallback `length_cells` with the staggered one, but leaves `half_width_cells` at its generic value, unchanged, for every port in the group.

2. Lateral narrowing (`_filter_dense_port_opening`, `translation/route_rust.py` around line 2359, and the group/window construction that feeds it, inside `run()`): after every port's raw footprint has been computed, for any instance with more than 2 endpoint ports, each port's *own* claimed lateral region is narrowed down to only the cells nearest to it (by lateral position, i.e. position measured perpendicular to the port's facing direction) compared to its immediate neighbors. This is what actually turns each port's raw 9-cells-wide lane into a much narrower one matching the real ~2.5-cell pitch between neighbors, and it is applied both when computing what to keep blocked for *other* nets ("foreign keepout") and when computing what a port's own net gets to use for its own routing (both paths call the shared helper `_opened_cells_for_spec`, which calls `_filter_dense_port_opening`).

### The bug this plan fixes: staggering and global reservation interact badly

Length staggering (mechanism 1) intentionally gives different ports in the same group different forward reaches. But every port's *raw*, un-narrowed footprint -- not its narrowed lane -- is what gets folded into the global `static_blocked_cells_before_port_reservations` (as described above). A longer-reaching sibling's raw footprint is still the *full width* (9 rows for this benchmark, since staggering never changes `half_width_cells`), so it extends laterally across every other sibling's row range too, not just its own. This means a longer-reaching sibling's own reservation can extend past a shorter-reaching neighbor's own reach, into space the shorter neighbor's own footprint never claimed for itself -- and since the shorter neighbor's own net gets no exemption for a *different* port's reservation, that gap stays blocked from its perspective, even though nothing physically occupies it.

This is exactly what was found for `mmi0_multiport_0_0`: `o3` and `o4` (staggered to `length_cells = 10`, giving a forward reach of `10 + 4 - 1 = 13` cells, reaching `x = 627` from their shared base column `x = 640`) reserve cells at `x = 627` through `x = 630` across every row from `y = 163` through `y = 171` -- which includes `o2`'s own row range (`o2`'s narrowed lane, after mechanism 2, is `y = 164-165`). `o2` itself was only staggered to `length_cells = 7` (reach `10` cells, to `x = 630`), so its own footprint never reserved `x = 627` through `629` for itself -- but `o3`/`o4` already reserved it, and `o2`'s job gets no exemption for `o3`/`o4`'s reservation. The result: `o2`'s narrowed 2-row lane is completely walled in, with zero cells belonging to any other net's already-committed route bordering it (confirmed directly -- this is a standing obstacle-map fact present before any routing happens, not congestion from routing activity), and the true open routing fabric, which genuinely starts at `x <= 626` for every relevant row, is unreachable. This is exactly why `multiportmmi_8x8` net `n_24` (`mmi0_ps_array_0_heater_1,o2 -> mmi0_multiport_0_0,o2`) failed with `No route found`.

### The fix: equalize reach within each dense group

Since the blocking reservation always comes from a *sibling in the same group*, and no sibling's own raw reservation can ever extend beyond whichever sibling in that group currently reaches furthest (by construction -- there is no fourth party), the complete fix is: after computing the initial staggered lengths for a qualifying group, find the group's current maximum forward reach (`length_cells + half_width_cells - 1`, maximized over every port in the group, using the shared `half_width_cells` value, since staggering never changes width) and raise every port in the group to the `length_cells` that produces that same maximum reach. This cannot make any port's reservation extend further than the group already, collectively, reserved before the fix -- it only removes the *gaps* between differently-staggered siblings, by giving every sibling the same forward reach as the one that already reached furthest. Because this happens once, per group, using only values already computed earlier in the same function call (no other port's not-yet-computed footprint needs to be examined, and no global obstacle-map attribute needs to be queried), it has no ordering dependency on when in `_RouteNetsRustSession.run()` it executes, unlike the abandoned "probe the obstacle map" design (see Surprises & Discoveries) whose ordering problem was the entire root cause of the first, failed implementation attempt.
