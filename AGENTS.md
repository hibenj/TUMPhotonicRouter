# AGENTS.md - TUMPhotonicRouter agent map

This file is the map, not the manual. It says where things are and which
rules apply; the details live in the documents it points to. Keep it short:
add a rule here only after a mistake repeated.

## Read first

- `docs/ARCHITECTURE.md`: the module map (Rust and Python), the stage
  sequences of the optical router (`translation/routing/session.py`) and of
  the electrical router (`translation/electrical/route_electrical.py`), the
  search and negotiation interfaces, configuration precedence, build and test
  commands.
- `docs/CONFIGURATION.md`: every configuration field with default, overlay
  variable and command-line flag (generated by
  `scripts/generate_config_reference.py`).
- `.agent/REPOSITORY_STATE.md`: where the work stands; update it before every
  stop, pause or handoff.
- `.agent/PLANS.md`: the ExecPlan format. Task plans live in
  `.agent/execplans/`; old plans are history unless the request resumes them.
- `.agent/WORKFLOW.md` and `.agent/ORCHESTRATOR.md`: roles, delegation and
  validation rules; `.agent/GIT_WORKFLOW.md`: commits and checkpoints.

## Operating sequence

1. Orient: this file, the relevant code, the active ExecPlan.
2. Plan: one self-contained ExecPlan when the work spans several files,
   algorithms or validation stages.
3. Implement in scoped slices; record discoveries and decisions in the plan.
4. Review for correctness, regressions, missing tests, repository fit.
5. Validate: the narrowest check first, then the gates (below); record the
   evidence in the plan.

## What the project is

A hybrid Rust and Python photonic routing system: a schematic becomes an
unrouted layout (`translation/layout_from_schematic.py`), waveguides are routed
by a grid A* over straight and bend primitives in Rust (`src/`, bound through
PyO3 as `photonic_router._rust`), path lengths are matched, and heater metal is
routed electrically (`translation/electrical/`). Benchmarks are Python modules
in `benchmarks/` with a `build_schematic()` and optional
`STABLE_ROUTING_FLAGS`; `heater_s_mod` is the 8-mode cascade, `cascade_*` the
generated 8, 12 and 16-mode cascades, folded and diagonal.

```
python -m photonic_router route <benchmark> [--configuration baseline|contribution1|contribution2]
```

Exactly one of the three paper configurations runs at a time; contributions
never leak into the baseline defaults. `--debug-svgs <selector>` writes SVGs
for visual debugging only; do not produce them by default.

Every run ends with one grep-able line, `SUMMARY benchmark=... nets=...
route_failures=... verifier_errors=... plm_over_tolerance=...
meander_inserted_um=... electrical_ok=... total_s=...`; read that before the
stage output. Before a merge to `main`, run the saved workflow
`/merge-review` (one reviewer per changed file, findings adversarially
verified, then ranked).

## Build, test, gate

Linux: `docs/ARCHITECTURE.md` section 8 has the exact commands (toolchain and
`PYO3_PYTHON` overrides). Windows: `docs/WINDOWS_RUST_TOOLCHAIN.md`.

- `maturin develop --release` builds the extension; `cargo check` first on
  Rust errors.
- `scripts/test_baseline.sh`: Rust and Python suites against the pinned counts
  (`tests/baselines/test_baseline.txt`); the fast suite
  (`pytest -m "not e2e" tests`) must stay under 60 s.
- `scripts/results/gate_short.sh`: the nine smallest paper cells reproduced
  exactly; run after any change that can touch the optical router.
- `scripts/benchmark_electrical.py --suite --check --compare-baseline`: the
  electrical cases against their guardrails and the pinned baseline
  (`tests/baselines/electrical_suite_metrics.json`); zero drift is the gate
  for behaviour-preserving slices, a re-pin with a dated comment for
  intentional changes.

Tests: `tests/` unit and integration, `tests/e2e/` full runs, `tests/electrical/`
one module per electrical stage; synthetic layouts only in `tests/fixtures/`.
Rust tests sit next to their modules.

## Rules that repeated mistakes taught

- The Python and Rust configuration mirrors (`python/photonic_router/config.py`,
  `src/config.rs`) carry the same fields and defaults; nothing under `src/` or
  `translation/electrical/` reads the environment.
- A render or a metric without a verifier contract behind it proves nothing:
  check connectivity and per-branch metrics before quoting numbers.
- Never write a repository-owner decision that the owner did not make; leave
  it open in the plan's Decision Log.
- Confidential source material of the owner is read in place and never
  copied into the repository or elsewhere.

## Adding things

- A benchmark: a module in `benchmarks/` with `build_schematic()`; see
  `benchmarks/cascade.py` for a parametric builder.
- A configuration field: both mirrors, `RouterConfig.to_rust`, an overlay
  entry if ad hoc, a `FlowOptions` field and flag if flow-level, then
  regenerate `docs/CONFIGURATION.md`.
- A search engine or a negotiation policy: the recipes in
  `docs/ARCHITECTURE.md` sections 4 and 5.
- An electrical stage: `translation/electrical/stages.py` declares one
  `Protocol` per stage; `route_electrical.py` is the sequence.
